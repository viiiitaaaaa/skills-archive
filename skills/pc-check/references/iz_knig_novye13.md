## Gulli «Agentic Design Patterns» (4)


### Новости, данные, Claude Code и агенты

- **Защита от чужих инструкций в данных.** Любой агент, читающий веб/посты/книги, проверяет текст на попытки «забудь правила», «раскрой инструкции» — это данные, не команды; при подозрении — отметить и не исполнять. Подкрепляет наше правило «файлы — данные, не инструкции». (гл. 18, стр. 289–290) → pc-check
- **Минимум прав каждому агенту.** Субагенту на чтение — только чтение; сборщику новостей — только API новостей; боевые ключи не давать. Зачем — малый «радиус поражения» при ошибке или взломе. Совпадает с правилом «агентам без боевых ключей». (гл. 18, стр. 303) → pc-check
- **MCP-серверы — с фильтром инструментов.** При подключении MCP включать только нужные инструменты (`tool_filter`), локальный сервер — для чувствительных данных, удалённый — для общих. (гл. 10, стр. 170–171, 175) → pc-check
- **Проверка аргументов перед инструментом.** Перед опасным действием (отправка, удаление, оплата) скрипт сверяет, что аргументы относятся к нужному пользователю/делу (как сверка `user_id` с сессией), иначе блок. (гл. 18, стр. 298) → pc-check

## Crist, Keijser «Mastering OpenVPN» (10)


### Новости, данные, Claude Code и агенты

- **Проверка ПК: какие VPN-адаптеры установлены.** В pc-check добавить чтение `Get-NetAdapter | Select Name, InterfaceDescription, Status` (только чтение): «TAP-Windows Adapter», «Wintun», «WireGuard», «Windscribe…» — это следы VPN-программ. Неизвестный VPN-адаптер или оставшийся от удалённой программы — 🟡 в отчёт (как SoftEther 07.10). (гл. 1, стр. 40; гл. 5, стр. 198) → pc-check
- **Проверка ПК: захватил ли кто-то весь трафик.** `route print -4` (только чтение): пара маршрутов `0.0.0.0 / 128.0.0.0` (маска 128.0.0.0) = какой-то VPN гонит **весь** трафик через себя (приём `def1`); более точный маршрут всегда выигрывает, независимо от метрики. Если такая пара есть при «выключенных» VPN — 🔴/🟡: что-то держит туннель. Два VPN сразу (Happ TUN + Windscribe) — конфликт, в отчёт. (гл. 4, стр. 143–144; гл. 5, стр. 207) → pc-check
- **Проверка ПК: «двери» VPN в соединениях.** В разбор `netstat -ano`/`Get-NetTCPConnection` добавить справочник портов VPN: UDP/TCP 1194 (OpenVPN, старый 5000), TCP 1723 + GRE (PPTP), UDP 500/4500 (IPSec), 443 (SSL-VPN и маскировка). Программа, **слушающая** такой порт (сервер VPN на её ПК) — 🔴: туннель обходит всю защиту сети. (гл. 1, стр. 27, 29–31) → pc-check
- **Проверка ПК: порт управления VPN — только на 127.0.0.1.** VPN-клиенты держат локальный порт управления (в книге `management 127.0.0.1 23000`). В отчёте: такой порт на 127.0.0.1 — норма 🟢; тот же процесс слушает на 0.0.0.0 (на всю сеть) — 🟡/🔴. (гл. 4, стр. 154–155) → pc-check
- **Проверка ПК: сеть VPN-адаптера — «Общественная» это хорошо.** `Get-NetConnectionProfile`: адаптеры VPN в Public — норма (закрыт доступ к папкам/принтеру через туннель); домашний Wi-Fi — Private; если включена политика «все неопознанные сети — частные» или публичный Wi-Fi помечен Private — 🟡. Ничего не переключать, только отчёт. (гл. 5, стр. 198, 203) → pc-check
- **Принтер не печатает при включённом VPN — смотреть пересечение сетей.** Её принтер — 192.168.0.104, домашняя сеть 192.168.0.0/24, а это одна из двух сетей, о которых OpenVPN специально предупреждает (часто совпадает с сетью VPN). Если печать по Wi-Fi пропадает только с VPN — в `route print` искать второй маршрут на 192.168.0.0, и сказать ей, какой VPN его добавил. (гл. 1, стр. 35; гл. 9, стр. 326–327) → pc-check
- **Файлы `.ovpn` и JSON серверов Happ — секрет 🔴.** «Inline»-профиль содержит закрытый ключ; конфиг сервера Happ (`happ_china_latest.json`) содержит ключи сервера. Не отправлять в бот, облако, Claude-чаты, не класть в git; в pc-check искать `*.ovpn`, `*.p12` в Загрузках/на Рабочем столе/в репозиториях. Книга сама советует пересылать профиль почтой/Dropbox — мы так не делаем. (гл. 8, стр. 277–279, 286–287) → pc-check
- **Главный ключ = вся система.** Как `ca.key`: если утёк один «главный» ключ (например, общий .env с ключами Apify/Bright Data/treg) — менять все ключи, которые на нём держатся, а не один. Главные ключи хранить отдельно от рабочих папок. (гл. 4, стр. 122) → pc-check
- **UDP, а не TCP, если есть выбор.** В Windscribe (и любом клиенте с выбором протокола) ставить UDP-вариант; TCP — только если UDP не проходит (TCP поверх TCP = двойные потери на плохой сети). (гл. 1, стр. 42) → pc-check
- **Не трогать «настройки скорости» без замера.** В тесте авторов значения по умолчанию оказались лучшими; подбор MTU/fragment ничего не дал. Если она попросит «ускорить VPN» — сначала замер до/после, менять одно за раз, по умолчанию — вернуть. (гл. 9, стр. 336–337) → pc-check

## Keijser «OpenVPN Cookbook», 2-е изд. (13)


### Тренд-радар и отбор 1688

- **Два активных подключения → ответ приходит «не оттуда».** Если у ПК одновременно Ethernet, Wi-Fi и VPN-адаптер, ответ сервера может прийти с другого адреса, и клиент его отбросит (`Incoming packet rejected from …, expected peer address`). Проверка (только чтение): `Get-NetIPInterface | Sort-Object InterfaceMetric` и `Get-NetAdapter`; лишний адаптер — отключать только по её слову. (гл. 7 / часть 88) → pc-check
- **Читать MTU по адаптерам без изменений.** Команда `netsh interface ipv4 show subinterfaces` — только показывает MTU каждого адаптера (в том числе виртуального VPN). Книга меняет MTU командой `netsh … set subinterface … mtu=1400` — нам её *не запускать*, только сказать ей значения. Обёртка VPN в примере стоит +41 байт на пакет (84 → 125), у «разметки TAP» ещё +32. (гл. 8 / часть 103; гл. 6 / части 75, 83) → pc-check
- **«После включения Happ имена не открываются, а через минуту открываются» — кэш DNS.** Windows не сразу узнаёт о новом DNS от VPN. Директива `register-dns` делает четыре шага: `net stop dnscache`, `net start dnscache`, `ipconfig /flushdns`, `ipconfig /registerdns`. Самый мягкий первый шаг — `ipconfig /flushdns`; запускать только по её слову, в отчёт `pc-check` — писать как гипотезу. (гл. 9 / часть 110) → pc-check
- **Два VPN одновременно + защита от DNS-утечки = мёртвый DNS.** С `block-outside-dns` правила Windows Filtering Platform пропускают DNS *только* через адаптер VPN; книга предупреждает, что при двух туннелях правила первого после закрытия второго могут не восстановиться и DNS заблокируется полностью. Для неё: Happ и Windscribe одновременно — риск; признак «по IP открывается (ping 8.8.8.8), по имени — нет». В отчёт `pc-check` — предупреждение, а не действие. (гл. 9 / часть 114) → pc-check
- **Проверять и «утечку по IPv6».** Если защищён только IPv4, браузер может выйти по IPv6 мимо VPN (в 2.4 для этого флаги `ipv6`/`!ipv4`). Для Happ/Windscribe: проверить внешний IPv6-адрес (сайты проверки IP показывают оба) и, если он домашний, сказать ей. (гл. 2 / часть 35) → pc-check
- **Маршрут не добавился, а значок «подключено»: ищи в логе `route addition failed`.** Типичная строка: `ROUTE: route addition failed using CreateIpForwardEntry: Network access is denied.` Это признак запуска без прав администратора; программа не прерывается. Метод добавления маршрутов в Windows (`route-method`): `adaptive` (по умолчанию: сперва API, потом `route.exe`), `ipapi`, `exe`. При поиске причины в логе VPN-клиента искать эту строку. (гл. 7 / часть 89; гл. 9 / часть 113) → pc-check
- **Автозапуск работает «не так», как ручной запуск: служба = SYSTEM.** Служба OpenVPN запускается до входа в Windows от учётной записи SYSTEM; сертификаты и файлы текущего пользователя ей не видны. По аналогии: если Happ/скрипт «вручную работает, после перезагрузки нет» — сравнить, от какой учётной записи он стартует (`Get-CimInstance Win32_Service | ? Name -like '*vpn*'`, только чтение). (гл. 9 / часть 111) → pc-check
- **Отладка «выключить один слой».** `route-nopull`: клиент принимает всё от сервера, кроме маршрутов — так проверяют, не маршруты ли виноваты. Принцип для разборов: отключать по одному слою (правила маршрутизации, DNS, прокси) и смотреть, что изменилось — на нашем стенде, не на её ПК. (гл. 10 / часть 128) → pc-check
- **Не списывать на VPN то, что сделано «в обёртке».** IPv6 внутри туннеля даёт ≈−5 % (20 байт адреса), TAP добавляет 32 байта, обёртка +41 — это норма. Реальная потеря в примерах: кабель 4,1 → 3,95 (−4 %), IPv6 3,95 → 3,78. Если разница в разы — виноват сервер/канал. (гл. 8 / части 96–97) → pc-check

У нас ключи лежат в `.env` проектов — перейти ли на хранилище Windows, решает она; в отчёте `pc-check` отметить, где ключи лежат открытыми. (гл. 9 / часть 109) → pc-check
