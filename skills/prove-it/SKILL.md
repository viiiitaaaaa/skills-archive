# Проверка работы агента

Агент почти никогда не врёт намеренно. Он сообщает то, что видит со своей
стороны, и этого часто недостаточно: команда вернула успех, но успех означал
не то; файл изменён, но не тот; тест зелёный, потому что ничего не проверяет.

Правило одно: **заявление без свежего доказательства не принимается.**
Не «запускал недавно», не «должно работать» - вывод команды в этом же ходе.

## Отчёт о проверке: прикладывается к слову «готово»

Это главное правило скилла, и оно про собственное поведение, а не про
чужое. **Заявление о завершении работы без отчёта о проверке не делается.**
Человеку не нужно каждый раз спрашивать «а ты точно проверил» - ответ
приходит вместе с результатом.

Отчёт короткий, 3-6 строк, и идёт в чат сразу под выводом о готовности:

```
Проверено:
  <что именно утверждается>  →  <чем доказано, с выводом>
  <что именно утверждается>  →  <чем доказано, с выводом>
Не проверено:
  <что осталось за рамками и почему>
```

Живой пример того, как это выглядит:

```
Готово: фильтр по датам в отчёте починен.

Проверено:
  тесты не падают        → pytest tests/reports, 34 passed, 0 failed
  исходный баг ушёл      → запрос за 31.03 возвращает 12 строк,
                           до правки возвращал 0
  правки в файлах        → git diff: reports/filters.py, +14 −6
Не проверено:
  поведение на годовом диапазоне - выходит за рамки задачи
```

**Что делает отчёт честным:**

```
Правило                         Почему
──────────────────────────────  ──────────────────────────────────
Вывод команды свежий            «запускал раньше» означает, что
                                проверялось другое состояние кода
Показан результат, не факт      «прогнал тесты» - не доказательство;
запуска                         «34 passed, 0 failed» - доказательство
Строка «Не проверено» есть      пустой список подозрителен: что-то
всегда                          всегда остаётся за рамками
Догадка помечена догадкой       часть вывода почти всегда достроена
                                по контексту, и читатель должен
                                видеть, какая именно
```

**Чего в отчёте быть не должно:** пересказа вместо вывода («всё прошло
успешно»), слов «должно работать», «скорее всего», «по идее», а также
радости раньше доказательства («Отлично, всё исправлено!»).

Если проверить что-то не удалось - так и написать. Честное «не проверил,
потому что нет доступа к базе» полезнее уверенного «всё работает»:
по первому можно принять решение, по второму нельзя.

## Быстрая проверка: пять вопросов

Задать их себе (или агенту) перед тем, как принять работу:

```
1  Какая команда доказывает это заявление?
2  Она запущена ПРЯМО СЕЙЧАС, а не раньше?
3  Я прочитал весь вывод, включая код возврата?
4  Вывод подтверждает именно заявление, а не соседнее?
5  Изменения реально в файлах - diff показывает их?
```

Пропущен любой пункт - работа не принята.

## Чем доказывается каждое заявление

```
Агент сказал            Доказательство              НЕ доказательство
──────────────────────  ──────────────────────────  ────────────────────────
«тесты проходят»        вывод прогона: 0 упавших    прошлый запуск,
                                                    «должны проходить»
«баг исправлен»         исходный симптом больше     код изменён,
                        не воспроизводится          «по логике должно»
«сборка проходит»       команда сборки, код 0       линтер чистый,
                                                    «логи выглядят нормально»
«файл обновлён»         diff показывает строки      агент сказал «записал»
«сообщение доставлено»  адресат подтвердил приём    API вернул success
«задача выполнена»      критерии из задания         «всё сделал»
                        по пунктам
```

Последняя строка самая частая: «выполнил» проверяется не общим впечатлением,
а построчной сверкой с тем, что просили.

## Красные флаги в ответе агента

Эти слова означают, что проверки не было:

```
«должно работать»        «по идее»           «probably»
«скорее всего»           «я уверен»          «всё готово!»
«осталось только»        «в целом работает»  «should pass»
```

Отдельный флаг - радость раньше доказательства. «Отлично, всё исправлено!»
без вывода команды означает, что команду не запускали.

## Ловушка успешного ответа

Самый неприятный случай: команда честно вернула успех, но успех означал
не то, что подумал агент.

```
Вернулось              Что это значит        Что НЕ значит
─────────────────────  ────────────────────  ─────────────────────────
success: true          запрос принят         адресат получил
exit 0 у линтера       стиль в порядке       код компилируется
тест зелёный           тест не упал          тест что-то проверяет
файл записан           запись прошла         содержимое правильное
```

Поэтому вопрос «что именно доказывает этот вывод» задаётся отдельно от
вопроса «успешно ли завершилась команда».

## Проверка, которая никогда не краснела, ничего не проверяет

Прежде чем опереться на проверку, стоит специально сломать то, что она
защищает, и посмотреть, заметит ли она. Не заметила - значит, она и раньше
ничего не ловила, просто светилась зелёным.

Типичный случай: 22 теста на текст предупреждения были зелёными, при этом
текст можно было заменить целиком на любой другой - все 22 остались бы
зелёными. Они проверяли, что предупреждение есть, но не что в нём написано.

## Спрашивать не только «нужное на месте», но и «лишнего не появилось»

Проверки обычно ищут то, что должно быть, и не смотрят на то, чего быть
не должно. Так рядом со старой версией функции появилась вторая, и вызов
стал падать с ошибкой неоднозначности - при полностью зелёной проверке.

Второй вопрос той же природы: результат действительно свежий или механизм
просто отработал вхолостую? Зелёный прогон не означает, что данные обновились.

## Проверка по именам не заменяет проверку по содержимому

Обновление скопировало старую версию кода и молча отменило прошлое
исправление. Проверка искала нужные блоки по названиям, нашла все до одного
и отчиталась успехом - внутри одного из них лежала старая логика.

Если проверяется наличие чего-то, стоит убедиться, что проверяется именно
содержимое, а не заголовок, имя файла или факт существования.

## Две независимые проверки могут оказаться одной

Два разных способа проверки, смотрящие в один и тот же источник, дают
иллюзию двойного подтверждения, а не двойное подтверждение.

Реальный случай: агент опровергал существование файла двумя способами -
поиском по папке и поиском в системе контроля версий. Оба вернули «пусто»,
файл существовал: агент смотрел в устаревшую копию проекта, и обе проверки
смотрели туда же.

Прежде чем считать проверки независимыми, стоит спросить, что будет, если
источник данных у них общий и он неверен.

## Цифры проверяются там, где живут настоящие данные

Число, которое уйдёт наружу - клиенту, в отчёт, в документ - проверяется
на реальной системе, а не на тестовой копии. Расхождения бывают
катастрофическими: 2 документа на стенде против 5719 на живой системе.

## Как встроить в работу

Три рабочих способа, от простого к системному:

**Сверка по пунктам.** Задание разбивается на проверяемые пункты заранее.
На приёмке каждый пункт закрывается своим доказательством. Пункт без
доказательства считается невыполненным, а не выполненным по умолчанию.

**Второй агент.** Один пишет, второй проверяет. Формулировка задания
проверяющему решает всё: «проверь, всё ли верно» даёт подтверждение,
«найди, где это не работает» даёт находки.

**Падающий тест до кода.** Если тест не падал ни разу, неизвестно, что он
проверяет. Тест, написанный после кода, подгоняется под готовое решение.

## Что делать с найденным

Обнаружив незакрытое заявление, вернуть работу с конкретикой: какой пункт
не доказан и какая команда это покажет. Общее «проверь ещё раз» приводит
к повторному «всё готово».

Формулировка для агента, которая работает:

```
Пункт 3 не принят. Заявлено «тесты проходят», вывода прогона нет.
Запусти <команда> и покажи результат целиком, включая код возврата.
```
