# Lanham «AI Agents in Action» — как делать (черновик)

Источник: только конспекты глав в `C:\Users\User\knigi_kupleno\glubokiy\` (12 файлов). Ничего сверх конспектов не добавлено.
Страницы даны как в конспекте. У части разделов номера в самом конспекте «поплыли» (например «стр. 80–61»), такие места помечены «(номер в конспекте сомнителен)». Сверять по книге перед важным решением.
Термины: LLM = большая языковая модель (нейросеть, которая пишет текст). Промпт = текст-запрос к модели. Токен = кусочек текста, за который берут деньги.

## Глава 1. Агенты и их мир (стр. 25–37)

Если хочу понять, что такое агент и сколько видов бывает:
- 4 уровня общения с LLM: 1) напрямую, без агента; 2) агент-прокси (посредник, переформулирует запрос, например для картинок); 3) агент/ассистент (вызывает внешние функции, пользователь подтверждает); 4) автономный агент (сам планирует и решает) (стр. 2 по конспекту; «пользователь подтверждает» в конспекте обрезано)
- 5 главных частей агента: профиль/персона, действия и инструменты, память и знания, рассуждение и оценка, планирование и обратная связь (стр. 5–8)
- Агент = сущность, которая автоматизирует работу с LLM, чтобы получать результат и самой принимать решения (стр. 36–37)

Если хочу собрать агента по пяти частям — шаги: 1) определить задачу и роль (профиль/персона, стр. 5); 2) подключить инструменты и функции (Actions, стр. 6); 3) настроить память и источники знаний (стр. 7); 4) добавить логику и оценку (стр. 8); 5) запустить планирование и обратную связь, чтобы задача шла по кругу итераций (стр. 8)

Примеры:
- Многоагентная система: «контроллер» (прокси) говорит с пользователем, фоновые агенты (программист, тестировщик) пишут код и тесты (стр. 3)
- AutoGPT: задача выполняется по шагам, на каждом шаге оценивается, достигнута ли цель (стр. 10)

Предупреждения:
- Автономные агенты вызывают вопросы этики и безопасности: мы не до конца понимаем их возможности. Доверие растёт через постепенное внедрение и контроль прав доступа (стр. 25–35)
- Автономного от неавтономного агента отличать важно: первый принимает решения сам (стр. 36)

## Глава 2. Силы LLM: API, локальные модели, промпты (стр. 38–62)

Если хочу подключиться к OpenAI из скрипта — шаги: 1) `pip install openai python-dotenv` (стр. 41); 2) ключ положить в `.env` (не из конспекта, моя добавка); 3) пример скрипта `connecting.py` (стр. 41)

Если хочу запустить модель у себя (LM Studio) — шаги: 1) выбрать модель; 2) нажать «Start Server»; 3) подключаться по адресу `http://localhost:1234/v1` (стр. 23 по конспекту, номер сомнителен); пример `lmstudio_server.py` (стр. 48)
- Если связь не идёт: проверить Server Model Settings, загруженная модель должна совпадать с настройками сервера (стр. 25)

Правила:
- Температура (`temperature`) от 0 до 1: 0 = самый стабильный ответ, 1.0 = самый разнообразный (стр. 41–43)
- 3 роли в чате: `system` (правила и контекст), `user` (запрос), `assistant` (история ответов) (стр. 42)

Приёмы промпта (стр. 51–57): писать подробно; назначать роль (от лица студента/инженера); отделять части разделителями (`'''` или теги вроде `<statement>`); давать пошаговые инструкции; давать примеры (few-shot, «несколько примеров»); ограничивать длину ответа (в словах или пунктах)

- Поддерживаемые компоненты на момент книги: knowledge (знания), memory (память), actions (действия) (стр. 68)

Если хочу подключить ассистента к своему API (custom actions, стр. 73–80) — шаги: 1) сделать помощника-генератора кода FastAPI и OpenAPI-описания (стр. 73); 2) попросить эндпоинт, например GET со списком задач (стр. 74); 3) сохранить код (`daily_tasks_api.py`), поставить `fastapi`, `uvicorn`, запустить `uvicorn daily_tasks_api:app --reload` (стр. 74–75); 4) открыть `http://127.0.0.1:8000/docs`, скопировать `openapi.json` (стр. 75–76); 5) запустить туннель: `./ngrok authtoken <ТОКЕН>`, затем `./ngrok http 8000` (стр. 76–77); 6) в ассистенте нажать Create New Action, вставить описание и добавить блок `servers` с адресом ngrok (стр. 77–78)
- Порт FastAPI в примере — 8000 (стр. 75)
- Опасно: публичный ассистент с действиями могут запускать незнакомые люди. Не выставлять наружу сервисы, которые берут деньги за запросы, и не гнать личные данные через ngrok (стр. 79)

- Лимит: до 512 МБ на одного ассистента (стр. 80); за раз примерно 5 файлов, зависит от размера (стр. 60 по конспекту, номер сомнителен)
- Без правила «только загруженное» ассистент подтягивает общие знания модели (не из конспекта, без страницы)
- Образцы запросов (таблица 3.1, стр. 61): поиск фразы в знаниях; «назови три самые похожие книги»; «какая из книг самая современная»

Если хочу опубликовать ассистента (стр. 61–65, номера сомнительны) — шаги: 1) убедиться, что протестирован (стр. 64); 2) Share, выбрать GPT Store, Save (стр. 61, 63); 3) указать категорию и ссылки на соцсети/GitHub для обратной связи (стр. 63–64)
- Расход идёт с аккаунта пользователя, не разработчика. Картинки, частый запуск кода, Vision (описание картинок), много файлов могут временно заблокировать аккаунт пользователя (стр. 62)
- Правило-образец: «RULE: When generating images, ensure the user is aware that creating multiple images quickly could temporarily block their account.» (стр. 62)

## Глава 4. Многоагентные системы: AutoGen, CrewAI, AgentOps (стр. 92–119)

- `human_input_mode="ALWAYS"` — спрашивать человека на каждом шаге (стр. 102); окончание чата по слову `TERMINATE` через лямбду (стр. 102)

Если хочу, чтобы второй агент проверял код первого (критик, стр. 103–105) — шаги: 1) агент-инженер `AssistantAgent` с системным промптом Python-разработчика (стр. 104); 2) агент-критик с промптом код-ревьюера (поиск уязвимостей и ошибок) (стр. 104); 3) функция `review_code`, берущая последнее сообщение инженера (стр. 104); 4) `user_proxy.register_nested_chats([{"recipient": critic, "message": review_code, "summary_method": "last_msg", "max_turns": 1}], trigger=engineer)` (стр. 104)
- `max_turns=1` у вложенного чата критика (стр. 104); `max_turns=2` у основного вызова (стр. 105)
- Цепочки и вложенные чаты искажают информацию («испорченный телефон»), контролировать `max_turns` (стр. 106)

Если хочу сэкономить токены при отладке (кэш AutoGen, стр. 105–106) — шаги: 1) обернуть вызов в `with Cache.disk(cache_seed=42) as cache:` (стр. 105–106); 2) передать `cache=cache` в `initiate_chat` (стр. 106)
- Кэш хранится в SQLite в папке `.cache`, позволяет продолжить прерванный разговор; `cache_seed` (любое число) выбирает хранилище (стр. 105–106)
- Без кэша сложные многошаговые задачи быстро упираются в лимит токенов (стр. 105)

Если хочу, чтобы агенты видели общий контекст (групповой чат, стр. 106–108) — шаги: 1) импортировать `GroupChat`, `GroupChatManager` (стр. 106); 2) `groupchat = GroupChat(agents=[user_proxy, engineer, critic], messages=[], max_round=20)` (стр. 107); 3) `manager = GroupChatManager(groupchat=groupchat, llm_config=llm_config)` (стр. 107); 4) запускать с `recipient=manager` (стр. 108)
- `max_round=20` — максимум раундов (стр. 107); `human_input_mode="NEVER"` — полностью без человека (стр. 107)
- Минус: групповые чаты «многословнее» и тратят больше токенов (стр. 108)

Если хочу чёткий конвейер ролей (CrewAI, стр. 108–111) — шаги: 1) `from crewai import Agent, Crew, Process, Task` (стр. 109); 2) агентам задать `role`, `goal`, `backstory`, `verbose=True`, `memory=True` (стр. 108–110); 3) задачам — `description`, `expected_output`, `agent` (стр. 110); 4) `Crew(agents=[...], tasks=[...], process=Process.sequential, memory=True, cache=True, max_rpm=100)` (стр. 111); 5) `crew.kickoff(inputs={"topic": "..."})` (стр. 111)
- `max_rpm=100` — не больше 100 запросов в минуту (стр. 111)
- CrewAI требует больше настройки, чем AutoGen, но даёт жёсткий контроль процесса; UserProxy не обязателен (стр. 108)

Если хочу видеть, что агенты делают и сколько это стоит (AgentOps, стр. 111–114) — шаги: 1) `pip install agentops` (или `pip install crewai[agentops]`) (стр. 112); 2) зарегистрироваться на app.agentops.ai, создать проект, скопировать ключ (стр. 112); 3) в `.env`: `AGENTOPS_API_KEY="..."` (стр. 112); 4) в скрипте `import agentops` и `agentops.init()` сразу после загрузки переменных окружения (стр. 112)
- Пример цены: одна шутка у агентов стоила чуть больше 50 центов (стр. 113)
- Агенты могут незаметно «сжигать» деньги из-за многословности и повторов, считать затраты надо до коммерческого запуска (стр. 113)

Если хочу команду «разработчик + проверяющие» (CrewAI, стр. 114–119) — шаги: 1) агенты: Senior Engineer, QA Engineer, Chief QA Engineer (стр. 114–115); 2) задачи `code_task`, `qa_task`, `evaluate_task` с `expected_output` (стр. 115–116); 3) для иерархии: `process=Process.hierarchical, manager_llm=ChatOpenAI(temperature=0, model="gpt-4")` (стр. 116–118); 4) `crew.kickoff()` (стр. 116)
- Иерархический режим может стоить в 2 раза дороже последовательного без заметного роста качества (стр. 118)
- График Repeat Thoughts в AgentOps: если агент повторяет мысли, он нерешителен — менять промпты, задачи или состав команды (стр. 118)
- Образец ожидаемого вывода тестировщика: «Your Final answer must be the full python code, only the python code and nothing else.» (стр. 115–116)

## Глава 5. Действия агента: function calling, плагины, Semantic Kernel (стр. 120–152)

Если хочу, чтобы агент делал дела во внешнем мире:
- Плагин/инструмент расширяет LLM: пользователь просит, LLM узнаёт плагин и вытаскивает параметры, плагин собирает данные (например, с сайта), LLM формулирует ответ (рис. 5.1, стр. 123)
- Агент — потребитель и координатор инструментов, не путать его с самой функцией (стр. 123–124)
- Function calling не поддерживался в открытых (open-source) моделях на момент написания книги (стр. 126)

Если хочу вызов функций OpenAI — шаги: 1) в запросе передать описание функций в параметре `tools` (стр. 125, листинг 5.1); 2) получить имя функции и аргументы в JSON (стр. 127); 3) проверить в коде, есть ли `tool_calls` (стр. 130); 4) найти свою локальную функцию, передать аргументы, выполнить (стр. 130); 5) результат добавить в `messages` с ролью `tool` и сделать второй запрос, чтобы модель ответила человеческим языком (стр. 130, рис. 5.4)
- Критично: сама LLM функцию НЕ выполняет, она лишь возвращает имя и аргументы; запускает ваш код (стр. 125–130)
- Для делегирования функций годится более дешёвая модель, например `gpt-3.5-turbo-1106` (стр. 129)
- Примеры: `chapter_4/first_function.py`, `chapter_4/parallel_functions.py` (стр. 126, 127)

Если хочу Semantic Kernel (SK, оркестратор от Microsoft: плагины, навыки, память, планирование; стр. 131–134) — шаги: 1) `pip uninstall semantic-kernel`, `git clone https://github.com/microsoft/semantic-kernel.git` (стр. 132, лист. 5.8); 2) `cd semantic-kernel/python`, `pip install -e .` (стр. 132); 3) `kernel = sk.Kernel()` и добавить сервис чата OpenAI или Azure OpenAI с ключами из `.env` (стр. 132, лист. 5.9)
- Языки: Python, Java, C#; плагин на одном языке нельзя напрямую использовать в другом (стр. 132)
- В шаблонах промпта переменные вида `{{$format}}`, `{{$subject}}`, `{{$genre}}` (`SK_context_variables.py`, стр. 134, лист. 5.10)
- `kernel.invoke_prompt` может потребовать `asyncio.run` (стр. 133)
- Терминология плавает: SK сначала звал модули «skills», потом «plugins», в коде остались старые названия (стр. 131–132)

Если хочу соединить промпт и обычный код (семантические + нативные функции, стр. 135–142) — шаги: 1) нативный код в классе, например `MySeenMoviesDatabase` (стр. 139, лист. 5.14); 2) декоратор `@kernel_function(description="...", name="...")` на каждый метод (стр. 139); 3) `kernel.import_plugin_from_object(MySeenMoviesDatabase(), "SeenMoviesPlugin")` (стр. 140, лист. 5.15); 4) вставлять в текст промпта `{{MySeenMoviesDatabase.LoadSeenMovies}}` (стр. 141, лист. 5.16)
- Структура плагина-промпта: папка плагина, папка функции, `config.json` (тип `completion`) и `skprompt.txt` (стр. 137, рис. 5.7)
- Функция, просто написанная в коде, в ядре сама не регистрируется — нужен явный импорт через `import_plugin` (стр. 142)

## Глава 6. Деревья поведения и Playground (стр. 153–183)

Если хочу управлять агентами по плану с проверками (дерево поведения, Behavior Tree, BT; стр. 153–160):
- BT придуман для роботов и игр (Родни Брукс, 1986). Узлы возвращают `SUCCESS` или `FAILURE`, не True/False (стр. 151 по конспекту, номер сомнителен). Обход сверху вниз и слева направо (стр. 154)

## Глава 8. Знания (RAG) и память агента (стр. 205–233)

Различие: знания = дополнение промпта из готовых документов, не память; память обновляется в ходе диалогов (стр. 205–206, 224).

Если хочу, чтобы агент отвечал по моим документам (RAG, генерация с извлечением) — две фазы (стр. 206–207): индексирование: 1) загрузить документ, разбить на чанки (куски); 2) превратить в векторы (эмбеддинги — числовые «отпечатки смысла») и сохранить в векторную БД. Запрос: 3) запрос превратить в вектор; 4) найти похожие чанки; 5) отдать найденное и вопрос в LLM
- Приёмы промпта: «Provide Reference Text» (даёт опорный текст, меньше выдумок) и «Use External Tools» (стр. 205–206)
- Шаги паттерна: Retrieve, Augment, Generate, Remember (сохранить ответ в память) (рис. 8.2–8.3, стр. 206–207)

Если хочу понять поиск по смыслу (стр. 208–215):
- TF = число вхождений слова ÷ число слов в документе (стр. 209). IDF = логарифм (всего документов ÷ документов со словом). TF-IDF = TF × IDF. Пример «blue»: TF 0.1670, IDF 0.301, TF-IDF 0.050 (стр. 209–210)
- Косинусное сходство от –1 до 1 (стр. 210); косинусное расстояние = 1 − сходство, от 0 до 2 (стр. 211, 215)
- Эмбеддинги `text-embedding-ada-002`: 1536 измерений; через PCA сжимаются до 3 для картинки (стр. 213–214)
- Файлы-образцы: `document_vector_similarity.py` (scikit-learn), `document_vector_database.py`, `document_visualizing_embeddings.py`, `document_query_chromadb.py` (Chroma DB, запрос `collection.query`)
- TF-IDF прост, но ненадёжен: считает частоты слов и не понимает контекст

Если хочу готовую загрузку и нарезку (LangChain, стр. 216–220) — шаги: 1) загрузить документ (например `UnstructuredHTMLLoader`); 2) разбить `RecursiveCharacterTextSplitter` или `CharacterTextSplitter.from_tiktoken_encoder`; 3) эмбеддинги и сохранение в Chroma; 4) поиск `db.similarity_search`
- Числа примера: чанк 100 символов, нахлёст 25 (стр. 218); по токенам: 50 токенов, нахлёст 10 (стр. 219). Файлы `langchain_load_splitting.py`, `langchain_token_splitting.py`
- Целиком в большую модель (например GPT-4 Turbo) документ подать можно, но дороже и часто хуже; нарезка остаётся лучшей практикой (стр. 216–220)

Если хочу дать агенту знания через Nexus (стр. 220–224) — шаги: 1) `pip install git+https://github.com/cxbxmxcx/Nexus.git` или клон и `pip install -e Nexus` (стр. 220); 2) `nexus run` (стр. 220); 3) страница Knowledge Store Manager: создать хранилище, загрузить документ (пример `back_to_the_future.txt`) (стр. 221); 4) подключить хранилище к агенту на странице чата (стр. 221)
- На момент книги Nexus работает только с одним хранилищем знаний сразу (стр. 221). Настройки нарезки: Chunking Option, Chunk Size, Overlap во вкладке Configuration (стр. 221–223). Большие документы индексируются долго (не из конспекта)

Если хочу память агента (стр. 224–230):
- Виды памяти по аналогии с человеком: сенсорная; кратковременная (контекст диалога); долговременная: декларативная, процедурная, эпизодическая, семантическая (стр. 224)
- Шаги в Nexus: 1) страница Memory, создать хранилище (например `my_memory`) (стр. 226); 2) выбрать движок агента, добавить личные факты и предпочтения (стр. 226); 3) использовать модель с функцией памяти, чтобы вытягивать факты из разговора в JSON (стр. 227); 4) для глубокой категоризации переключить тип на SEMANTIC во вкладке Configuration (стр. 228–229)

## Глава 10. Рассуждение и оценка (стр. 268–295)

Карта приёмов: ось Y — «мышление», ось X — «планирование» (стр. 269). Рассуждение = понимание хода мысли; планирование = порядок действий к цели (стр. 276).

Если хочу запустить примеры потоков — шаги: 1) открыть папку потока в VS Code, окружение, `requirements.txt` (стр. 270); 2) открыть `flow.dag.yaml` в визуальном редакторе (стр. 270); 3) настроить подключение к LLM и блоку эмбеддингов (стр. 271); 4) Play или Shift-F5 (стр. 271)

Прямые приёмы (стр. 269–276):
- Zero-shot (без примеров), One-shot (один), Few-shot (несколько) (стр. 272)
- Вопрос-ответ (`question_answer.jinja2`): отвечать коротко по контексту, а если ответа нет — «Unsure about answer» (стр. 272)
- Few-shot (`few_shot.jinja2`): персона создателя словарей, примеры выдуманных слов «whatpu», «farduddle», вернуть только запрошенное предложение (стр. 270, 274)
- Zero-shot (`zero_shot.jinja2`): классификация neutral/negative/positive без примеров, только результат (стр. 275)

Если хочу, чтобы модель решала по шагам (стр. 276–285):
- Chain of Thought (CoT, цепочка рассуждений): в промпт кладём задачи с подробным пошаговым решением (стр. 279, 280)
- Zero-shot CoT: добавить фразу «Let's think step by step» (стр. 282)
- Prompt Chaining: задача делится на блоки `decompose_steps.jinja2`, `calculate_steps.jinja2`, `calculate_solution.jinja2` (стр. 283–285). Запуск: папки `chain-of-thought-prompting`, `zero-shot-cot-prompting`, `prompt-chaining`, Shift-F5 (стр. 277, 282, 283)
- Минусы: цепочки бывают излишне многословны, а пошаговое рассуждение не гарантирует верный ответ без оценки (стр. 283, 285)

Если хочу надёжность через повторы (self-consistency, самосогласованность; стр. 285–289) — шаги: 1) открыть `self-consistency-prompting/flow.dag.yaml` (стр. 284); 2) Batch Run (стр. 284); 3) файл `statements.jsonl` с одинаковыми задачами для многократных прогонов (стр. 284); 4) Run в созданном YAML (стр. 284); 5) оценка: `self-consistency-evaluation/flow.dag.yaml`, скрипт `consistency.py` считает косинусное расстояние (через `scipy.spatial.distance.cosine`) и выбирает самый стабильный ответ (стр. 287)
- Можно ставить высокую температуру для разнообразия идей, а потом брать самый согласованный результат (стр. 286)

Если задача сложная и точность важнее цены (Tree of Thought, ToT, «дерево мыслей»; стр. 290–294) — шаги: 1) открыть `tree-of-thought-evaluation/flow.dag.yaml` и запускать поиск в ширину (стр. 290–292); 2) блоки парами: один генерирует варианты, второй оценивает (стр. 292); 3) пустой вход (`None` или `""`) — блок сразу прекращает работу (ветка отсечена) (стр. 293); 4) оценка вернула балл, выше порога запускается следующий шаг (стр. 293); 5) пустые финальные ответы значат, что узел или его родитель не прошёл проверку (стр. 294)
- Только поиск в ширину удобен в Prompt Flow из-за графа (DAG); в глубину так просто нельзя (стр. 290)
- Порог: `eval > 25` (стр. 293). Одна задача может потребовать до 27 вызовов LLM, на практике около 12+ (стр. 294)
- Пример кода `semantic_function.py` с `evaluation.invoke_async(query)` и `function.invoke_async(query)` (стр. 292–293)
- ToT не всегда практичен из-за числа вызовов (стр. 294)

Итог главы (стр. 295): Direct, Few-shot, Zero-shot, CoT, Prompt chaining, Self-consistency, ToT. Упражнения: 3 промпта для суммаризации статьи и сравнение; промпты для логических загадок; промпт-предсказание результата опыта и второй промпт-оценка (стр. 294–295).

## Глава 11. Планирование, оценка и обратная связь (стр. 296–322)

Главное: агент без планирования — просто чат-бот; автономный агент берёт цель, сам делит на подзадачи, исполняет и возвращает результат (стр. 296–297, 321).

Если хочу увидеть, как ведёт себя LLM без планировщика (стр. 297–300) — шаги: 1) цель на естественном языке (стр. 297); 2) агент строит план (пример: собрать данные, разметить, визуализировать, отчитаться) (стр. 297); 3) запустить Nexus через Gradio: `nexus run gradio` (стр. 298); 4) создать агента, выбрать движок (OpenAI, Azure, Groq; не LM Studio без поддержки инструментов; Claude для этого теста не брать, у него планирование встроено) (стр. 298); 5) дать точные действия (`search_wikipedia`, `get_wikipedia_page`, `save_file`) и поставить Planner = None (стр. 299); 6) дать составную цель и убедиться: сырая LLM делает первый шаг и спотыкается на зависимых (стр. 299–300)
- Образец цели: `Search Wikipedia for pages on Calgary and download each page and save it to a file called Wikipedia_Calgary.txt` (стр. 299)
- Давать агенту только нужные инструменты: лишние путают, у API есть лимиты (стр. 299, 321)
- Модели из коробки умеют параллельные действия, но не последовательные (зависимые) без планировщика (стр. 300)
- ВАЖНО по безопасности: действия агента имеют реальные последствия. Агент может «выйти из-под контроля»: качать лишние файлы, зациклиться между инструментами, удалить нужные файлы (стр. 299)

Итеративное и последовательное выполнение (стр. 301–303, 345):
- Итеративное (по умолчанию у обычных LLM): шаг, остановка, ждёт «continue» (стр. 302, 345)
- Последовательное/плановое (GPT Assistants, Claude): все шаги внутри агента без остановок (стр. 302, 345)
- Шаги проверки: 1) открыть GPT Assistants Playground (или Claude, где планирование встроено) (стр. 301); 2) ассистенту добавить `search_wikipedia`, `get_wikipedia_page`, `save_file` (стр. 302); 3) отправить ту же цель (стр. 302); 4) ассистент сам пройдёт цепочку и выдаст результат (стр. 302)
- Большинство моделей (включая GPT-4o на момент книги) умеют вызов инструментов, но не последовательное планирование без обёртки или ассистентов (стр. 301)
- Шаг «суммаризировать» можно добавить в цель: отдельного инструмента нет, ассистент использует свои языковые навыки (стр. 302)

Если хочу свой планировщик (стр. 303–309) — шаги: 1) промпт планировщика в JSON с few-shot: правила, `[AVAILABLE FUNCTIONS]`, специальные функции (например цикл `for-each`), `[GOAL]` (стр. 304–305); 2) `create_plan`: загрузить действия агента, подставить цель и функции, отправить в LLM БЕЗ истории чата, чтобы экономить токены (стр. 305–307); 3) `execute_plan` локально: разобрать JSON; на `for-each` выполнять внутреннюю функцию для каждого элемента, результаты класть в `context` (стр. 307); 4) финальный вызов LLM с контекстом для итога пользователю (стр. 306, 308)
- Код: `basic_nexus_planner.py` (стр. 304–307). Форма плана: `{"subtasks": [{"function": "GetJokeTopics"}, {"function": "for-each", "args": {...}}, {"function": "EmailTo", "args": {...}}]}` (стр. 304–307)
- План строить отдельно от истории, потому что промпт планировщика съедает много токенов (стр. 305)
- Локальный планировщик в Nexus обходит встроенную работу LLM с инструментами: всё исполняется в окружении агента (стр. 309)
- Минус: внешнее планирование обходит цикл обратной связи LLM, исправить ошибку на середине труднее (стр. 309)

Если хочу, чтобы модель училась на ошибке (o1-preview, «Strawberry»; стр. 309–312) — шаги: 1) дать сложную логическую задачу (стр. 309); 2) при неверном ответе спросить: `the correct answer is {X}, please review what you did wrong and suggest feedback you could give yourself when trying to solve similar future problems` (стр. 311); 3) взять сгенерированные советы (внимательно читать, рисовать шкалу времени, перепроверять) (стр. 311–312); 4) вставить их в системные инструкции или промпт для похожих задач (стр. 311)
- Пример: задача о путешественнике во времени Алексе: 3 дня до битвы + 3 дня во время + прыжок на 50 лет вперёд на 20 дней и возврат к концу битвы (10 дней). Верно 27 (или 26), o1-preview дала 7 (стр. 309–311)
- Красивая пошаговая цепочка (CoT) создаёт иллюзию правильности: без обратной связи слепо верить рассуждению LLM нельзя (стр. 311)
- Примеры полученных правил: «Visualization: draw a timeline», «Time Continuity» (стр. 311–312)

Если выбираю, где нужны планирование и рассуждение (стр. 312–314, табл. 11.1 и 11.2 на стр. 313–314):
- Личный ассистент: внутри LLM/промпта на устройстве, для вызова инструментов
- Бот поддержки: планирование и рассуждение НЕ используются (ограниченная среда, нет сложных инструментов)
- Автономный агент: в промпте и внутри LLM на сервере, для сложных цепочек
- Совместная работа: внутри LLM в общей среде (например, авто-написание и запуск тестов рядом с программистом)
- Игровой ИИ: в LLM на сервере/в приложении для механик игры
- Исследования: везде, на всех этапах (до, во время и после ответа)
- Глубокое рассуждение замедляет ответ, в чатах, где нужна мгновенность, не применять (стр. 314)

Оценка и обратная связь в системах (стр. 315–319):
- Сейчас чаще это внешние модули относительно агента (стр. 315–319)
- Шаги: 1) внешний мониторинг анализирует ответы после сессии (метрики RAG, точность и т. п.); 2) для автономных агентов — ручная проверка плюс внутренние циклы оценки (как в CrewAI и AutoGen); 3) в чате фиксировать прямой отзыв пользователя и сохранять в долгосрочную память агента; 4) в исследовательских агентах оценку и обратную связь отнести в самый конец, чтобы не зациклиться (feedback looping)
- Оценка ботов поддержки и автономных агентов — после взаимодействия, на сервере (стр. 316); в совместной работе — в реальном времени (стр. 316, 318)
- Мультиагентная оценка во время исследования часто зацикливается и роняет качество на текущих моделях (стр. 319); тяжёлое рассуждение замедляет отклик (стр. 315)
- OpenAI Strawberry (o1) уже встроила рассуждение и планирование в саму LLM (стр. 315, 319)

Упражнения главы 11 (стр. 320–322): 1) (начальный) агент-планировщик (Wikipedia + сохранение в файл); 2) (средний) цикл обратной связи после каждого шага; 3) (средний) параллельное и последовательное выполнение в Nexus; 4) (продвинутый) свой планировщик на промптах в Nexus; 5) (продвинутый) обработка ошибок в последовательном планировании при сбоях API.
- Параллельное выполнение для зависимых шагов неизбежно ломается (стр. 320). Готовые планировщики есть в LangChain, Semantic Kernel, OpenAI Assistants, Claude, Nexus (стр. 321)
