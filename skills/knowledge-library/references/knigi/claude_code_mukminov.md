## О книге коротко

Учебник для разработчиков: как поставить Claude Code, как ставить задачи, как писать с ним код, тесты, документацию, работать с Git, базами данных, MCP и хуками; в конце шесть учебных проектов (SaaS, API маркетплейса, Telegram-бот, CLI на Go, расширение Chrome, перенос старого кода).

## Конспект по главам

### Часть I. Введение и основы

#### Глава 1. Что такое Claude Code и зачем он нужен
- Четыре вида ИИ-помощников для кода: **автодополнители** (Copilot — подсказывают следующую строку), **ИИ-редакторы** (Cursor — правят несколько файлов), **чат-боты** (ChatGPT — код копируешь руками), **агенты** (Claude Code — сам читает файлы, запускает команды, проверяет результат). Агент — программа, которая не только отвечает, но и *действует* в цикле «сделал → посмотрел результат → поправил».
- Философия «напарник, а не автопилот»: человек в цикле принятия решений (**HITL**, human-in-the-loop — «человек в петле»: ИИ делает, человек одобряет важное).
- Ограничения: размер контекста (рабочей памяти) конечен; **галлюцинации** (уверенно выдуманные функции и факты); стоимость; дата среза знаний (не знает свежих библиотек); хуже работает с редкими технологиями. Совет на каждое: проверять тестами, давать документацию, дробить задачи.
- Сравнения с Copilot / Cursor / Q Developer / Gemini Code Assist — рекламные, на 2026 устарели.

#### Глава 2. Установка и настройка окружения
- Установка через npm, Homebrew, Docker; для Windows автор пишет «только через WSL2» — **устарело**, у неё Claude Code работает прямо в Windows.
- Иерархия настроек (кто главнее): флаги командной строки → переменные окружения → настройки проекта `.claude/` → личные `~/.claude/` → по умолчанию.
- CLAUDE.md — постоянные инструкции проекта; может лежать и в подпапках (дополняет, а не заменяет общий).
- Пример `permissions`: `allow` (разрешить без вопросов) и `deny` (запретить всегда) — например запрет записи в `.env`, `rm -rf`, `sudo`, `curl … | bash`.
- Ключи API держать в переменных окружения или менеджере секретов, `.env` — в `.gitignore`.
- Типовые ошибки установки: «command not found» (нет пути в PATH), 401 (неверный ключ), rate limit (слишком много запросов — подождать / дробить), прокси и VPN (переменные `HTTP_PROXY`, `HTTPS_PROXY`).
- Экономия: `/compact`, начинать с Sonnet, конкретные промпты, CLAUDE.md вместо повторов, дробить задачи, смотреть `/cost`. Бюджет «10–50 $ в месяц» — для API-ключа, к её подписке не относится.

#### Глава 3. Первые шаги
- Режимы: интерактивный; разовый `claude -p "…"` (ответил и вышел); продолжение `claude -c` / выбор старой сессии `claude --resume`; **pipe-режим** — подать текст на вход: `cat error.log | claude -p "найди причину"`, `git diff | claude -p "проверь изменения"`.
- Фазы ответа: получил запрос → план → вызовы инструментов → вопрос разрешения на опасное → итог.
- Команды: `/help`, `/clear` (новый лист), `/compact` (сжать, можно с фокусом: `/compact сохрани всё про базу данных`), `/status`, `/cost`, `/model`, `/permissions`, `/config`.
- Контекст: при 70–80 % заполнения — думать о сжатии; при переполнении старые сообщения сжимаются, CLAUDE.md остаётся. «Забыл» — напомнить.
- Умеет смотреть картинки: макет → вёрстка, скриншот ошибки → причина, схема → конфиг.
- Паттерны общения: **«Контекст → Задача → Ограничения»**; «Обзор → Детали → Реализация» (сначала обсудить архитектуру, потом код); **«Покажи перед изменением»** (план без правки файлов); «Исправь и проверь» (после правки — запуск тестов); «Объясни как учителю».
- Одна сессия — одна задача; `/clear` перед совсем новой.

#### Глава 4. Архитектура и принципы работы
- Как понимает проект: метаданные (package.json, README, CLAUDE.md) → структура папок → «ленивое» чтение нужных файлов + поиск grep → смысл кода.
- Инструменты: чтение, запись, **точечная правка** (меняет кусок, а не весь файл — безопаснее), Bash, поиск, веб, MCP. Ценность — в цепочке: запустил тест → прочитал ошибку → нашёл место → поправил → снова запустил.
- Безопасность в 4 слоя: обучение модели, категории инструментов (чтение — без вопросов, запись/команды — с подтверждением), настраиваемые `allow`/`deny`, подтверждение в реальном времени («разрешить один раз / всегда / запретить»).
- Цикл агента: подумать → действовать → посмотреть → повторить; лимит шагов защищает от бесконечных попыток.
- Модели Opus / Sonnet / Haiku и «начинай с Sonnet» — **устарело** (у неё Opus 5.5 каждый день, Haiku — субагентам).
- Кэш промпта: неизменная часть разговора дешевле при повторе. Советы автора «не менять CLAUDE.md часто» верны; «/compact лучше, чем /clear» — спорно (см. «Чего не брать»).
- Расширения: свои слэш-команды (файлы `.md` с `$ARGUMENTS`), хуки, MCP.

#### Глава 5. Эффективное общение с ИИ
- Три уровня промпта: «сделай логин» → структурированный → «экспертный» (что сделать, технические требования, ограничения «не трогай X, не добавляй зависимостей, следуй стилю файла Y»). Длинный точный промпт экономит переделки.
- Принципы: конкретность (не «красивый дизайн», а цвета hex, радиусы, шрифты), только нужный контекст, разбивка на этапы, **примеры ожидаемого результата** (вход → выход), роль.
- Шаблоны промптов по типам: генерация кода (вход, выход, граничные случаи, ошибки), **отладка** (ошибка, файл, как воспроизвести, ожидалось, получилось, что уже пробовали), рефакторинг (цели, что менять нельзя), ревью (фокус, формат ответа с уровнями серьёзности), документация.
- Структура CLAUDE.md: описание, стек, архитектура, команды, соглашения, важные решения, **«Чего НЕ делать»**.
- Антипаттерны: рыхлый промпт; микроменеджмент («открой строку 42»); «прочитай весь проект»; слепое доверие; **20 попыток «не работает, исправь»** (надо остановиться и сменить подход); прыжки между темами в одном сообщении.
- Итерации: «Да, но…», от простого к сложному, **«Критик»** (попросить проверить свой же код), «Сравни два способа».
- Большие проекты: «фокусная линза» (работаем только с этими папками), «проводник» (объясни путь запроса), «карта зависимостей».
- Имена в коде — по-английски, комментарии можно по-русски.

### Часть II. Практическое использование

#### Глава 6. Написание кода с нуля
- Методика 5 шагов: описание словами → архитектура до кода → «скелет» проекта → функции по одной → запуск и проверка.
- Паттерны: «слой за слоем», «сначала тесты» (TDD — пишем проверки, потом код, который их проходит), **«скопируй стиль»** (сделай модуль как уже существующий), «прототип → боевой вариант».
- Частые ошибки генерации и лекарства: устаревшие API (указывать версии), лишний код («минимальная реализация, ничего сверх просьбы»), дрейф стиля (CLAUDE.md), **забытые граничные случаи** (перечислять явно: пустой ввод, очень длинная строка, эмодзи, параллельные запросы, обрыв связи с базой).

#### Глава 7. Рефакторинг (улучшение кода без изменения поведения)
- Сначала понять чужой код: обзор проекта, разбор модуля, поиск «скелетов» (TODO, закомментированный код, магические числа, файлы без тестов).
- «Запахи кода» (признаки будущих проблем): класс-«бог» на 800 строк, длинная функция, правка одной фичи в 5 местах.
- Модернизация старого кода, ускорение (запросы к базе, кэш, параллельность), единая обработка ошибок.
- **«Рефакторинг как переезд»**: выносить кусками, после каждого шага приложение остаётся рабочим; сначала план без кода.

#### Глава 8. Отладка
- Цикл: описание → гипотеза → проверка → исправление корня.
- Разбор трассировок ошибок (stack trace — список «кто кого вызвал» до места падения).
- Типовые баги на примерах: **двойное списание** (нет проверки «уже оплачено?» — лечится идемпотентностью: повтор операции не меняет результат), «проверил, потом списал» при параллельных запросах (гонка — лечится одной атомарной операцией), забытый `await`, утечки памяти, `localhost` внутри Docker, общий кэш без привязки к пользователю, `NaN` из пустой строки.
- Стратегии: поиск коммита-виновника (`git bisect`), «резиновая уточка» (подробно описать проблему), сначала тест, который воспроизводит ошибку.
- **Скрипт диагностики**: собрать версии, состояние зависимостей, результат тестов, последние ошибки логов — в одном выводе, удобном для разбора.
- После каждого найденного бага — **регрессионный тест** (проверка, что этот баг не вернётся).

#### Глава 9. Тесты
- Пирамида: unit (одна функция), интеграционные (несколько частей вместе), E2E (весь путь как пользователь).
- Тесты с заглушками (моками — подменами внешних сервисов), параметризованные (одна проверка на таблице входов), Playwright для браузера, TDD, покрытие кода, mutation testing (проверка, что тесты ловят специально внесённые ошибки), фабрики тестовых данных.

#### Глава 10. Базы данных
- Проектирование схем (нормализация, индексы, «мягкое удаление» — пометка вместо удаления), ORM, ускорение запросов (убрать N+1 — когда на каждую строку делается отдельный запрос), миграции с откатом, перенос данных с журналом ошибок (`failed_migrations` — плохие строки откладываются для ручного разбора, а не теряются), Redis-кэш, безопасность (параметризованные запросы против SQL-инъекций).

#### Глава 11. Документация
- Хорошая документация объясняет **почему**, а не «что» (комментарий «увеличиваем счётчик» бесполезен; «скидка 15 % VIP — решение коммерческого директора от 15.01» полезен).
- README, OpenAPI, ADR (запись архитектурного решения: контекст → решение → последствия), CHANGELOG из истории Git, Mermaid-диаграммы (схемы текстом), проверка, что документация не устарела.

#### Глава 12. Git и совместная работа
- Коммиты по смыслу (conventional commits: `feat`, `fix`…), разбивка смешанных правок на отдельные коммиты, разрешение конфликтов с объяснением каждого решения, описание PR (что сделано, как проверить, чек-лист), чистка истории, git-хуки (Husky).
- Случайно закоммиченный ключ: вычистить историю **и обязательно отозвать ключ**.
- Правила для команды: код от ИИ проходит то же ревью; не больше ~200 строк изменений за раз.

### Часть III. Продвинутые возможности

#### Глава 13. MCP (Model Context Protocol)
- MCP — стандарт подключения внешних сервисов: сервер даёт инструменты (действия), ресурсы (данные), промпты (готовые сценарии).
- Примеры: PostgreSQL, GitHub, Slack, Sentry, Puppeteer (браузер); как написать свой MCP-сервер на TypeScript.
- Безопасность: минимальные права (например, пользователь базы **только на чтение**), токены в переменных окружения, журнал вызовов, разрушительные операции по умолчанию закрыты.
- Формат настройки (в `settings.json`, транспорт SSE) и имена пакетов — **устарели** (сейчас `claude mcp add`, файл `.mcp.json`, транспорт Streamable HTTP).

#### Глава 14. Автоматизация
- Свои команды в `.claude/commands/` и `~/.claude/commands/` с `$ARGUMENTS` (примеры: «утренний ритуал», «проверка готовности к выкладке» с [+]/[-] по пунктам).
- Хуки: `PreToolUse` (до действия — можно проверить и запретить), `PostToolUse` (после — например, автоформатирование), **`Notification`** (уведомление на рабочий стол, когда Claude ждёт ответа или закончил).
- Headless (без окна): `claude -p "…" --output-format json --max-turns 10`; встраивание в скрипты, CI (автоматическая проверка в GitHub Actions).
- Пример «скрипт обновления зависимостей»: обновить → тесты → прошли — коммит, не прошли — откат и запись в журнал.
- Пример кода SDK и часть флагов — **устарели/выдуманы** (сейчас Claude Agent SDK).

#### Глава 15. DevOps
- Dockerfile (многоэтапная сборка, непривилегированный пользователь, проверка здоровья), docker-compose, Kubernetes, Terraform, CI/CD, мониторинг, логи в JSON, health-check (адрес «жив ли сервис»), Nginx, скрипты выкладки и бэкапов (с проверкой восстановления из бэкапа). К нашим делам почти не относится.

#### Глава 16. Безопасность
- Не вставлять реальные секреты в чат (описывать «пароль скрыт»).
- Аудит: инъекции (SQL, команд), XSS (вредный скрипт через пользовательский ввод), слабая авторизация, секреты в коде, режим отладки на боевом сервере, CORS «всем можно», уязвимые зависимости.
- Защита API и форм: ограничение частоты запросов (rate limiting: например, 5 попыток входа в минуту с одного IP), проверка ввода, заголовки безопасности (HSTS, CSP, X-Frame-Options), CSRF/CORS, шифрование персональных данных.
- **Чек-лист перед запуском**: секреты в переменных окружения, отладка выключена, только HTTPS, заголовки безопасности, ограничение частоты, проверка ввода, ошибки не показывают внутренности, журнал событий безопасности, бэкап настроен и проверен.

#### Глава 17. Разные языки
- Python (pandas-отчёты, FastAPI, асинхронный сборщик с `Semaphore` — ограничитель числа одновременных запросов, повтор с растущей паузой, 2 запроса/с на сайт), Go, Rust, TypeScript, C#; перевод кода между языками «идиоматично, а не дословно».

#### Глава 18. Предметные области
- Мобильные приложения, анализ данных (**когортный анализ** — как возвращаются покупатели, пришедшие в один месяц; **RFM-сегментация** — делить покупателей по давности покупки, частоте и сумме), ML-прогноз оттока, real-time, блокчейн, IoT, игры, NLP, скоринг. Для нас — только когортный/RFM-анализ, когда появятся продажи.

### Часть IV. Реальные проекты

#### Глава 19. SaaS с нуля
- Стек «по обоснованию», схема данных, авторизация, канбан, real-time, выкладка. Уроки: план перед кодом, одна фича за раз, тесты на каждом шаге, ревью каждого файла.

#### Глава 20. API маркетплейса
- Корзина с граничными случаями (**товар закончился между добавлением и оплатой; цена изменилась после добавления**; магазин отключён), статусы заказа, окно возврата 14 дней, комиссия платформы, поиск с фильтрами, кэш каталога с TTL (временем жизни).

#### Глава 21. Telegram-бот на Python
- aiogram 3, быстрый ввод «500 кофе» с автокатегорией, бюджеты с предупреждением на 80 %, графики, выкладка: webhook или polling (два способа получать сообщения), **корректная остановка** (graceful shutdown — бот доделывает начатое перед выходом), health-check, автозапуск после перезагрузки.

#### Глава 22. CLI на Go
- Утилита с командами `init / env / health / deploy`. Полезная идея: `env diff` — **сравнить два `.env` по именам ключей, не показывая значения**; `env validate` — пустые обязательные ключи, дубли.

#### Глава 23. Расширение Chrome
- Manifest V3, popup, боковая панель, контекстное меню, хранение (sync 100 КБ, local 5 МБ), экспорт в Gist.

#### Глава 24. Перенос старого кода
- Фаза 1 — исследование (что есть, риски). Фаза 2 — **характеристические тесты**: прогнать старую систему на типовых данных и записать ответы как эталон «как работает сейчас». Фаза 3 — перенос данных с проверкой (число записей совпадает + выборочная сверка). Фаза 4 — **«удушающее дерево»** (strangler fig): новая система забирает функции по одной, старая работает, пока не перенесено всё. Фаза 5 — проверка.
- Уроки: без тестов не переносить; поэтапно, а не «всё сразу»; данные отдельно от кода; **не улучшать во время переноса** (сначала перенести как есть, потом улучшать); всегда план отката.

### Часть V. Лучшие практики и будущее

#### Глава 25. Лучшие практики
- Пять правил: контекст (что, где, зачем); CLAUDE.md как главный актив (с разделом «Определение готово»); маленькие шаги; всегда проверять; улучшать итерациями.
- Антипаттерны: «сделай всё», слепое доверие, «промпты вместо своих знаний» (0 × 10 = 0), «контекстная амнезия» (100+ сообщений без сжатия).
- Режимы общения: «Архитектор — не пиши код», «Наставник», «Напарник — сохрани мою структуру», «Ревьюер — без стилистических правок».

#### Глава 26. Ограничения и подводные камни
- Признаки переполненного контекста: перестал следовать правилам начала, повторяет исправленные ошибки, забыл решения.
- Как узнать галлюцинацию: функция, которой нет в документации; пакет, которого нет в npm/PyPI; «слишком удобный» синтаксис. Лекарство — запуск, тесты, официальная документация, вопрос «ты уверен, что это существует?».
- Чего не делать: вставлять реальные секреты, автоматизировать разрушительные операции (`DROP TABLE`, `rm -rf`, force push).
- Где Claude Code не лучший выбор: пиксельный дизайн, сетевые проблемы, профилирование, бизнес-решения, финальная проверка безопасности.

#### Глава 27. Будущее
- От ассистента к агенту, мультимодальность, долгая память — к 10.2026 частично уже наступило (память, фон, облако, браузер). Ценные навыки: формулировать требования, ревью ИИ-кода, проверка, безопасность, знание предметной области.

#### Приложения А–В
- Шпаргалка команд (часть устарела: `/project:…`, `--dangerouslySkipPermissions`), шаблоны CLAUDE.md для бэкенда/фронтенда/Python/монорепозитория, словарь терминов.

## Что применяем у нас

Только то, чего нет в `claude-code-priemy` и глобальном CLAUDE.md. Формат: что сделать — зачем — когда.

1. **Шаблон «сообщение об ошибке скрипта»** → `claude-code-priemy`
   Что: когда ломается сборщик (tg_monitor, радар, 1688, бот «Дела»), писать задачу по шести строкам: *Ошибка (текст как есть) · Файл/скрипт · Как повторить · Что ожидалось · Что получилось · Что уже пробовали*.
   Зачем: Claude не гадает и не повторяет уже проверенное; меньше ходов — дешевле.
   Когда: в начале любого «не работает» со скриптом.

2. **Снимок поведения перед переделкой работающего скрипта** (характеристический тест) → `claude-code-priemy`, `knowledge-library`
   Что: перед тем как переписывать/ускорять рабочий сборщик — прогнать его на фиксированном входе (например, 3 сохранённые страницы или 1 файл xlsx) и сохранить выход как эталон; после переделки сравнить «совпало N из M строк». Правило из книги: **сначала перенести как есть, улучшать — отдельным шагом**.
   Зачем: переделка «заодно» ломает то, что работало, и это видно только через неделю.
   Когда: асинхронность в сборщике, переезд скрипта в новую папку/проект, смена библиотеки.

3. **Граничные случаи сборщика — явным списком в задаче** → `claude-code-priemy`, `sourcing-1688`, `trend-radar`
   Что: в ТЗ на новый сборщик перечислять: пустая страница / 0 товаров; капча или антибот; обрыв VPN (Happ) посреди сбора; иероглифы и эмодзи в названии; цена диапазоном «35–70»; повторный запуск после падения (продолжить, а не начать заново).
   Зачем: ИИ по умолчанию пишет «счастливый путь», а наши сайты как раз ломаются на краях.
   Когда: каждый новый сборщик или большая правка старого.

4. **Повтор без вреда (идемпотентность) для записей наружу** → `shopify-admin`, `dela`
   Что: в скриптах, которые пишут в Shopify (цены, остатки, описания) или отправляют сообщения ботом, перед записью проверять «уже сделано?» (то же значение уже стоит; это голосовое уже получило ответ) и пропускать. Повторный запуск скрипта не должен дублировать действие.
   Зачем: книга разбирает «двойное списание»; у нас тот же риск — двойная отправка итога в бот/чат дела, повторное изменение цены.
   Когда: при написании любого скрипта, который меняет что-то вне ПК.

5. **Простой «замок» через `permissions.deny` вместо хука** → `claude-code-priemy` (ставить только по её слову, через `update-config`)
   Что: в `~/.claude/settings.json` правилом `deny` запретить чтение/запись `.env` и папки «Ключи», `rm -rf`, `curl … | bash`. Это проще хука: одна строка, без скрипта. Точный синтаксис правил сверить с документацией code.claude.com/docs/en/permissions перед вставкой (в книге он мог устареть).
   Зачем: критичное — замком, а не текстом (правило уже есть в скилле, это самый дешёвый способ его выполнить).
   Когда: при «уборке инструкций» или первой же настройке хуков.

6. **Хук `Notification` — всплывающее окно Windows** → `claude-code-priemy` (её решение)
   Что: хук, который показывает уведомление Windows, когда Claude закончил долгую задачу или ждёт её ответа (разрешение, вопрос).
   Зачем: долгие сборы и «новости» идут по 10–30 минут — не надо сидеть у экрана.
   Когда: если она скажет «хочу знать, когда закончил».

7. **Скрипт-диагностика для сборщиков** → `claude-code-priemy`, `knowledge-library`
   Что: один `diagnose.py` на проект: версия Python и библиотек, есть ли нужные ключи в `.env` (**только имена, без значений**), открывается ли целевой сайт (и через Happ, и напрямую), последние 20 строк ошибок из лога. Вывод — одним блоком.
   Зачем: при поломке сразу видно «сайт не открывается / ключа нет / библиотека обновилась», без долгого расследования. Совпадает с правилом данных: значения ключей наружу не уходят.
   Когда: при следующей поломке любого сборщика — сделать один раз и переиспользовать.

8. **Сравнение `.env` по именам ключей** → `claude-code-priemy`
   Что: если ключи в разных проектах (радар, lead-engine, бот) разъехались — сравнивать только списки имён (`TREG_API_KEY` есть / нет), не выводя значения.
   Зачем: найти, где не хватает ключа, не засветив сам ключ в чате.
   Когда: при переносе ключа между проектами или «скрипт вдруг не видит ключ».

9. **Чек-лист безопасности формы заявки и сайта Frivent** → `site-design`, `b2b-sbor`
   Что: перед запуском лендинга frivent.ru проверить: только HTTPS; форма заявки — ограничение частоты отправки и защита от спама; проверка полей (телефон/почта) на сервере; ошибки не показывают внутренности; ключи — в переменных окружения; заголовки безопасности (HSTS, CSP, X-Frame-Options); заявки сохраняются + бэкап.
   Зачем: B2B-формы первыми получают спам-ботов; потерянная заявка = потерянный клиент.
   Когда: перед публикацией лендинга и после каждой правки формы.

10. **Перенос сайта «по кускам» (удушающее дерево)** → `site-design`
    Что: если старый сайт Frivent заменяется новым — переносить страницами/разделами, старое работает до конца, каждый перенесённый раздел проверяется (ссылки, формы, заявки дошли), только потом старое удаляется. Перед переносом — план отката.
    Зачем: не остаться на день без сайта и заявок.
    Когда: если дойдёт до замены существующего frivent.ru.

11. **Когортный анализ и RFM, когда появятся продажи** → `dropship-lessons`, `knowledge-library`
    Что: через 2–3 месяца продаж — разбить покупательниц по месяцу первой покупки (сколько вернулись) и по RFM (давность / частота / сумма), чтобы понять, кому слать письма и скидки.
    Зачем: повторные покупки дешевле новых; без этого реклама считается «в лоб».
    Когда: после первых ~100 заказов в магазине (не раньше — мало данных).

12. **Бот «Дела»: корректная остановка и проверка живости** → `dela`
    Что: при правке бота — обработчик остановки (доделать начатую загрузку на Drive перед выходом) и простая проверка «бот жив» (последнее время обработки сообщения в файле).
    Зачем: в памяти уже были случаи «бот перезапущен» — так видно, что он лёг, и ничего не теряется на перезапуске.
    Когда: при следующей правке бота.

13. **Логи в Claude через конвейер** → `claude-code-priemy`
    Что: длинный лог не вставлять в чат, а подать на вход разовому запуску: `Get-Content tg_monitor.log -Tail 200 | claude -p "найди причину падения, кратко"`. В `-p` нет скиллов и CLAUDE.md — правила передавать в самом промпте.
    Зачем: лог не засоряет основную сессию и её кэш.
    Когда: разбор больших логов сборщиков.

## Чего НЕ брать (устарело к 10.2026 или не подходит)

- **Модели и цены:** `claude-sonnet-4-20250514`, Opus 4, «Sonnet — модель по умолчанию, начинайте с Sonnet», «контекст 200K у всех моделей», «10–50 $ в месяц» — устарело; у неё Opus 5.5 на подписке, цены и окна смотреть в `/usage`, `/context`, скилле `claude-api`.
- **«Windows только через WSL2»** — устарело, Claude Code работает в Windows напрямую.
- **Формат хуков из главы 4** (`"preToolUse": [{"tool": …, "command": …}]`) и переменные `$FILE_PATH`, `$TOOL_INPUT` в командах — не тот формат; сейчас хук получает JSON на вход, имена инструментов `Write`/`Edit`, а не `WriteFile`. Брать идеи хуков, не код.
- **Ключи настроек** `defaultModel`, `autoApprove`, `theme`, `maxTurns` в settings.json, переменные `CLAUDE_MODEL`, `CLAUDE_CODE_MAX_TURNS` — не подтверждены документацией; не вставлять, не проверив.
- **Команды `/project:review`, `/user:standup`** — старая схема имён; у неё свои скиллы и `/команда` без префикса.
- **MCP через `mcpServers` в settings.json и транспорт SSE**, пакеты `@anthropic/mcp-server-puppeteer` и т. п. — устарело; сейчас `claude mcp add`, `.mcp.json`, Streamable HTTP. Для браузера у нас Claude in Chrome / Dolphin.
- **«Claude Code SDK» `import { Claude } from '@anthropic-ai/claude-code'`** — такого API нет; сейчас Claude Agent SDK.
- **`--dangerouslySkipPermissions`** (ещё и с ошибкой в написании) — не использовать вообще: отключает все вопросы (то же, за что отвергнуты Auto-Company и setup.sh из «40+ советов»).
- **«Подумай внимательно» включает расширенное размышление**, Chain-of-Thought «думай пошагово» — противоречит её CLAUDE.md; глубина задаётся `/effort`.
- **«Выступи как старший DevOps-инженер» (роль в промпте)** — у нас отказ от «ты эксперт по …» (скилл, раздел «Бриф субагенту»).
- **Negative prompting «НЕ используй …» как основной приём** — противоречит writing-for-agents («говорить, что делать»); запрет — только в паре с правильным действием.
- **«Предпочитайте /compact вместо /clear», «/compact после каждого блока»** — у нас решено иначе: `/clear` между разными задачами, `/compact` — перед перерывом; кэш на подписке живёт час.
- **«Нет памяти между сессиями», «нет фонового выполнения», «не может кликать в браузере»** — устарело: у неё автопамять, `Ctrl+B`, облачные сессии, Claude in Chrome.
- **«Claude Code сам маскирует секреты перед отправкой»** — непроверенное утверждение; не полагаться, следовать правилу данных 🟢/🟡/🔴.
- **Cron-автоматизация (глава 14)** — противоречит правилу «без автозапуска» (trend-radar).
- **Учебные проекты (Next.js 14, Prisma, Kubernetes, Terraform, Go CLI, расширение Chrome)** — не наш стек и не наши задачи; версии библиотек тоже устарели.
- **Сравнения с Copilot/Cursor/Gemini** — рекламные и устаревшие, решений не меняют.
