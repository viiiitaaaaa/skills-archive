# Промпты, скиллы и агенты — что поменялось к сентябрю 2026 и что это значит для нас

Собрано 29.09.2026 из 8 материалов. Для каждого: 3–7 выводов простыми словами, потом «Что применить у нас»
(конкретные скиллы из `C:\Users\User\.claude\skills\` и конкретные правки — сами скиллы здесь НЕ правились).
В конце — чек-лист «Ревизия скилла» и шаблон тестовых примеров.

Словарик (встречается ниже часто):
- **Промпт** — текст-инструкция для модели. **Скилл** — папка с `SKILL.md`: инструкция, которую Claude подгружает сам, когда задача похожа на описание скилла.
- **description (описание скилла)** — 1–3 строки в шапке `SKILL.md`. Только по ним Claude решает, открывать скилл или нет. Остальной текст он видит лишь после открытия.
- **Токены** — «кусочки текста», за которые платим. Чем длиннее инструкции и прочитанные файлы, тем дороже каждый шаг.
- **Effort (уровень усилий)** — сколько модель «думает» перед ответом: low / medium / high / xhigh / max. Выше — умнее, но дольше и дороже.
- **Субагент** — помощник, которого основная модель запускает на отдельную подзадачу; он работает в своём «блокноте» и возвращает только итог.
- **Eval (эвал, проверка)** — набор тестовых запросов с критериями «правильно / неправильно», чтобы измерять, помогает ли скилл.
- **Костыль** — старая инструкция, написанная под слабую модель («проверь дважды», «думай шаг за шагом», «ОБЯЗАТЕЛЬНО!!!»). Новым моделям мешает.

## 1. Anthropic: гайд по промптам для Claude Fable 5.1 + статья «чистка костылей»

Источники:
- Официальный гайд Fable 5.1: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1 (прочитан целиком)
- Гайд Fable 5 (на нём стоит 5.1): https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5
- Статья про экономию: https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform
  Цифру «−46 % цены за +0,5 пункта» на официальной странице нашла дословно («the last step up to max adds about half a point for 46% more cost»).
  Цифры **−14,6 % стоимости и +5,3 % точности** в тексте официальной страницы при чтении не нашла (возможно, они на графике);
  их со ссылкой на эту статью приводит пересказ: https://www.zeniteq.com/anthropic-shares-how-to-reduce-cost-and-improve-performance-with-claude-5uu91d

Выводы:
1. **Старые скиллы вредят новым моделям.** Прямо сказано: скиллы, написанные под прежние модели, «часто слишком предписывающие» и могут ухудшать результат. Совет — пересмотреть и убрать старые инструкции, если без них лучше.
2. **Шесть костылей, которые Anthropic вычищала** (эксперимент на промптах поддержки клиентов): «проверь дважды»; «будь максимально тщательным», «КРИТИЧНО: ТЫ ОБЯЗАН…»; жёсткие процедуры «шаг 1…шаг 6» и «думай шаг за шагом в черновике»; старые примеры, подогнанные под ошибки старой модели; противоречащие друг другу правила; устаревшие настройки. После чистки (команда `/claude-api prompt-audit`) — дешевле и точнее.
3. **Effort — главный рычаг цены.** Начинать с `high`, остальные уровни проверять на своих примерах. `max` почти не добавляет качества (+0,5 пункта за +46 % цены). Сильная модель на низком effort бывает дешевле слабой на высоком.
4. **Коротко работает лучше длинного.** Fable 5.1 так хорошо слушается, что одна фраза заменяет список из десяти запретов. Пример из гайда: «Please remove all mannered prose» (убери вычурные обороты).
5. **Модель должна знать «зачем».** Шаблон: «Я делаю [большую задачу] для [кого]. Им нужно [что даст результат]. Поэтому: [просьба]».
6. **Отчёт — только по доказательствам.** Фраза из гайда почти убрала выдуманные «всё готово»: перед отчётом сверить каждое утверждение с результатом инструмента из этой сессии; не проверено — так и сказать.
7. **Границы и «доделай до конца».** Модель может спрашивать разрешение на то, что уже поручено, или обещать «дальше я сделаю…» и останавливаться. Лекарство — сказать: обратимые действия делай сам, останавливайся только перед необратимым, сменой объёма работ или когда нужен ответ человека. И обратное: если человек просто спрашивает или рассуждает — дай оценку и не чини без просьбы. Ещё Fable 5.1 любит переписывать файл целиком вместо точечной правки и добавлять «лишние улучшения» — на оба случая в гайде есть готовые фразы.
   Важно для Fable 5: просьбы «пересказать свои рассуждения в ответе» могут вызвать отказ модели (`reasoning_extraction`) — такие строки из скиллов убрать.

Что применить у нас:
- **Все скиллы:** прогнать по чек-листу в конце файла. Кандидаты на удаление — «проверь дважды», «очень важно», повторы одного правила в трёх местах. Настоящие запреты (aliexpress.ru, профиль Dolphin 859648353, Taobao без автосбора, CJ — нет) оставить, но одной спокойной строкой с причиной.
- **tg-news:** в SKILL.md её просьба 29.09 «подумай, по какой логике я отбирала…» — это цитата, её оставить как контекст, но само правило отбора записать утвердительно («отбираю так: …»), без «подумай». Добавить фразу про отчёт по доказательствам: «панель обновлена» писать только после проверки времени изменения файла панели.
- **shopify-admin:** добавить блок границ: сами делаем обратимое (названия, теги, описания черновиков); спрашиваем перед удалением товаров/коллекций, массовой сменой цен, публикацией темы. Добавить: «не переписывать шаблон/файл темы целиком ради одной строки».
- **sourcing-1688, trend-radar:** первым абзацем — «зачем»: «отбираем вещи для магазина одежды в США, её вкус — тренд + изюминка; итог — строки в таблице `cj\…xlsx`». Длинные разделы «грабли» и истории дат перенести в `references/` (они нужны не при каждом запуске).
- **dela:** оставить строгие правила (документы в суд — необратимое, отправку подтверждает она). Добавить из гайда Fable 5.1: цитаты из закона и судебных актов помечать кавычками и ссылкой, пересказ — своими словами.
- **Effort:** по умолчанию `high` (уже так). Для механики — `cut-products`, `dsers-import`, `product-links`, раскладка файлов в `disk-hygiene` — можно `/effort medium`. `max` не включать ради «на всякий случай».

## 2. OpenAI: «Rethinking skills and prompts for GPT-6 Astra»

Источник: https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra (открылся)

Выводы:
1. **Новым моделям не нужны «маршруты по шагам».** Подробные рецепты «сделай 1, потом 2, потом 3» для умной модели — лишний текст, он тратит место и тормозит.
2. **Слишком широкое описание скилла мешает выбору.** Когда описаний много и они длинные, система их укорачивает — модель видит меньше и хуже выбирает скилл. Пример из статьи: плохо — «Используй при работе с базами, запросами, моделями»; хорошо — «Используй при добавлении или изменении миграции».
3. **Лишние предостережения останавливают работу.** Жёсткие запреты, написанные для ненадёжных моделей, теперь заставляют модель зря тормозить.
4. **Не надо заставлять проверять всё.** Новые модели сами запускают проверки; старая фраза «обязательно прогони тесты» ведёт к лишним прогонам.
5. **«Прочитай все документы перед любой правкой» — плохо.** Хорошо — привязать документ к ситуации: «про границы сервисов — смотри architecture.md».
6. **Оставить:** явные разрешения («локальные тесты запускай без вопросов») и чёткий критерий «когда задача закончена». Совет — попросить саму модель провести аудит инструкций.

Что применить у нас:
- **Описания всех 23 скиллов** сократить до 300–500 символов: что делает + 1–2 конкретные ситуации «когда» + 5–8 слов-триггеров. Начать с тех 10, что показались без описания (список выше), и с самых длинных: `sourcing-1688`, `knowledge-library`, `dropship-lessons`, `trend-radar`, `dela`.
- **Не пересекать описания:** `shopify-admin` / `shopify-collections` / `style-collections` все говорят про «коллекции». В каждом описании прямо разделить: style-collections — «какой товар в какой стиль» (решение), shopify-collections — «завести коллекции в магазине» (действие), shopify-admin — «прочие правки магазина».
- **Правило «читать X перед Y» привязать к ситуации:** в `sourcing-1688` и `trend-radar` вместо «сначала прочитай все файлы» — «про юнит-экономику смотри …, только когда считаем цену».
- **Разрешения прописать явно** (у нас уже есть память «браузер разрешён целиком»): в `dolphin-shots`, `tg-news`, `sourcing-1688` — «открывать/закрывать вкладки и профиль без вопросов».

## 3. Google: как делать красивые интерфейсы с ИИ (типографика → компоненты)

Источник: «How to design better looking apps with Google AI Studio» — https://aistudio.google.com/learn/ai-ui-design-google-ai-studio

Ниже — только то, что видно из выдержек поисковика по этой странице и соседних материалов, без домыслов.

Выводы (по выдержкам):
1. В запросе на дизайн называть конкретно: палитру (с HEX-кодами), иерархию шрифтов (размеры и насыщенность заголовков и текста), обработку карточек (рамки, скругления), плотность отступов и общее настроение (например, «редакционный минимализм»).
2. Идти слоями: сначала дизайн-система, потом отдельно шрифты, раскладка, компоненты, мелкие анимации — а не всё одним промптом.
3. Для компонентов указывать состояния: наведение (hover), нажатие (active), неактивно (disabled).
4. Самый быстрый путь к цельному виду — приложить 1–несколько скриншотов-образцов; модель может сама вытащить из скриншота «язык дизайна» и вернуть его как промпт.
5. Слабое место ИИ-интерфейсов — именно типографика (шрифты); без указаний выходит «шаблонный ИИ-вид».

Что применить у нас:
- **site-mockups:** в рецепте генерации экранов держать порядок слоёв: 1) шрифты (пара заголовок/текст, размеры для H1/H2/текста/цены), 2) оболочка без цвета (уже есть), 3) токены коллекций (уже есть), 4) компоненты с состояниями — кнопка «В корзину» обычная/наведение/неактивна (нет размера), бейдж Sold out, выбор размера. Добавить в SKILL.md одну строку-шаблон с этими полями.
- **site-mockups + Inspo MCP:** перед новым экраном — 3–5 образцов через `inspo` (уже подключён), из них вытащить «язык дизайна» текстом и вставить в промпт.
- **shopify-admin** (вёрстка главной/футера): те же правила шрифтов, чтобы тема не разошлась с подложкой.

## 4. Курсы CMU 11-768 «AI Agents» и Stanford CS329Z «Engineering AI Agents»

Источники:
- Stanford CS329Z: https://cs329z.stanford.edu/ (расписание прочитано)
- CMU 11-768: https://www.cmu-agents.com/ — официальная страница не отдала текст (только заголовок). Программа ниже — по подробному пересказу: https://www.heyuan110.com/posts/ai/2026-09-08-cmu-11-768-ai-agents-course/
- «Don't Sleep on Single-agent Systems» (доп. чтение CS329Z), блог OpenHands, 26.09.2024: https://www.all-hands.dev/blog/dont-sleep-on-single-agent-systems (найдено, сам текст не открывала); близкая научная работа: https://arxiv.org/abs/2505.18286 — по её аннотации, выигрыш многоагентных систем над одноагентными уменьшается по мере роста силы моделей.

Выводы:
1. **Три инженерные задачи любого агента (CS329Z, неделя 1): разбиение задачи на части, данные, оценка качества.** Всё остальное — детали.
2. **Тест = 4 части (CS329Z, неделя 7):** запрос, окружение (какие файлы/доступы есть), когда остановиться, как оценить. Без любой из четырёх тест «плавает».
3. **LLM-as-judge (модель-судья):** вторая модель ставит «годится / не годится» по правилам. Бывает попарная (какой из двух ответов лучше) и поточечная (этот ответ проходит или нет). Правила для судьи писать как конкретные «PASS если… / FAIL если…».
4. **pass@k против pass^k.** pass@k — «хотя бы один из k запусков удачный» (годится, когда человек выбирает лучший вариант из нескольких). pass^k — «все k запусков удачные» (нужно, когда ошибка дорогая и результат идёт без просмотра). Модель непостоянна: 1 удачный запуск ничего не доказывает.
5. **Не торопиться с многоагентными схемами.** Один агент с хорошими инструментами часто лучше «команды агентов», особенно на сильных моделях.
6. **Навыки подгружаются по требованию (CMU, лекция 4):** в системном промпте только имена и описания, полный текст — когда нужен. Это ровно устройство скиллов Claude Code — поэтому описание так важно (см. материал 2).
7. **Сжатие истории разговора** — обычная часть агента; при сжатии важно явно сохранять решения, ограничения, точные цифры и названия.

Что применить у нас:
- **dela** — меряем по pass^k (документ в суд должен быть правильным каждый раз): реквизиты через `scripts/check_rekvizity.py`, суммы и даты — сверка с исходником.
- **love-scripts, product-scenes, room-scenes, artlist-product-ads** — меряем по pass@k: она всё равно выбирает из 2–3 вариантов, достаточно, чтобы хоть один был хорош.
- **trend-radar / sourcing-1688** — вердикт «брать / наблюдать / отказ» по одному и тому же товару должен совпадать в 3 запусках из 3 (pass^3). Если «плавает» — правило отбора записано неясно.
- **Не делить скиллы на «команды агентов».** tg-news, trend-radar, sourcing-1688 — оставить одним агентом; субагентов звать только на чтение больших файлов (см. материал 8).
- Для каждого скилла записать тесты по форме «запрос / что есть в окружении / когда стоп / как проверить» — шаблон в конце файла.

1. Демо ACME — агент-консультант магазина: понимает сложный запрос («палатка, спальник и плитка для похода с двумя детьми»), собирает набор из каталога, сравнивает товары прямо в чате, показывает корзину, отвечает про заказ, возврат и правила магазина.

3. Оплата остаётся в обычной системе магазина; агент подключается к каталогу, корзине, оформлению, истории заказов и предпочтениям покупателя.
4. Заявленные результаты у ритейлеров: корзины до +35 %, покупатели на 60 % чаще доходят до оплаты (цифры компании, не независимые).
5. Шаблон по статье поднимается локально «меньше чем за час»; есть варианты на Messages API, Agent SDK и Managed Agents.

Что применить у нас (на потом — консультант по размерам и образам):
- **Сначала данные, потом агент.** Консультант по размеру бесполезен без таблиц размеров. Сейчас: при заведении товара в `shopify-admin` сохранять таблицу размеров поставщика 1688 (см, обхваты) в метаполя товара (metafields) и переводить в размеры США (XS–XL / 0–16). Источник таблицы — карточка 1688 из `sourcing-1688`.
- **Образы («с чем носить»)** — только из того, что есть в магазине и в наличии; опора — `style-collections` / `shopify-collections`.
- **Правила консультанта** сразу записать: не выдумывать размеры и составы; если данных нет — «уточню» и ссылка на таблицу; без давления («осталось 2 шт!», если это неправда); возвраты и сроки доставки — только из страниц магазина.
- Когда дойдёт до дела — отдельный скилл (например, `size-advisor`) с 10–15 тестами «рост/вес/обхваты → размер» и проверкой pass^k.

## 7. Claude Code: `claude plugin eval` — как написать проверку для скилла

Источник: https://code.claude.com/docs/en/plugin-evals (прочитан); про «папку скиллов как плагин»: https://code.claude.com/docs/en/plugins/loading

Выводы:
1. **Что делает:** гоняет плагин на наборе тестов и ставит баллы. Каждый тест запускается 3 раза с плагином и 3 раза без него; итог — `WITH`, `W/OUT` и `Δ` (разница = польза плагина). Если без скилла тоже 1.00 — скилл не нужен для этой задачи.
2. **Устройство:** папка `evals/`, в ней по папке на тест: `prompt.md` (сверху настройки: `max_turns`, `allowed_tools`, `model`, `timeout_seconds`; ниже — запрос, как его написал бы человек, без названия скилла) и `graders/` (проверки). Самое простое начало — `claude plugin eval init`: Claude сам расспросит и напишет тесты.
3. **Виды проверок:** бесплатные — `regex` (текст/файл содержит шаблон, или `match: not_contains` — не содержит), `tool_used` (вызван ли инструмент, в т. ч. скилл; `min: 0, max: 0` — «ни разу»), `tool_order` (A раньше B), `file_exists` (создан ли файл); платные — `llm` и `baseline` (судит вторая модель по правилам «PASS если… / FAIL если…»; по умолчанию судья маленький, для тонких правил `--judge-model sonnet`). Своего кода в проверках нет.
4. **Хорошая привычка:** в каждом тесте одна проверка на результат и одна на путь (сработал ли нужный скилл). Длинные файлы проверять `regex`, а не судьёй — судья «плавает».
5. **Частая первая находка:** Δ около нуля и проверка «скилл сработал» падает — значит, скилл не выбирается на обычной фразе, править его description.
6. **Деньги и лимиты:** каждый прогон — настоящие запросы к модели на наш тариф. Дешёвая итерация: `claude plugin eval . --case <имя> --runs 1 --ablation none`, но выводы — только после 3 запусков. Если упёрлись в лимит, баллы падают в 0 и выглядят как «поломка» — смотреть колонку NOTES.
7. **Важно для нас:** команда работает с плагином (папка с `.claude-plugin/plugin.json`). Наши скиллы — обычные папки в `~/.claude/skills/`, не плагины. Варианты: сделать учебную папку-плагин с копией одного скилла, либо для правки одного скилла прямо в разговоре — скилл `skill-creator`, у него свой формат `evals/evals.json` (документация прямо говорит, что форматы друг друга они не читают). Требуется Claude Code v2.1.269+.

Что применить у нас:
- Начать с 3 скиллов, где ошибка дороже всего: **dela**, **sourcing-1688**, **shopify-admin**. Для каждого — 2–3 теста по шаблону ниже + проверка `tool_used: Skill`.
- Для описаний, которые сейчас не доходят до модели (10 скиллов из списка сверху), тест «скилл сработал на обычной фразе» — прямая проверка правки description.
- Поле `model` в `prompt.md` позволяет сравнить Opus 5.5 и Fable 5.1 на одних и тех же тестах, прежде чем что-то переключать.

## 8. Spotify: как урезать токены в Claude Code (дорогая модель думает, дешёвая читает)

Источник: https://engineering.atspotify.com/2026/9/portal-by-spotify-cut-my-claude-code-token-usage-by-90 (открылся)

Выводы:
1. **Схема:** Claude думает и правит; дешёвая модель (у них Gemini 2.5 Flash) читает большие файлы и отвечает на вопрос по ним коротко. Экономия на чтении больших файлов — в среднем ~90 %.
2. **Как устроено:** плагин `shunt` с двумя хуками (автоматическими проверками перед каждым действием): `check-file-size` не даёт Claude читать файл длиннее 350 строк и отправляет его «читателю»; `check-bash-read` ловит `cat/head/tail` по большим файлам.
3. **Что отдают дешёвой модели:** прочитать много файлов ради одного вопроса, шаблонный код по образцу, типовую документацию.
4. **Что оставляют Claude:** правки (у пересказа нет точных номеров строк), решения, отладку, всё рискованное, маленькие файлы (там экономии нет).
5. **Минусы:** +10–30 секунд на каждую передачу; делегировать мелочь невыгодно.

Что применить у нас (своими средствами, без Gemini):
- Роль «дешёвого читателя» у нас — **субагент** Claude Code (например, тип `Explore` или модель `haiku`): он читает большое и возвращает выжимку.
- **sourcing-1688 / trend-radar:** сырые ответы treg/1688 (JSON, HTML карточек), логи радара — читать субагентом с вопросом «верни только строки: offerId, цена, 复购率, остатки, 代发». В SKILL.md записать: «файлы > ~300 строк не читать целиком, а отдавать субагенту с конкретным вопросом».
- **tg-news:** разбор сотен постов — субагентом пачками; основной агент только собирает итог и обновляет панель.
- **disk-hygiene:** рефераты из больших учебных файлов — субагентами.
- **Сами SKILL.md по 40–50 КБ** — это тоже «большой файл», который читается каждый раз. Вынести справочное в `references/` и подгружать по случаю (материал 2, вывод 5).
- Хук как у Spotify можно добавить позже через `update-config`, но сначала — просто правило в скиллах.

## Ревизия скилла — чек-лист (применять к любому нашему скиллу)

1. **Описание ≤ ~500 символов**: что делает + когда использовать (1–2 ситуации) + 5–8 триггерных фраз её словами. Не пересекается с соседними скиллами.
2. **Скилл реально срабатывает** на обычной фразе без названия скилла (проверка: тест `tool_used: Skill` или просто новая сессия).
3. **Первый абзац — «зачем»**: для кого результат и что он даёт магазину (не только «что делать»).
4. **Критерий «готово»** записан одной строкой: какой файл/таблица/сообщение должны появиться и где.
5. **Нет костылей**: «проверь дважды», «думай шаг за шагом», «будь максимально тщательным», «КРИТИЧНО», пересказ своих рассуждений в ответе. Капс и «ОБЯЗАТЕЛЬНО» — только у настоящих запретов, с причиной.
6. **Нет противоречий**: одно правило в одном месте; старые пороги удалены (пример: 复购率 было 60 %, стало 40 % — в тексте не должно остаться 60 %).
7. **Нет жёсткого «рецепта по шагам»**, где модель сама справится; шаги оставить только там, где порядок важен технически (вход в аккаунт, профиль Dolphin, порядок столбцов таблицы).
8. **Границы действий**: что делаем сами (обратимое), что только с её подтверждения (удаление, деньги, отправка от её имени, публикация, суд).
9. **Отчёт по доказательствам**: «готово» — только после проверки результатом инструмента (файл есть, API ответил, панель обновилась).
10. **Справочное вынесено** в `references/` со ссылкой «смотри, когда …»; сам SKILL.md — примерно до 15–20 КБ.
11. **Большие данные** (JSON, HTML, логи > ~300 строк) читает субагент с конкретным вопросом, а не основная модель.
12. **Решения из памяти учтены** и не пересматриваются (профиль 859648353, .com а не .ru, CJ нет, Taobao без автосбора, её порядок столбцов, перевод запросов в скобках).
13. **Даты и версии**: устаревшие куски («было до 28.09…») убраны или перенесены в журнал.
14. **Уровень effort** указан, если он отличается от обычного (механика — medium; решения и документы — high; max — не нужен).
15. **Есть 2–3 теста** по шаблону ниже, и понятно, как их мерить: pass@k (она выбирает из вариантов) или pass^k (ошибка дорогая).

## Шаблон тестовых примеров для скилла (2–3 на скилл)

Формат одного теста (4 части из курса CS329Z):

```
Скилл: <имя>
Тест N: <короткое имя>
Запрос (как она пишет, без названия скилла): «…»
Окружение: какие файлы/доступы/вкладки должны быть (или «ничего»)
Каким должен быть итог: 2–4 конкретных признака (файл, строка, число, фраза)
Чего НЕ должно быть: 1–2 признака провала
Как проверить: regex / файл создан / скилл вызван / судья «PASS если… FAIL если…»
Мера: pass@3 (достаточно одного удачного из 3) или pass^3 (удачны все 3)
```

Примеры, заполненные для наших скиллов:

**sourcing-1688 — «юбка в клетку»**
- Запрос: «найди на 1688 юбку в клетку миди, как у 晴雅, от одной штуки».
- Итог: строки в таблице отбора в её порядке столбцов; у каждой строки 复购率 модели ≥ 40 %, цена 25–65 ¥, продажи > 0, отметка «от 1 шт» (✅/УТОЧНИТЬ/❌); ссылки вида `detail.1688.com/offer/<id>.html`.
- Не должно быть: CJdropshipping, Taobao, товаров с остатками в единицы.
- Проверка: regex по файлу + судья по правилам отбора. Мера: pass^3.

**shopify-admin — «почему Sold out»**
- Запрос: «почему у меня все юбки Sold out?»
- Итог: ответ с причиной по данным API (остаток, отслеживание запасов, локация), без изменений в магазине — это вопрос, а не просьба чинить.
- Не должно быть: вызова изменяющих запросов (mutation) до её «исправь».
- Проверка: судья «PASS если причина названа по данным и ничего не изменено». Мера: pass^3.

**dela — «иск по голосовому»**
- Запрос: «сделай ходатайство по делу Галан по последнему голосовому».
- Итог: .docx в папке дела на Drive; реквизиты прошли `check_rekvizity.py`; цитаты из ГПК в кавычках со статьёй.
- Не должно быть: отправки в суд/третьим лицам без её подтверждения.
- Проверка: file_exists + regex «ст\. \d+ ГПК» + судья. Мера: pass^3.

**love-scripts — «что ответить»**
- Запрос: «он написал "what are you up to this weekend?", что ответить?»
- Итог: 2–3 варианта на английском + русский перевод + какой приём в каждом.
- Проверка: regex на 2–3 варианта, судья на уместность. Мера: pass@3.

**tg-news — «новости»**
- Запрос: «новости».
- Итог: свежий сбор, разбор, панель обновлена (время изменения файла сегодня), панель открыта; реклама/мемы/дубли в skip, ИИ и фон — в soft.
- Не должно быть: удаления старого моложе месяца.
- Проверка: tool_used (скилл вызван) + файл панели изменён + судья по 3 случайным постам. Мера: pass^3.
