## Что делает скилл harness-creator (по шагам)

Идея: у каждого проекта с ИИ-агентом должно быть 5 «подсистем»: инструкции, состояние, проверка, границы задачи, жизненный цикл сессии (`SKILL.md:22-30`).

1. Смотрит, что уже есть в проекте: файл инструкций, список фич, команды проверки.
2. Спрашивает только то, чего нельзя угадать (для какого агента, можно ли перезаписывать).
3. `create-harness.mjs` создаёт 5 файлов-заготовок (не трогает существующие):
   - `AGENTS.md`/`CLAUDE.md` — как стартовать, правила, «что значит готово», как закончить сессию (`templates\agents.md`);
   - `feature_list.json` — список задач со статусом, зависимостями и полем `evidence` (улика);
   - `progress.md` — что сделано / в процессе / дальше / блокеры / решения;
   - `session-handoff.md` — передача смены следующей сессии;
   - `init.sh` — один скрипт «проверь, что всё здорово» (определяет npm/pytest/go test сам, `harness-utils.mjs:143-210`).
4. `validate-harness.mjs` ставит оценки 1–5 по пяти подсистемам (по 5 вопросов «да/нет» каждая, `harness-utils.mjs:229-265`), называет самое слабое место («бутылочное горлышко»).
5. `run-benchmark.mjs` сначала проверяет сам себя (создаёт временный харнесс и оценивает), потом оценивает проект и считает, сколько тестовых сценариев (`evals.json`) покрыто.
   Честная оговорка автора: это проверка «формы», а не «работает ли агент лучше» — для этого нужны прогоны «до/после» (`SKILL.md:76`).
6. Справочники (`references\`): память между сессиями, как оформлять скиллы, права инструментов, бюджет контекста, несколько агентов, хуки и запуск, «грабли» (15 штук).

Урок: оценка по ключевым словам в тексте (`textHas` ищет слова). Чтобы её нельзя было «накормить» словами, автор считает только слова в заголовках/списках/таблицах/коде, а не в обычных абзацах (`harness-utils.mjs:296-319`).

## Что делает audit-harness.sh (по шагам)

Читает проект (ничего не меняет), для каждой проверки пишет PASS/WARN/FAIL и в конце список «что исправить».
Деление: CRITICAL (обязательно, без них exit 1) и RECOMMENDED (желательно). Строки 35-63.

1. Инструкции (111-162): файл есть; в первых 10 строках сказано «что это за система»; есть команда проверки; есть MUST/MUST NOT; правило «обновляй доки в том же коммите»; один коммит = одно логическое действие; файл 50–200 строк (роутер, не энциклопедия); у каждого правила есть «почему» (source/why).
2. Инструменты (165-172): есть ли settings.json / MCP-конфиг.
3. Среда (175-195): lock-файл зависимостей, закреплена версия языка, команды `setup`/`dev`.
4. Состояние (198-226): `PROGRESS.md`, `DECISIONS.md`, `feature_list.json` с полями id/behavior/verification/state.
5. Обратная связь (229-241): команда `check`/`test` и она описана.
6. Продолжение между сессиями (244-270): блок «Текущее состояние» (хеш коммита + тесты), ритуал «входа» и «выхода», предупреждение «не спеши, если контекст кончается — останови и сохрани», сообщения коммитов объясняют ПОЧЕМУ.
7. Правило WIP=1 и «VCR» (297-332): одна активная задача за раз; считает долю «прошедших» от «начатых» из feature_list.
8. Список фич (335-371): у каждой фичи `evidence`; статус ставит только скрипт проверки, не сам агент; одна фича = одна сессия; состояния not_started → active → passing без пропусков.
9. Против «готово» раньше времени (374-406): определение «готово» = есть улики, а не «я уверен»; 3 слоя проверки (синтаксис → поведение → сквозная) по порядку; у каждого слоя есть `repair` (что делать, если упал).
10. Сквозные тесты и границы (409-443): файл правил `arch-rules.json` с полями what/why/fix; «каждая находка ревью становится правилом».
11. Наблюдаемость (446-476): «контракт спринта» до работы, журнал событий сессии (JSONL), рубрика оценки A/B/C/D.
12. Чистое состояние (479-509): чек-лист из 5 пунктов (сборка, тесты, список обновлён, нет отладочного мусора, запуск работает), скрипт проверки можно запускать повторно, уборка двух видов (сразу и раз в неделю).

## Что взять в НАШИ скиллы (5–8 идей)

1. **Статус «прошло» ставит проверка, а не исполнитель** (audit L08, строки 361-363). Куда: агент `proverka` и табло задач. Правило: пункт получает «готово» только вместе с `evidence` (команда + вывод, путь + размер файла), а не со словами «сделано». Это то, что `proverka` и так делает, — добавить обязательное поле «улика» в «готово» и в `razdat.py todo-done --note`.
2. **«Готово = улики, а не уверенность» + 3 слоя по порядку** (L09, 378-392). Куда: `proverka`. Слой 1 — файл существует и открывается; слой 2 — содержимое верное (числа, ссылки); слой 3 — итог работает целиком (панель открывается, бот отвечает). Если слой N упал, дальше не идём. У каждого упавшего слоя — строчка «как чинить» (`repair`).
3. **Один журнал на «вход» и «выход» из сессии** (L05, 248-270 + `templates\progress.md`, `session-handoff.md`). Куда: длинные сборы (tg_monitor, 1688). Заготовка из полей: «Последнее обновление / активная задача / сделано / в процессе / дальше / блокеры / решения / файлы / улики / следующий шаг». Сейчас у нас «N из M» и сохранение по ходу — добавить «первое действие следующей сессии» и «что проверить на старте».
4. **Предупреждение «не спеши, когда кончается контекст»** (L05, 260-262). Куда: правила длинных сборов и вкладок пульта. Текст: «Если лимит близко — НЕ торопись закончить: сохрани прогресс, запиши точку, с которой продолжить, остановись». Это подпирает наше правило «лимит 70% — стоп».
5. **WIP=1: одна активная задача за раз** (L07, 301-332). Куда: табло агентов пульта. Показатель «доля завершённых от начатых» (VCR): если начато много, а закончено мало — это сигнал на табло (красная полоска). Дёшево и наглядно.
6. **Каждая найденная ошибка становится правилом-проверкой** (L10, 441-443, формат what/why/fix). Куда: писание скиллов и `proverka`. Когда `proverka` или она находит ошибку — записываем правило в трёх полях: ЧТО нарушено, ПОЧЕМУ плохо, КАК ЧИНИТЬ (с названием конкретного файла/поля). Это то же, что наш «Урок → вписать в скилл» (приём Harness²), но с жёстким форматом.
7. **Короткий корневой файл — роутер, детали отдельно** (L04, 141-149; `SKILL.md:92`, `context-engineering-pattern.md`). Куда: написание скиллов. Ориентир 50–200 строк на входной файл (наши CLAUDE.md и SKILL.md); у каждого правила пометка «откуда/почему и когда убрать» («source / remove when»). Старые правила без причины — кандидаты на удаление.
8. **Предохранитель «не накормить проверку словами»** (`harness-utils.mjs:296-319`) и **самопроверка проверялки** (`run-benchmark.mjs`: сначала прогнать на заведомо хорошем образце). Куда: `proverka`. Перед проверкой отчёта сверять не «есть ли слово», а «есть ли файл/цифра/вывод команды»; и иногда давать ему заведомо битый и заведомо хороший образец, чтобы убедиться, что он ловит ошибки.

Бонус из «грабель» (`references\gotchas.md`) — для памяти и скиллов:
- №1: у индекса памяти жёсткий лимит; пиши в индекс одну строчку-крючок, детали — в отдельный файл (у нас так и устроен `MEMORY.md`; держать строки короткими).
- №12: описание скилла режется (~150 знаков); главное — в начало («триггеры»).
- №15: «сироты» — файлы, на которые нет ссылки из индекса; раз в время искать и предлагать убрать (удалять только с её слова).

## Что нам не подходит

- Всё про код-репозитории: `init.sh`, `Makefile`, `npm/pytest`, `package-lock`, `.nvmrc`, `make check-arch`, TypeScript-примеры. У нас сборщики на Python и скиллы-тексты, не приложение с тестами.
- Правила про коммиты («один коммит = одно действие», «объясняй почему») — частично полезны, но у неё `git` лишь резервная копия, а не рабочий процесс команды.
- Мультиагентные паттерны (coordinator/fork/swarm, `multi-agent-pattern.md`) и «двухфазное вытеснение» — это про устройство самих ИИ-инструментов, а не про наши задачи. Наш пульт уже решает это по-своему.
- `curl | bash` как способ запуска (`audit-harness.sh:4`) — по нашим правилам защиты так не делаем никогда.
- Оценки 1–5 по ключевым словам — грубый ориентир по «форме»; сами авторы признают, что реальную пользу он не измеряет (`SKILL.md:76`). Для нас важнее реальные проверки (файл открылся, цифра совпала).
- Скилл надо ставить через их `node`-скрипты в проект — нам не нужно, у нас готовые шаблоны уже в своих скиллах.
