## (а) Шаблоны и ресурсы — что это, когда брать, наш короткий вариант

В курсе «минимальный набор» — 4 файла: корневые правила, `feature_list.json`, журнал прогресса, `init.sh`. У нас эти роли уже играют: CLAUDE.md, табло агентов, память, чеклист шагов. Ниже — только то, чего у нас нет или чем можно усилить.

### 1. AGENTS.md / CLAUDE.md (шаблон корневых правил)
Что: 6 шагов «перед работой» (где я, прочитай прогресс, список задач, последние изменения, запусти стартовую проверку, прогони базовую проверку), 5 правил работы, «определение готово» из 4 пунктов, 5 шагов «в конце сессии». Главное правило: если базовая проверка уже красная — чинить её, а не наслаивать новое.
Когда: начало сессии долгой задачи.
Наш вариант (для сборщика, например tg_monitor или 1688):
```
Перед работой: 1) в какой я папке; 2) прочитать ЖУРНАЛ ПРОГРЕССА; 3) выбрать ОДНУ незакрытую задачу из чеклиста;
4) запустить быструю проверку, что вчерашний результат цел (файлы на месте, число записей не упало);
5) если проверка красная — чинить её первой.
Готово = задача выполнена + проверка ПРОГНАНА + улика записана (команда и её вывод) + завтра можно продолжить с нуля.
```

### 2. init.sh (стартовый скрипт «поставить, проверить, показать команду запуска»)
Что: один файл, три переменные (установка, проверка, запуск). Запуск программы не включается сам — только по флагу.
Когда: у кода с тестами.
Наш вариант: у нас Python-сборщики, тестов нет, поэтому идея такая — «стартовая сводка» в начале долгого сбора: рабочая папка, свободное место на диске, сколько записей вчера, когда был последний успешный запуск, есть ли ошибки в логе. Печатается одним экраном. Делать только по её слову.

### 3. claude-progress.md (журнал прогресса)
Что: сверху «Текущее проверенное состояние» (корень, как запустить, как проверить, самая главная незакрытая задача, блокер); ниже записи по сессиям с полями: цель, сделано, ЧТО ПРОВЕРЯЛИ, УЛИКИ, коммиты, файлы, известный риск, следующий лучший шаг. Файл сам не обновляется — агент обновляет, только если правила велят.
Когда: сборы дольше одной сессии.
Наш вариант: заготовка уже есть (`harness-creator-chuzhoy.md`, идея 3). Новое только: два поля «Что проверяли» и «Следующий лучший шаг».

### 4. feature_list.json (список задач для машины)
Что: на каждую задачу — `id`, приоритет, область, название, «что увидит пользователь», статус из четырёх (`not_started`, `in_progress`, `blocked`, `passing`), `verification` (шаги проверки списком), `evidence` (улики), `notes`. Сверху блок правил: «одна в работе», «passing только с уликой», «проверку не пропускать».
Когда: много однотипных шагов, легко бросить на полпути.
Наш вариант для 1688:
```
{ "id":"yubki-03", "title":"Собрать 50 поставщиков юбок", "status":"not_started",
  "verification":["файл suppliers.csv существует","строк >= 50","нет пустых цен","нет повторов ссылок"],
  "evidence":[], "depends_on":["yubki-02"] }
```
`passing` ставит только прогон проверки; руками статус не правят.

### 5. session-handoff.md (передача между сессиями)
Что: 5 блоков — «проверено сейчас», «что менялось», «сломано или не проверено», «следующий шаг» (почему он, что считать готовым, ЧТО НЕЛЬЗЯ ТРОГАТЬ на этом шаге), «команды».
Когда: сессия длинная или в проекте несколько живых направлений.
Наш вариант: тот же текст, но блок «что нельзя трогать» — обязательный. Его нет в наших заготовках.

### 6. clean-state-checklist.md (чек-лист «оставь чисто»)
Что: 6 галочек — запуск работает, проверка работает, прогресс записан, статусы честные (нет ложных «passing»), нет недописанного без заметки, следующий может продолжить без ручной починки.
Наш вариант: см. идею (г) №5 — часть можно сделать автоматической.

### 7. evaluator-rubric.md (оценочная таблица для проверяльщика)
Что: 6 пунктов (верность, проверка прогнана с уликами, держался ли в рамках задачи, переживёт ли перезапуск, понятность для следующего, готовность к передаче), оценка 0–2 по каждому, вердикт Accept / Revise / Block, поля «чего не хватает», «что починить», «когда проверять снова».
Важная оговорка автора: «из коробки агент плохой судья — находит проблемы и сам себя уговаривает принять». Поэтому рубрику надо НАСТРАИВАТЬ: прогнать на готовой работе, сравнить оценки с твоим суждением, где расходятся — уточнить критерий «прошло/не прошло», повторить. План: 3–5 кругов, каждое изменение записывать.
Наш вариант для `proverka`: вердикт у нас уже есть (✅/⚠️/❌). Взять отсюда НАСТРОЙКУ (см. (г) №1).

### 8. quality-document.md (оценки A–D по областям)
Что: таблица областей продукта и слоёв, оценка A–D, столбцы «проверка / понятность для агента / стабильность тестов / дыры / когда обновляли». Плюс «снимки бенчмарка» и «журнал упрощений» (какой компонент обвязки убрали, ухудшилось ли, вернули или нет). Правило: каждый компонент обвязки — это ставка «модель этого не умеет»; модели растут, ставки устаревают; проверяй, убрав один компонент и сравнив.
Когда: перед началом нового этапа и после значимой сессии.
Наш вариант для Пульта и скиллов: таблица «скилл → оценка A–D → когда последний раз реально использовали → дыра». Оценка без команды-улики не ставится (см. (в), P06).

### 9. reference/ — четыре короткие справки
- **method-map** — таблица «что сломалось → какой файл чинит». Холодный старт → журнал прогресса. Разбег по задачам → список задач. Объявили готово без доказательства → привязать готово к улике. Хрупкий запуск → стартовый скрипт. Слабая передача → handoff. Субъективная оценка → рубрика. Принцип: добавь самый маленький файл под наблюдаемую поломку, а не пихай всё в один большой файл.
- **initializer-agent-playbook** — «первая сессия» оставляет 5 вещей: корневой файл, список задач, журнал, стартовый скрипт, первый чистый коммит. Тест: свежая сессия отвечает на 5 вопросов (что это, как запустить, как проверить, что не сделано, что дальше).
- **coding-agent-startup-flow** — фиксированный порядок старта + «зеркало» в конце сессии.
- **prompt-calibration** — в корневом файле оставить назначение, пути запуска/проверки, жёсткие запреты, обязательные файлы, правила конца; вынести длинные истории, детали подсистем, примеры для одного места. «Если файл стал свалкой прошлых ошибок — дроби».
Наш вариант: method-map как таблица в `claude-code-priemy` — «поломка → какой наш файл» (у нас её нет в таком виде).

### 10. «Продвинутый пакет» OpenAI (openai-advanced) — для больших проектов
Что: корневой AGENTS.md как «роутер» (карта: куда идти за чем) + папка `docs/` из ~12 файлов. Из них нам полезны по идее:
- **PLANS.md** — когда ОБЯЗАТЕЛЕН план-файл: работа длится больше одной сессии; задевает больше одной подсистемы; рискованная проверка/выкатка; есть открытые решения. Минимум в плане: цель, что внутри и вне рамок, как проверять, риски, журнал, открытые решения. Готовые планы переносят в «completed», а не удаляют — как память для будущих сессий.
- **tech-debt-tracker.md** — таблица «отложенного»: дата, область, долг, почему отложили, риск, КОГДА ВЕРНУТЬСЯ (триггер).
- **RELIABILITY.md** — «золотые маршруты»: 3 главных сценария, у каждого повторяемая проверка и понятный признак провала. Правило: «фича не готова, если система потом не перезапускается чисто».
- **SECURITY.md** — секреты не в коде; чужой контент недоверенный; список действий, требующих явного «да», и команд, которые агент не запускает сам; повторяющиеся замечания безопасности превращать в проверки.
- **PRODUCT_SENSE.md** — «чего нельзя»: скрытые разрушительные действия, молчаливый провал без сообщения, неясный источник правды для видимого состояния.
- **ARCHITECTURE.md** — карта доменов, направление зависимостей, «горячие точки» (где агенту менять опаснее всего).
Не берём: FRONTEND/DESIGN/db-schema и папку `references/*.txt` — это про код приложения.

### 11. Четыре SOP (пошаговые инструкции) из пакета OpenAI
- **Закодировать знание в репозиторий** — триггеры: «агент всё время спрашивает, как устроено», «решили в чате». Шаги: перечислить, где знание прячется; решить, к какому типу относится (архитектура, поведение, безопасность, надёжность, состояние работы, внешняя справка); записать в подходящий файл; убрать старые копии, чтобы осталась ОДНА правда. Это у нас = память + скиллы; новое — шаг «убрать устаревшие копии».
- **Цикл наблюдаемости**: запрос → сопоставить → подумать → исправить → перезапустить → ПРОГНАТЬ ТОТ ЖЕ сценарий → проверить. Один и тот же повторяемый сценарий после каждой правки.
- **Цикл проверки интерфейса**: снимок «до» → одно действие → снимок «после» → сравнить; «чисто» = нужный текст есть, неожиданных ошибок нет, повтор даёт то же. Для её сайтов (Смарт Люкс) — подходит как порядок ручной проверки.
- **Слои архитектуры** — про код, нам не нужен.

### 12. Шаблоны цикла из лекции 13 (сверх задания, но важные)
- **goal-шаблон**: цель одним предложением; критерии приёмки, каждый проверяется командой; рамки — «можно трогать» и «ЧТО НЕ ТРОГАТЬ»; способ проверки по порядку; **условия остановки**: все критерии прошли ИЛИ максимум N кругов ИЛИ «3 круга подряд без продвижения (одна и та же ошибка)» ИЛИ блокер, который сам не решить; «если застряла на 2 круга — смени подход или упрости».
- **checker-prompt**: «ты не хвалишь, ты ищешь недочёты. Не нашёл ничего — это твой провал». Каждое замечание: описание, ГДЕ (файл:строка), ДОКАЗАТЕЛЬСТВО, тяжесть (критично/средне/мелко). Итог: Pass / Fail / Minor.
- **maker-prompt**: в сдаче обязательный блок «в чём я НЕ уверен — на это проверяльщику смотреть в первую очередь».
- **loop-state**: сводка по кругам (сколько пройдено, провалено, замечаний, ручных вмешательств) + список повторяющихся блокеров.
- **Мелочи**: `pass-gate-policy` (статус «проходит» только если сценарий реально прогнан, улика записана, нет блокирующей ошибки, система не в сломанном состоянии); `review-feedback-to-rule` (повторяющееся замечание ревью → проверка + текст «как чинить»); `next-task-template` (какая задача следующая / почему / что считать готовым / что менять нельзя); `anti-patterns` (всё в одном файле; одно правило в трёх местах; устаревшие правила, которые никто не проверяет; слишком узкие «если…то»; длинные мануалы в стартовом контексте).

## (б) Разборы чужих обвязок

Общая рамка курса: у каждой обвязки пять частей — инструкции, инструменты, среда, состояние, обратная связь (проверки).

### Pi (минимальное ядро + «расширения»)
Идея автора: ничего не решает за тебя, всё — точки подключения. Системная подсказка минимальная.
Можно перенять:
1. **Журнал-дерево вместо «краткого пересказа»**: сессии хранятся ветками, можно вернуться к любому месту и пойти другим путём. Для нас — вместо пересказа вчерашней сессии хранить сырой журнал решений и ветку «отвергнуто».
2. **Три файла-памяти у сообщества Pi**: `PROGRESS.md`, `LESSONS.md` (кандидаты-уроки собираются автоматически в конце сессии), `STANDARDS.md`, плюс `VISION.md`. Идея «уроки собирает расширение, а не человек по памяти» — перекликается с «Уроком» из `proverka`.
3. **Расширения-«перехватчики»**: запретить запись в `.env`, спросить перед опасной командой, будить агента сообщением из внешнего события. У нас это уже `pult\hooks\storozh.py`.
4. **Сжатие контекста — сменяемая стратегия** (по темам, с другой моделью для пересказа).
5. **Правила по уровням**: общий → папка выше → текущая; скиллы грузятся по требованию (бережёт кэш запроса, то есть деньги).
Не подходит: «сделай сам расширение на TypeScript», сессии-деревья в формате их программы, установка пакетов сообщества (чужой код → только через карантин).

### Claude Code (то, чем мы пользуемся)
Идея: цикл простой, весь вес — вокруг него: память, права, хуки, субагенты.
Можно перенять:
1. **Четыре уровня CLAUDE.md** (организация / личный / проект / локальный) + CLAUDE.md в подпапке подгружается только когда читают файлы той папки. У нас так и устроено (общий + папка проекта).
2. **Автопамять режется**: грузятся только первые 200 строк или 25 КБ. Мы это проверили на наших файлах — см. (г) №3.
3. **Хук `Stop`** — срабатывает, когда агент объявляет «готово», и может не пустить без проверки. Это «детерминированная проверка вместо просьбы в промпте».
4. **Чьё дело что**: CLAUDE.md = «что», скиллы = «как», MCP = «куда подключиться», хуки = «когда принудительно». Если смешать — течёт контекст.
5. **Субагент пишет в свой отдельный файл** и не раздувает главный разговор (для нас: поручать объёмное помощникам).
6. **Сжатие воронкой**: сначала без потерь (выбросить повторы), потом структурно, только в конце «пересказ нейросетью».
Оговорка курса: подробности про «пять слоёв сжатия» и «семь режимов прав» взяты из чужого разбора версии 2.1.88 и могли устареть; названия режимов прав сменились.
Не подходит: «организационный уровень» (мы одни).

### Codex (OpenAI)
Идея: репозиторий = единственный источник правды; AGENTS.md — «оглавление-страница» (около 100 строк), не энциклопедия.
Можно перенять:
1. **Указывать неизменные границы и команду проверки, а не расписывать реализацию** («don't micromanage, focus on invariants»). Для заданий помощникам (см. (г) №7).
2. **Четыре действия с контекстом**: Записать (вынести из окна в файл), Выбрать (подтянуть только нужное), Сжать, Изолировать (поручить субагенту, чтобы он не видел лишнего).
3. **Передавать только изменения среды** (какая ветка, какая папка), а не вставлять заново всё описание каждый ход. Для Пульта: при сообщении вкладке — только то, что изменилось.
4. **Каждая задача в своей рабочей копии** (git worktree — отдельная копия папки на своей ветке): границы задают физически, а не просьбой.
5. **Команды проверки лежат в спецификации**; перед рискованным действием — план и одобрение.
Не подходит: монолит на Rust, `.codex/agents/*.toml`, целая «миллион строк кода написал агент» история — другой масштаб.

### DeepSeek Harness (всё — плагин, включая сам цикл)
Идея: обвязка — отдельная «операционная система», модель заменяема. Статус: «предварительная версия для разработчиков», механизмы ещё меняются.
Можно перенять:
1. **«Что увидела модель — то записано»**: всё, что попало в запрос к модели, можно восстановить из журнала; это проверяется программно. Для нас: сохранять точный текст задания, отданного вкладке, помощнику или Hermes, с временем — тогда сбой можно разобрать.
2. **Журнал только дописывается, не перезаписывается** — можно проиграть заново.
3. **Каждый шаг цикла — событие**, на которое можно повесить проверку/память/запрет, не трогая сам цикл.
4. **«Шов возможностей»**: инструмент зависит от интерфейса («файловая система»), а не от конкретной реализации — можно сменить среду, не меняя что видит модель.
Не подходит: сама архитектура плагинов (нужна команда программистов), настройка дороже пользы для нас; цену признаёт и сам курс.

## (в) Проекты — что делает решение и один приём

Все проекты строятся на ОДНОМ учебном приложении (база знаний в окне Electron). Каждый следующий начинается с итога предыдущего. Смысл — не приложение, а СРАВНЕНИЕ: один и тот же заказ с «слабой» и «сильной» обвязкой.

**P01. Базовая линия против минимальной обвязки.** Заготовка: только фраза «Сделай приложение, которое показывает документы и отвечает на вопросы». Решение: те же коды плюс AGENTS.md, список из 4 задач, `init.sh`, журнал. Приём: **вместо вопроса «получилось?» — таблица «задача → где смотреть улику в заготовке → где в решении»**, и мерить 4 вещи: завершено, время до первого запуска, ручные повторы, преждевременное «готово». Применять к любому нашему «до/после».

**P02. Читаемое для агента рабочее пространство.** Две сессии: сессия A оставляет работу недоделанной, сессия B стартует только по папке. Решение: подробные `ARCHITECTURE.md`, `PRODUCT.md`, `session-handoff.md` (там «Решения» с причиной, напр. «отдельный канал для содержимого, чтобы список был лёгким»). Приём: **нарочно оборвать сессию посередине и проверить, продолжит ли новая только по записям.** Это тест «свежей сессии».

**P03. Непрерывность и контроль рамок.** Решение: правило «одна задача за раз» из 6 шагов (выбрать → сделать только её → проверить → записать статус и улику → коммит с id задачи → только потом следующая) + схема зависимостей между задачами («метаданные → нарезка → статус / вопросы-ответы»). Приём: **рисовать зависимости между шагами стрелками прямо в правилах**, чтобы агент не начал шаг, для которого нет основы. Для 1688: «ссылки → карточки → цены → сводка».

**P04. Обратная связь времени работы и контроль границ.** В заготовке посеян скрытый баг: у файла длиннее 1000 знаков куски текста выходят пустыми. Решение: общий журнал с полями время / уровень / служба / сообщение / данные (JSON) + скрипт `check-architecture.sh` (три проверки `grep`: «в интерфейсе нет файловых модулей», «в службах нет электрона», «нет React в серверной части»; код выхода 1 при нарушении). Приёмы: (1) **логировать и число, и объём** (число кусков И суммарные знаки — именно «сумма знаков = 0» выдаёт пустые куски); (2) **сначала воспроизвести баг на длинном образце, потом чинить**; (3) границы проверяет скрипт, не просьба. Для сборщиков: после сбора печатать «N записей, суммарно M знаков».

**P05. Роли и циклы проверки.** Один и тот же вариант (история диалога) делается тремя способами: одна роль / исполнитель+оценщик / планировщик+исполнитель+оценщик. Итоговые оценки в решении: 1,6 → 3,3 → 4,9 из 5. Приёмы: (1) **планировщик ДО кода пишет критерии приёмки (в варианте C их 10), что внутри и вне рамок** — «контракт спринта»; (2) **журнал оценок по кругам** (2,8 → 3,1 → 3,3; 4,2 → 4,6 → 4,8 → 4,9) — видно, что исправление действительно улучшает; (3) менять можно только роль, фичу при сравнении не менять. Оговорка: эти оценки написаны в файлах руками как образец, не получены прогоном — как реальный замер нельзя считать.

**P06. Капстоун (итог всего).** В заготовке продукт уже есть, обвязки почти нет. Решение: полный набор — AGENTS, CLAUDE, список из 15 задач, `init.sh`, передача, чек-лист на 30 пунктов, рубрика, таблица качества, `benchmark.sh`, `cleanup-scanner.sh`, `check-architecture.sh`, `RELIABILITY.md`. Приём: **`cleanup-scanner.sh` ищет разрыв между данными — 5 проверок:** (1) файл содержимого без записи в списке (сирота); (2) файл кусков без записи в индексе; (3) запись в списке без файла; (4) «проиндексирован» без кусков; (5) история ответов ссылается на удалённый документ. Это дёшево и ловит тихое гниение данных. Оговорка (важная): `benchmark.sh` только ИМИТИРУЕТ работу (копирует файлы и прикидывает число кусков по пустым строкам), а в таблице качества почти все области — «A» (одна «B»), рубрика — «5.0/5», «все 30 пунктов пройдены», написано самим автором. То есть курс сам попадает в ловушку «сам себя оценил» из лекции 9. Мы этот приём переносим, а их цифры как доказательство не берём.

**P07. Первый автоматический цикл (только страница, папки нет).** Три опыта: `/goal` (цель + проверка + стоп), `/loop` по таймеру (интервал 10–30 минут, смотреть не менее 2 часов), maker-checker (минимум 5 кругов, всё в `loop-state.md`). Приёмы: (1) **сначала один ручной прогон как базовая линия** (сколько кругов, сколько вмешательств), потом тот же `goal.md` автоматически; (2) считать: сколько нашёл, сколько починил сам, сколько ложных срабатываний, сколько ухудшил, сколько времени ушло на разбор; (3) итоговый вопрос: «потолок качества — у делающего или у проверяющего?». Свой критерий «стоит ли автоматизировать»: время сэкономленное против времени на разбор результата.

**P08. Первый граф (только страница).** Три опыта на отдельных ветках: нарисовать цикл как граф (узлы, связи, общее состояние `state.md`, правила «если…то»); параллельные узлы в отдельных рабочих копиях; условный откат + узел «человек одобряет». Приёмы: (1) **найти неявные связи** — решения, которые раньше жили только в голове агента; (2) **откат к узлу, породившему проблему, а не к последнему** (для этого в общем состоянии записывают, из какого слоя ошибка: например, тесты зелёные, но задачу поняли неверно → вернуться к «исследованию», не к «написанию»); (3) **формат запроса к человеку**: что случилось, что изменилось, почему нужен человек, что будет при «да» и при «нет»; у узла одобрения — таймаут (через N часов без ответа — отказ или повышение уровня). Каркас на LangGraph в лекции 14 — в нём правило «после провала проверки вернуться в реализацию» БЕЗ предела повторов (возможен бесконечный круг), и проверка — заглушка `"def test" in code`. Это каркас-набросок, не рабочее решение.
