## 2. Ключевые идеи простыми словами

### 2.1. Оценка промпта (prompt evals) — как это устроено по курсу

**Три пути после того, как промпт написан:** (1) проверил один раз — «сойдёт»; (2) проверил пару раз, поправил угловой
случай; (3) прогнал через конвейер оценки и правишь по цифрам. Курс: первые два — ловушки, в которые попадают все;
реальные пользователи принесут то, о чём ты не подумал.

**Конвейер из 5 шагов (lesson 10):** черновик промпта → набор тестовых входов (dataset) → прогон каждого входа через модель →
оценщик ставит балл 1–10 → среднее по набору → меняешь промпт → снова. Пример: 10, 4, 9 → среднее 7,66; после правки 8,7.

**Набор тестов генерирует модель** (дешёвая, Haiku): «сделай массив JSON-объектов с полем task…», вывод — через prefill
` ```json ` + stop sequence ` ``` `, затем `json.loads`. Набор сохраняют в `dataset.json`. Во время разработки — 2–3 теста
(быстро), для финальной проверки — больше. Параллельность прогона начинать с 3 (иначе упрёшься в лимиты API).

**Код конвейера — три функции:** `run_prompt(test_case)` (вставить вход в шаблон, вызвать модель) →
`run_test_case` (вызвать + оценить) → `run_eval(dataset)` (по всем, среднее). Курс: «это и есть большая часть любой системы
оценки; сложность — в деталях».

**Три вида оценщиков:**
- **Код** — длина, есть/нет слов, валидность синтаксиса (`json.loads`, `ast.parse`, `re.compile` → 10 или 0), читаемость.
- **Модель** — качество, следование инструкции, полнота, полезность, безопасность.
- **Человек** — гибко, но медленно и утомительно.
Сначала записать **критерии** (пример: формат «только код без пояснений», валидный синтаксис, решает задачу).
Формальные критерии — коду, смысловые — модели. Итог — среднее (или взвешенное) двух баллов.

**Главный приём оценщика-модели:** просить не только число, а JSON с `strengths` (1–3 сильные стороны), `weaknesses`
(1–3 слабые), `reasoning` (почему) и `score` 1–10. «Без этого модель скатывается к средним оценкам около 6».

> You are an expert code reviewer. Evaluate this AI-generated solution. Task: {task} Solution: {solution}
> Provide your evaluation as a structured JSON object with: "strengths", "weaknesses", "reasoning", "score" (1-10).
> — «Ты эксперт. Оцени решение. Верни JSON: сильные стороны, слабые, обоснование, балл 1–10».

**Дополнительные критерии в оценку** (`extra_criteria`): «в ответе должны быть: калорийность, БЖУ, блюда с граммовкой
и временем». Отчёт прогона — HTML с обоснованием по каждому тесту.

**Цифры из урока, как растёт балл** (план питания для спортсмена): наивный промпт 2,32 → прямая первая строка 3,92 →
список требований к результату 7,86 → дальше XML-теги и пример. **Правило: одна правка за раз → перемерить.**
Лучшие ответы из прогона (балл 10) берут как образцы в сам промпт.

**Без инфраструктуры (Claude 101, курс для НКО):** взять 5–10 своих прошлых результатов (письма, анализы) → дать Claude
ту же задачу → сравнить с эталоном → записать, какой контекст пришлось добавить. Пример Rio: прогнал прошлый квартал,
где ответ известен; ИИ нашёл корреляцию, но пропустил тип программы → в инструкцию на будущее «учитывай тип программы»;
даты набора ИИ пытался угадать → правило «без дат в данных когортный анализ не делать». «Если после нескольких
уточнений не выходит — эту задачу не делегируем».

**Выбор модели тем же эвалом (Platform 101):** 20–30 реальных примеров; прогон снизу вверх Haiku → Sonnet → Opus;
«правильная модель — самая дешёвая, чей ответ ты бы отправил». `response.usage` показывает токены = деньги.
В одном конвейере разные модели на разные шаги: сортировка — Haiku, черновики — Sonnet, сложные ответы — Opus.

**Thinking тоже решается эвалом:** сначала довести промпт без размышлений; включать extended thinking, только если
точности всё ещё не хватает. На Opus 5 размышление адаптивное, глубина — параметр `effort` (low…max, по умолчанию high)
внутри `output_config`. Для классификации и извлечения — не нужно.

### 2.2. Промпт-инжиниринг (что даёт баллы)

- **Первая строка — самая важная.** Глагол-действие и задача: не вопрос «что ему есть?», а «Сгенерируй однодневный
  план питания для спортсмена с учётом ограничений».
- **Конкретика двух видов:** (а) **требования к результату** — длина, структура, обязательные элементы, тон — «почти
  в каждом промпте»; (б) **шаги процесса** — только для сложного: разбор причин, решения, где надо рассмотреть несколько
  сторон (пример: падение продаж → рынок, отрасль, люди, оргизменения, отзывы клиентов).
- **XML-теги** для данных: `<sales_records>` лучше `<data>`; разделять `<my_code>` и `<docs>`.
- **Примеры** в `<sample_input>` / `<ideal_output>` + одна фраза «почему этот ответ хороший». Брать примеры на частые ошибки
  (сарказм в отзыве → «негатив»).
- **Картинки — те же правила:** «сколько шариков?» ошибается; методика «пронумеруй каждый, потом пересчитай другим способом»
  или пример с известным ответом — работает. Пример большого промпта: оценка пожарного риска по спутниковому снимку —
  5 шагов, шкала 1–4 с описанием каждого уровня, «по каждому пункту одно предложение, в конце — число».
- **Цепочка вместо одного длинного промпта, если модель игнорирует часть запретов:** сначала написать, вторым запросом —
  только исправление:
  > Revise the article provided below. 1. Identify any location where the text identifies the author as an AI and remove
  > them 2. Find and remove all emojis 3. Locate any cringey writing and replace it with text written by a technical writer.
  > — «Перепиши: убери упоминания ИИ, все эмодзи, замени неуклюжие места».

### 2.3. Структурированный вывод

- **Prefill + stop sequence:** последним сообщением ставим ответ ассистента ` ```json `, а `stop_sequences=["```"]` —
  модель пишет чистый JSON и останавливается. Работает для CSV, списков, кода. Важно: **с extended thinking prefill
  несовместим** (оговорка курса).
- **Через инструмент:** схема инструмента = схема ответа; API проверяет JSON по схеме и отдаёт его целиком по ключам
  верхнего уровня. `fine_grained=True` отключает проверку — быстрее, но может прийти невалидный JSON
  (`"word_count": undefined`) → обязательно `try/except json.JSONDecodeError`.
- **Цитаты (citations):** `"citations": {"enabled": True}` в документе → в ответе `cited_text`, номер документа, страницы
  (для текста — позиции символов). Для проверки фактов — ровно то, что нужно.
- В курсе «capabilities»: структурированный вывод, исполнение кода, системный промпт — «средства, чтобы намерение
  не размывалось».

### 2.4. Инструменты и агентный цикл

- Модель **не выполняет** инструмент, она просит; выполняет наш код. Цикл: запрос с `tools` → `stop_reason == "tool_use"` →
  выполнить все блоки `tool_use` → вернуть `tool_result` с тем же `tool_use_id` → повторять до `end_turn`.
- Ошибку инструмента тоже возвращать (`is_error: True`, текст ошибки) — модель часто сама повторит с исправленными
  параметрами. Поэтому в функциях — проверка входа и **понятные сообщения об ошибке** («Location cannot be empty»).
- **Описание инструмента — 3–4 предложения:** что делает, когда звать, что возвращает + описание каждого параметра.
  «Расплывчатое описание — причина №1, почему агенты промахиваются».
- **Инструменты должны быть общими и сочетаемыми** (как у Claude Code: bash, read, write, grep), а не «узкие под одну
  задачу» — тогда агент решит и то, что не планировали.
- **Осмотр окружения (environment inspection):** «как модель узнает, что действие сработало?» — читать файл до правки,
  скриншот после клика, проверка ответа API, для видео — субтитры whisper и кадры ffmpeg.
- **Проверь базу перед следующим слоем:** добавил инструмент/источник/MCP — задай системе вопрос с заранее известным
  ответом («1+1»). «Проверенная база — единственная, от которой можно отлаживать».
- Встроенные инструменты: web search (`max_uses`, `allowed_domains` — только нужные сайты), web fetch, code execution
  (песочница без сети, файлы через Files API), memory, text editor.
- Platform 101: **Tool Runner** в SDK сам крутит цикл; **Managed Agents** — цикл на стороне Anthropic
  (агент → окружение → сессия → события; поток событий открывать **до** отправки задания). Рубрика + отдельный оценщик
  в своём контексте возвращает замечания, агент дорабатывает (Lighthouse 96).
- Скилл vs инструмент vs MCP: «инструменты — для твоих данных, скиллы — для твоих процессов, MCP — для чужих сервисов».
  MCP можно сузить: `default_config: {"enabled": false}` и включить только чтение.

### 2.5. Workflows против агентов (модуль 9)

- **Workflow** — заранее известная цепочка вызовов; **агент** — цель + инструменты, путь выбирает модель.
- Workflow: выше точность (модель занята одним шагом), проще тестировать, предсказуемо. Агент: гибкий, но ниже доля
  успешных задач и трудно проверять. **Рекомендация курса: «всегда workflow, где возможно; агент — только когда правда нужен».
  Пользователю не важно, что у вас модный агент, ему нужно, чтобы работало».**
- **Цепочка (chaining):** задача режется на последовательные шаги; между шагами можно делать обычную обработку кодом.
- **Маршрутизация (routing):** первый дешёвый вызов относит вход к категории из списка → дальше только один специальный
  промпт/конвейер. Шаблон:
  > Categorize the topic of a video into one of the listed categories: <topic>…</topic> <categories>- Educational
  > - Entertainment …</categories> — «Отнеси тему к одной категории из списка».
- **Параллелизация:** один вход — несколько независимых оценок, каждая со своими критериями (у курса: пригодность детали
  для металла / полимера / керамики…), затем шаг-агрегатор сравнивает и решает. Плюсы: внимание на одном аспекте,
  каждую ветку правишь и тестируешь отдельно, новый вариант = новая ветка.
- **Оценщик-оптимизатор (evaluator-optimizer):** производитель делает → оценщик сверяет с критериями → замечания назад →
  повтор до приёмки (пример: фото детали → CAD-модель → рендер → сравнить с фото).
- **Оркестратор-исполнители** в этом курсе отдельным уроком **нет**; ближе всего — Managed Agents, пример 3: координатор
  раздаёт инцидент трём специалистам (каждый в своём контексте, общая файловая система), сводит отчёт; отправка в Slack —
  после одобрения человеком.

### 2.6. Кэширование промптов (prompt caching)

- Модель предобрабатывает вход; без кэша эта работа выбрасывается. Кэш хранит её и при повторе **того же начала** запроса
  отвечает быстрее и дешевле.
- **Живёт 5 минут**, каждое использование продлевает бесплатно; есть 1 час — дороже запись.
- Включается **вручную**: `cache_control: {"type": "ephemeral"}` на блоке; кэшируется всё **до и включая** точку.
  Порядок обработки: **инструменты → system → сообщения**. До **4 точек** кэша. Минимум **1024 токена** в кэшируемой части.
- Изменение **одного символа** (даже «please») до точки — кэш сброшен. Поэтому стабильное (инструкции, схемы инструментов,
  большой документ) — в начало, меняющееся (вопрос, дата, данные) — в конец.
- Проверка: `cache_creation_input_tokens` в первом ответе, `cache_read_input_tokens` в следующих.
- Platform 101: «системный промпт 4 000 токенов × 100 вызовов в час — разница между нормальным счётом и звонком из бухгалтерии».

### 2.7. Контекст, RAG, память

- **Четыре приёма для долгого агента:** (1) подгрузка «по требованию» (just-in-time) — не класть всё в промпт, а дать
  инструмент «достать раздел»; (2) серверное сжатие истории (compaction); (3) кэш; (4) memory tool — папка заметок между
  сессиями, хранилище наше.
- **«Потеря в середине»:** точность падает >30 %, если важный факт в середине длинного контекста. Важное — **в начало и
  повторить в конце**. «Больше контекста ≠ лучше: отбирай безжалостно, ставь стратегически, повторяй главное».
- **RAG:** нарезка (по размеру с перекрытием — надёжный запасной; по разделам — если структура гарантирована;
  по предложениям — середина) → эмбеддинги (у Anthropic нет, курс берёт VoyageAI) → поиск по косинусной близости.
  Для артикулов и кодов («INC-2023-Q4-011») смысловой поиск промахивается → **BM25** (точные редкие слова) +
  слияние рейтингов RRF: `score = Σ 1/(k + место)`.

### 2.8. Как устроена модель — 4 свойства (AI capabilities and limitations)

| Свойство | Сильная зона | Слабая зона | Чем лечить |
|---|---|---|---|
| Предсказание следующего токена | пересказ, переформатирование, известное | **конкретика**: имена, даты, цифры, ссылки, цитаты | цитаты, проверка, «генератор + проверяющий» |
| Знания | частое, устоявшееся | редкое, локальное, свежее, спорное | веб-поиск, RAG, инструменты |
| Рабочая память | материал влезает, сессия текущая | длинные тексты, середина, «помнит прошлый чат» | вперёд важное, по кускам, заново подавать |
| Управляемость | короткие проверяемые указания (таблица, ≤100 слов) | длинные рассуждения, абстракции, точная арифметика | цель + формат, контрольные точки, код для счёта |

- **Следы обучения:** поддакивание (sycophancy), многословие, лишняя осторожность, уверенность ≠ точность.
  Проверка: начать с ложного «эта стратегия непробиваема» и сравнить с «честно возрази, если я неправ».
- **Буква вместо духа:** указание выполнено, смысл нет («сделай короче», а беда в структуре). Лечить — **назвать цель**,
  а не повторять указание громче. Для многошаговых — **контрольная точка** («покажи результат шага 2 и жди»).
- **Диагностика сбоя = назвать пару свойств:** выдуманные ссылки = предсказание + знания → проверять конкретику;
  дрейф длинного диалога = память + управляемость → новый чат и заново контекст; неверная математика → в код;
  согласие с плохой посылкой → пригласить возражать.

### 2.9. 4D — модель работы человека с ИИ (AI Fluency)

- **Три режима:** Automation (ИИ делает по инструкции), Augmentation (думаем вместе), Agency (настроили — работает сам).
- **Delegation (делегирование)** = Problem Awareness (понять цель и работу) + Platform Awareness (что умеет система) +
  Task Delegation (кто что делает). «Делегировать исполнение обычно безопасно, делегировать суждение — обычно нет».
- **Description (описание)** = Product (что на выходе: формат, аудитория, стиль) + Process (как подходить) +
  Performance (как вести себя: кратко/подробно, спорить/поддерживать). 6 приёмов: контекст, примеры, ограничения,
  шаги, «сначала подумай», роль/тон; «секретное оружие — попросить ИИ улучшить сам промпт».
- **Discernment (различение)** = Product (точность, уместность), Process (логика, пропуски), Performance (поведение в диалоге).
- **Diligence (ответственность)** = Creation (какую систему и какие данные), Transparency (честно про роль ИИ),
  Deployment (проверил и ручаешься за то, что отдаёшь).
- **Два цикла:** внутренний Description ↔ Discernment (каждый день: описал → оценил → уточнил); внешний
  Delegation ↔ Diligence (решения: что отдавать ИИ, какие данные, кто отвечает за итог).
- **Для строителей:** «тесты приёмки до первой строки кода» — проверяемые, «чужой человек скажет: прошло / нет»
  (хорошо: «пациент с простым смартфоном видит время ожидания за 30 секунд без регистрации»; плохо: «удобно»).
  **Description Chain:** голос пользователя → требование → тех. задание → инструкция ИИ → тесты; «код работает, продукт
  нет» = порвалось звено выше. **5 линз проверки:** корректность, качество, соответствие задаче, опыт пользователя,
  ответственность. «"Сделай красиво" — желание, а не задание». «Ты отвечаешь за результат, не за вывод: "это написал ИИ"
  ничего не объясняет». Решение перед выкладкой: выпустить / исправить / остановить.

### 2.10. ИИ для малого бизнеса

- Начать с **досье-контекста о бизнесе** (что продаём, кому, ценности, ограничения) и давать его в начале работы.
- **Аудит рутинных задач:** частота, время, стандартна ли, цена ошибки → три корзины: «ИИ делает сам» (FAQ, документированное),
  «ИИ готовит, человек решает» (персональные письма, сводка отзывов), «только человек» (жалобы, переговоры, сбои).
  Вопрос не «может ли ИИ», а «должен ли».
- **Гигиена данных:** убрать имена, контакты, платёжные данные, закупочные цены («Покупатель A / Поставщик X»);
  чувствительное — только в инструмент со строгими настройками; утекло — удалить чат и запросить удаление.
- **Проверка исследований ИИ:** отметить минимум 2 утверждения (нормы, цены, сроки) и сверить с первоисточником;
  ИИ путает юрисдикции и подаёт устаревшее как текущее. Тест: попросить ссылки на организации/поставщиков и проверить, существуют ли.
- **Политика ИИ на 1 страницу:** что отдаём ИИ / что всегда человеку / как отвечаем (проверка, прозрачность, что делать при ошибке).
  Освободившееся время — на «человеческое»: личная записка покупателю, отношения.

### 2.11. Агент в команде (human-agent teams)

- 4 принципа: чёткие роли (у каждой повторяющейся работы один владелец, агент тоже), **записанная «полярная звезда»**
  (измеримая цель — её ставит человек), постепенное доверие (расширять права по одному виду задач после серии удач),
  нужный доступ к информации («для агента незаписанное не существует»).
- 5 вопросов готовности: всё открыто и ищется? владельцы записаны? у всех нужные инструменты? есть проверка (рубрика,
  тест, второй агент) **до** человека? есть цель?
- Старт: первая видимая работа агента — утренняя сводка; «объяснил одно и то же дважды — запиши в скилл»; еженедельный
  разбор «что работает».
