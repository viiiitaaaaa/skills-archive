## 2. Ключевые идеи простыми словами

### 2.1. Неделя 1 — почему таблицу нельзя «загрузить в чат»
- Контекстное окно — рабочая память модели. Загруженный файл не «изучается», а кладётся в это окно. Большой CSV (180 МБ) туда не влезет — приложение **молча обрежет, возьмёт выборку или подсмотрит кодом**. «Если не знаешь, что из этого случилось, — ответу верить нельзя».
- Правильная схема: модели даём **описание столбцов (кодбук), список колонок и маленькую выборку**, а она пишет **код**, который обрабатывает всю таблицу вне окна.
- Длинный чат портится («context rot» — гниение контекста): на одну задачу — один свежий чат/сессия; в слайдах — качество падает примерно после 20+ обменов.
- «Неровная граница» (jagged frontier, по Моллику): ИИ сверхчеловечески хорош в одном и неожиданно плох в соседнем, и где граница — не видно, пока не проверишь. Пример из задания: доход по округам Коннектикута — штат перешёл с округов на «плановые регионы», и ИИ обычно **молча это замазывает**.
- Модель обучена быть услужливой, поэтому «скорее даст уверенный неверный ответ, чем скажет "не знаю"».

### 2.2. Неделя 2 — конвейер и «вайб против направленного»
Привычки промпта для кода:
- Назвать инструменты («pandas и matplotlib»), показать форму данных (имена колонок + типы, или выборку 1/1000), задать выход («одна строка на (страна, год)», «PNG 1200×800», «3–5 рисунков, не больше»).
- > «Vague: *Analyze this data and write a report.* Specific: *Estimate the association between income and trust across countries, controlling for region. One LOESS scatter + one table. 700 words, non-causal language.*» — расплывчато против конкретно: что связываем, с какими поправками, сколько рисунков, сколько слов, без слов о причинности.

Как работать в Claude Code по курсу:
- **Сначала план, потом код:** «Don't write code yet — propose a plan» (Shift+Tab — режим плана).
- **Просить скрипты, а не ответы:** «Write 01_download.py … then run it». К концу — нумерованная цепочка `01_download → 02_clean → 03_aggregate → 04_join → 05_report`.
- **Большой файл не пускать в окно:** агент смотрит его только кодом (head, размеры, типы, value_counts). Если пытается прочитать целиком — остановить: «don't read the CSV, inspect it with pandas».
- **Проверка после каждого шага:** «Print row counts before and after. Show 5 random rows.» Потом открыть итог самому — «самопроверка агента хороша, ваша выборочная проверка обязательна».
- **Одна фаза — одна сессия:** закончили чистку → `/clear` → одна строка-итог («Чистые данные в data_clean/x.csv, строка = товар; теперь сводим»).
- **Проверка понимания:** спросить «объясни разницу между Q6 и Q7 простыми словами» и «где в кодбуке определён Q57? Процитируй дословно» — цитата заставляет действительно посмотреть.
- **Тихая ошибка перекодировки:** код пропуска (−2) посчитан как число и отравил индекс. Лечение: «Show the value counts of Q57 before and after recoding, side by side».
- **На джойнах «врут» счётчики строк:** «How many rows before and after the join? Which countries failed to match, and why?» — и **требовать список несовпавших строк, а не только их число** (классика — разные коды: GBR против UK).
- Композитный индекс: каждый пункт привести к z-оценке (стандартизовать) и усреднить — так разные шкалы складываются честно; среднее ≈ 0.
- Эксперимент: сначала дать ИИ «Create a nice looking report on an interesting question using this data», оценить 1–10, потом строить по шагам. Разница — и есть урок.

### 2.3. Неделя 3 — проверять работу ИИ
Типовые ошибки кода от ИИ: **не тот тип джойна** (потеряли строки), **пропуски** (откуда NaN?), **правдоподобно, но неверно** («проведи меня по расчёту шаг за шагом»), **выдуманный код или цифры**. Каждый раз: «Explain the code you just wrote. What assumptions did you make?» — объясни код и какие допущения сделал. Всегда смотреть: строки после джойна, сводную статистику (средние разумны?), несколько случайных строк.

**Три вида тестов** (из страницы «Designing projects»):
1. **Тесты данных** (падают громко, когда мир поменялся): схема и типы на месте, первичный ключ уникален, обязательные поля не пустые, даты разбираются, числа в разумных пределах, категории из известного списка, нет подозрительных дублей, смешанных единиц, сломанной кодировки.
2. **Описание данных** (data-describe — не «прошёл/не прошёл», а ритуал перед любым выводом): сколько строк, групп, событий; распределения главной цифры; крайние случаи — самый частый/редкий, ранний/поздний, наибольший/наименьший. «Не можете чётко описать выборку — не знаете, что усредняют ваши выводы».
3. **Тесты кода:** функция = f(x); игрушечный вход из 3–5 строк, где правильный ответ известен заранее. Просить так: «give me a pytest for this function with a mock DataFrame of 3 rows covering these edge cases».

Пять тестов к таблице отелей (переносятся 1:1): ключ уникален; ключевые поля не пустые; внешний ключ есть в справочнике; доля в пределах 0–100; число строк в ожидаемом диапазоне. **Тест должен возвращать сами провалившиеся строки**, а не только «FAIL».

- CLAUDE.md делится на две короткие части: **предпочтения** («Python, pandas вместо циклов, итог в /out, функции до 40 строк») и **обязательные практики** («файлы данных неизменяемы — никогда не править CSV на месте, писать новый в /out»; «перед функцией — мини-тест на 5 строках выдуманных данных»). Правило пополнения: **что поправила дважды — строка в CLAUDE.md.** Коротко: «лишний текст разбавляет важные правила».
- Где хранить правило: верно только в этом проекте → CLAUDE.md; задача, которую сделаешь и в другом проекте → скилл. «Сомневаешься — в CLAUDE.md; второй раз копируешь тот же кусок — переноси в скилл». Зрелый скилл — тот, что прошёл три проекта без правок.
- Примеры скиллов из курса: `write-data-tests` («для схемы таблицы — проверки обязательных колонок, типов, уникальности ключа, непустых ключевых полей, разумных диапазонов»), `classify-texts-with-llm` («пачками по 20, фиксированный системный промпт, разбор JSON, проверка схемы, запись в /out/classified_{date}.csv, ключ API не логировать»).
- Синтетические данные: ИИ хорошо генерирует правдоподобную таблицу-справочник по описанию (доли каналов в сумме 100%, комиссии 10–18%) — но потом **проверить**: суммы, правдоподобие, присоединяется ли обратно.
- Автономный запуск (`claude -p "..."`) — только на знакомом проверенном конвейере: нужная ветка, записанный критерий успеха, `git diff` после, тесты после. На новом коде и общих ресурсах — нельзя.
- Рабочий цикл: **Инвентаризация** («что тут лежит?») → **План** («какие шаги?») → **Выполнение и проверка**.

### 2.4. Проектирование большого проекта (страница «Designing projects»)
- **Два режима.** A — «делаю то, что в целом знаю»: проверяю построчно. B — «делаю то, чего не умею» (новый метод, новая библиотека): проверить код не могу, могу только **бета-тестировать** — запускать, сравнивать с тем, что понимаю, строить дешёвые проверки правдоподобия. Главная ошибка — **уверенность режима A на работе режима B.** Назвать режим вслух до начала.
- **Пусть ИИ возьмёт у тебя интервью до кода:**
  > «I want to do X. Before you write any code, ask me 5–8 questions to clarify goals, constraints, risks, and what 'done' looks like. Don't propose solutions yet.»
  > (Хочу X. До кода задай 5–8 вопросов: цели, ограничения, риски, что значит «готово». Решения пока не предлагай.)
  Ответы сохранить в `PLAN.md` и сослаться из CLAUDE.md (`@PLAN.md`). Вскрывает: какой ключ, что одна строка, что значит «хорошо», какие строки выкидываем.
- **Вертикальный срез сначала:** одна страна, один сезон, один источник, одна классификация — «кривовато, но целиком». Потом вширь (больше источников), потом вглубь (лучше промпты). Обратный порядок — «собрать всё → классифицировать всё → обнаружить, что конвейер сломан» — самая частая причина провала.

### 2.5. Джойны (страница «Joining tables» + проект)
- Ключи: первичный (уникален в своей таблице), внешний (ссылается на чужой первичный), составной (несколько колонок вместе: товар + неделя).
- **Один-ко-многим раздувает строки:** отель × 3 отзыва = 3 строки отеля. Посчитать потом среднее по отелям «в лоб» — отели с большим числом отзывов весят больше.
- Четыре типичные беды: неожиданное число строк; **тихая потеря** при inner (ключи с опечаткой/другим форматом); одинаковые имена колонок (`name_x`, `name_y`) — переименовать или взять только нужные; **разный тип ключа** (1 ≠ "1") — совпадений ноль.
- Сессия 3 проекта: «Не начинайте анализ, пока у вас нет джойна, которому вы доверяете». Решения, которые надо **записать до склейки** (`PANEL.md`): единица наблюдения (одна строка = что?), индекс времени, единый чистый идентификатор для всех таблиц, дата события, окно «до/после», **политика пропусков** (неделя без данных: выкинуть, поставить 0 или протянуть прошлое значение). Правильного ответа нет — но выбрать один и защищать.

### 2.6. Неделя 5 и сессия 2 — оценка текстов LLM-ом
- Четыре способа оценить тон: готовый словарь (VADER — дёшево, прозрачно, не знает предметной области), свой словарь предметной области («clinical» в футболе — похвала), ML-модель (BERT), LLM через API (лучше всех понимает контекст, но стоит токенов и менее прозрачна).
- Порядок работы: **сначала оценить вручную** (5 текстов, шкала −2…+2), потом ИИ простым и подробным промптом, сравнить рассуждения.
- Правила шкалы из курса: смешанный тон без явного перевеса → 0; **не уверен → 0**; сильные слова тянут к краям (±2).
- **Проверка до масштаба:** вручную разметить ~20 текстов (в слайдах для серьёзного решения — **30–50**), прогнать промпт, сравнить. Цель — **≥ 80% совпадений**; ниже — править промпт, а не гнать весь массив.
- **Структурированный ответ** (schema): заранее заданные поля и допустимые значения, API заставляет ответ им соответствовать. Набор полей из курса: `score`, `reason`, `is_relevant` (+ `confidence`); в слайдах: `p_sack_4w`, `evidence_for`, `evidence_against`, `is_relevant`, `confidence`. Метки — перечислением (`Literal["positive","neutral","negative"]`), короткие поля, не эссе. Флаг `is_relevant` в том же вызове дешевле отдельного фильтра.
- **Три искажения, когда LLM выдаёт число** (слайды «LLM Scoring»):
  1. **Сжатие к середине** — обученная «осторожность» прячет крайние значения (ниже 0.05 и выше 0.70), пока явно не разрешишь всю шкалу.
  2. **Перевес тона** — модель реагирует на тон текста, а не на реальную ситуацию (бодрая цитата тренера снизила оценку, хотя положение плохое).
  3. **Невидимый контекст** — модель знает только то, что в тексте; место в таблице, история, деньги — невидимы, если не дать их в промпте.
- **Шесть стратегий промпта для оценки:**

| Стратегия | Суть | Плюс / минус |
|---|---|---|
| Грубая | «Оцени 0–1 вероятность X» | быстро / шумно, плохо откалибровано |
| С якорями | «Одни тексты — кризис (≈1), другие — стабильность (≈0). Оцени этот» | ровнее между текстами |
| JSON по шаблону | поля с доводами за/против, `is_relevant`, `confidence` | читается машиной, заставляет приводить доводы; **база конвейера** |
| Сначала рассуждение, потом число | абзац анализа → число | +5–15% точности / дороже |
| Самосогласованность | тот же промпт 5–10 раз при temperature 0.7, взять среднее | меньше шума; **разброс сам = мера неоднозначности** / больше вызовов |
| По вероятностям токенов | ответ только LOW/MEDIUM/HIGH, читать logprobs | честнее калибровка / нужен доступ к logprobs |

- Решения, которые надо записать в `prompt_classifier.md`: temperature (0 — воспроизводимо; 0.7 — только вместе с самосогласованностью), сколько размечать вручную, формат (JSON — для проверяемости), модель (дорогая против дешёвой), как сводить по текстам (среднее по умолчанию; **максимум ловит пик сигнала**), окно времени.
- **Калибровка** (бонус-задание): правда ли, что оценка 0.20 сбывается в ~20% случаев? 30 событий + 30 контрольных недель, кривая «предсказано → случилось», Brier score (средний квадрат ошибки вероятности).
- **Модель:** брать **самую маленькую, что проходит проверку на ваших данных** (20–50 реальных примеров). Сравнить две модели на одной выборке; похоже — оставить дешёвую.
- Привычки API-конвейера: промпт в одной переменной; сначала `head(5)`/`head(10)`; **сохранять частичные результаты по ходу**; логировать **имя модели и версию промпта**; повторы с паузой 1-2-4 с; ключ — только из переменной окружения; часть ответов проверить руками; ответ модели — не истина.
- Масштаб и цена: ~1 500 текстов — «пара долларов»; бюджет на проект — $5. Начинать с 1 источника, 1 сезона, 3 месяцев.
- Итог — две таблицы: **по одному тексту** (`news_uid`, объект, дата, score) и **сводная по (объект, неделя)** с `avg_score` и `n_articles` (сколько текстов дали среднее — без этого среднее из 1 текста выглядит так же весомо, как из 30). Единица времени («неделя») — выбор: записать и держать одинаковой.
- «Молчание» — тоже данные: смена, о которой не писали, — это не «ожидание 0», а **нет покрытия**.

### 2.7. Воспроизводимость (страница «Reproducible research» + `repro-toy-example`)
- Определение: **незнакомец клонирует папку, запускает одну команду и получает те же цифры, таблицы и графики.**
- Минимум: README (зачем, откуда данные, как запустить, где итог); закреплённые версии библиотек (`requirements.txt`); одна команда (`make all` / `python main.py` / `run.sh`), которая проходит «скачать → почистить → посчитать → отчёт»; папки `data/raw`, `data/clean`, `out`; CLAUDE.md.
- Правила из CLAUDE.md учебного репозитория (можно брать как есть):
  > «**Data is immutable.** Never edit a file in data/raw/ or data/clean/ in place. Write a new file.» — сырьё и промежуточное не правим, пишем новый файл.
  > «**Every script is idempotent.** Running it twice produces the same output.» — повторный запуск даёт тот же итог.
  > «**Every script prints what it's doing** and what file it wrote — no silent side effects.» — каждый скрипт пишет, что делает и какой файл записал.
  > «One script = one job.» «All outputs that humans read go to out/.»
- Ноутбуки — для разведки, не для итога: «run cell 7 before cell 4» убивает воспроизводимость.
- Последний пункт чек-листа: «склонировали в чистую папку и прогнали — получили то же». **Не делали — значит, не знаете, воспроизводимо ли.**
- Документация данных: на каждую таблицу — формат, число строк и колонок, **что такое одна строка**, период и охват, ключевые поля, пропуски (сколько и почему), путь «источник → обработка → итог». На переменную: имя, смысл, тип, единица, допустимый диапазон, коды категорий, коды пропусков, доля пропусков. ИИ хорошо делает черновик словаря, но **3–5 переменных сверить с источником руками**.

### 2.8. Графики и отчёт
- «ИИ дал *что-то*, а не *то, что я хотел*» — график доводится 4+ итерациями (подписи, доверительный интервал, сноска с N, цвета). На каждой итерации: код верный? что нравится/не нравится?
- Отчёт: вопрос → данные (источник, переменные) → метод → результат (один главный, объяснить его) → вывод 1–2 абзаца: причинно ли, переносится ли. Связь ≠ причина — писать «связано», а не «вызывает».
- Финальную презентацию проекта — **полностью проверяет человек**.

### 2.9. Неделя 4 (коротко — приёмы промпта, не эконометрика)
- **Помощник против критика:** сессия 1 предлагает список; **отдельная** сессия 2: «Argue, for each, why it should not be included»; критику вернуть в сессию 1: «Revise and give a final list».
- **Цепочка без подсказки ответа:** не называть термин, который хочешь получить (иначе модель выдаёт учебные шаблоны), а описать ситуацию и вести шагами: сначала «какие факторы определяют решение», потом «какие из них не связаны с помехами».
- Перед такими разговорами отключать память/историю чатов, чтобы модель рассуждала от задачи, а не от прошлых бесед.

**Шаблон безопасного merge для сверки PDD↔1688** (дополняет `pandas.md`, раздел 6):

```python
def key(s):  # один вид ключа в обеих таблицах
    return s.astype(str).str.strip().str.replace(r'\.0$', '', regex=True)

pdd['offerId'], otbor['offerId'] = key(pdd['offerId']), key(otbor['offerId'])
assert otbor['offerId'].is_unique, otbor[otbor['offerId'].duplicated(keep=False)]  # дубли — показать
n_left = len(pdd)
m = pdd.merge(otbor, on='offerId', how='left', indicator=True,
              validate='many_to_one',          # упадёт, если в «Отборе» ключ повторяется
              suffixes=('_pdd', '_1688'))
assert len(m) == n_left, f'строк было {n_left}, стало {len(m)} — раздулось'
print(m['_merge'].value_counts())               # сколько сошлось / нет
m[m['_merge'] == 'left_only'].to_excel('ne_soshlos.xlsx', index=False)  # сами строки, не число
```
(`validate` и проверка длины — мой перенос идеи курса «count rows before and after» на pandas; в курсе только печать длин.)
