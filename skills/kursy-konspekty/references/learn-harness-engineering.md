## 1. Что это за курс и для кого

Бесплатный курс «на проектах» про **harness** («обвязка, упряжь» — всё вокруг модели, кроме неё самой: инструкции, инструменты, среда, состояние, проверки). Главная мысль: сильная модель на настоящей работе всё равно проваливается, если обвязка плохая; чинить надо обвязку, а не покупать модель дороже. Пять частей обвязки: инструкции, состояние, проверка, границы задачи (scope), жизненный цикл сессии. В курсе 14 лекций и 8 проектов: на всех проектах растёт одно учебное приложение (база знаний на Electron — программа-окно для компьютера). Для тех, кто уже работает с кодовыми агентами (Claude Code, Codex) и хочет стабильности; не для тех, кому нужен «ИИ с нуля» или только промпты. (README сам путается: в одном месте «13 лекций и 7 проектов», в другом 14 и 8 — верно второе, оно совпадает с папками.)

## 2. Лекции

**1. Почему сильные агенты всё равно проваливаются.** Одна и та же модель (Opus 4.5) дала почти неработающее приложение с голой настройкой и куда более полное — с полной обвязкой. При сбое сначала ищи слабое место в обвязке, а не вини модель. Приём: пять слоёв для разбора причины — постановка задачи, подача контекста, среда запуска, обратная связь проверок, хранение состояния; вести журнал «задача — успех/провал — какой слой виноват» 3–5 кругов. «Definition of Done» (определение «готово») — условия, которые проверяются командой (пример: тест проходит, `mypy --strict` чист).

**2. Что такое harness на самом деле.** Обвязка = пять подсистем: инструкции (`AGENTS.md`/`CLAUDE.md`), инструменты, среда, состояние (`PROGRESS.md`, git), обратная связь (тесты, линтер — программа, ловящая огрехи в коде, сборка). Один файл с промптом — ещё не обвязка. Приём: «карта, а не мануал» — входной файл около 100 строк, детали в `docs/`. Пример курса (GPT-4o, приложение ~20 000 строк): только README — успех 20% запусков; +AGENTS.md — 60%; +команды проверки — 80%; +шаблон файла прогресса — 80–100%. Модель не менялась. Ещё: «долг обвязки» — она гниёт как код, её надо периодически ревизовать.

**3. Репозиторий — единственный источник правды.** Чего нет в репозитории (папке проекта), того для агента не существует: чат, Jira, головы людей ему не видны. Приём: «тест свежей сессии» — новая сессия, имея только папку, должна ответить: что это, как устроено, как запустить, как проверить, где мы сейчас. Целевой разрыв «знаю, но не записано» — меньше 10%. Состояние агента по аналогии с базами данных (ACID): фиксировать только проверенное (атомарность), проверять после каждого шага (согласованность), у параллельных агентов свои файлы/ветки (изоляция), знания — в файлах, не в памяти сессии (долговечность).

**4. Почему один гигантский файл инструкций не работает.** Раздутый файл съедает окно контекста (600 строк — 8–15% окна на 128K), а «потерянное в середине» модель слушает хуже, чем начало и конец. Приём: входной файл 50–200 строк (до 15 жёстких правил, команды первого запуска, ссылки на темы с условием «когда читать»), темы по 50–150 строк; каждое правило с пометкой источник / когда применять / когда удалить. Упражнение: «аудит шума» — доля инструкций, нужных именно этой задаче. Честная оговорка курса: исследование ETH Zurich нашло, что файлы контекста не всегда повышают успех и дорожают более чем на 20%.

**5. Почему длинные задачи теряют связность.** Окно конечно, задача переходит в следующую сессию; сжатие сохраняет «что», но теряет «почему». Модель при нехватке места начинает торопиться («context anxiety», тревога контекста). Приём: файлы состояния — `PROGRESS.md` (текущее состояние, сделано, в работе, известные проблемы, дальше), `DECISIONS.md` (дата, решение, причина, отвергнутая альтернатива), коммит после каждого законченного куска; «приход на смену» (прочитать прогресс, прогнать проверку) и «уход со смены» (обновить, проверить, закоммитить). Если задача займёт больше 60% окна — готовь передачу заранее. У Sonnet 4.5 тревога была сильной (нужен перезапуск сессии), у Opus 4.5 слабой.

**6. Почему инициализации нужна отдельная фаза.** Если смешать подготовку и работу над функциями, агент любит видимый код и экономит на фундаменте. Приём: сессия 1 делает только инфраструктуру: запускаемая среда, хотя бы один проходящий тест, чек-лист готовности к старту, разбивка задач с критериями приёмки, чистый коммит. Метрика — время до первого проходящего теста. Пример: пересборка понимания во 2-й сессии 20 минут против 3 минут; окупается за 3–4 сессии.

**7. Почему агенты хватаются за много и не доделывают.** Пять функций начато — ни одна не проходит проверку. Приём: WIP=1 (в работе одна задача; термин из канбана — «доски задач»), у каждой функции своя команда проверки, список областей работы лежит файлом в репозитории (состояния not_started / active / blocked / passing), считать VCR (проверенных / начатых) и не начинать новое, пока VCR < 1. Пример (REST API, 8 функций): без ограничений 37,5% готово, с WIP=1 — 87,5%.

**8. Почему список функций — «кирпич» обвязки.** Список функций — не заметка человеку, а машинный файл (`feature_list.json`), который читают планировщик, проверяющий и отчёт передачи. У каждого пункта тройка: описание поведения + команда проверки + состояние. Состояние в `passing` переводит только успешная проверка, агенту нельзя править его руками. Размер пункта — «выполнимо за одну сессию» («пользователь добавляет товар в корзину» — ок; «сделать корзину» — слишком широко). Пример: новая сессия поняла состояние за 3 минуты вместо 20 и не переделывала готовое.

**9. Почему агенты объявляют победу слишком рано.** Агент систематически самоуверен; «готово» должна решать обвязка. Приём: три слоя проверки — статический разбор, запуск (тесты, старт, ключевые пути), сквозной сценарий; порядок: сначала работает, потом быстро, потом красиво. Работник и независимый строгий оценщик — разные роли. Сообщения об ошибках должны говорить, что сломалось и что чинить. Пример Anthropic: один агент 20 минут и $9 — основное не работает; три агента 6 часов и $200 — игра в основном работает.

**10. Почему сквозные (end-to-end) тесты меняют результат.** Юнит-тесты проверяют части по отдельности и пропускают сбои на стыках. Агент гонит только самые быстрые тесты и объявляет конец. Приём: иерархия проверок — если пропущен обязательный уровень, задача «не завершена»; правила архитектуры как проверки (запрет «слой А лезет в слой Б» одним grep); сообщение об ошибке из трёх частей ERROR / WHY / FIX; повторяющиеся замечания ревью превращать в автоматическую проверку. Пример: юнит-тесты прошли, сквозные поймали 5 дефектов, которые юнит не поймал ни одного.

**11. Почему наблюдаемость — внутри обвязки.** Без сигналов о том, что система делала, агент слепой: решения вслепую, оценка на глаз, повторы наугад. Два слоя: сигналы времени работы (логи, события, проверки здоровья, трассы) и артефакты процесса (план, рубрика оценки, критерии приёмки). Приём: «контракт спринта» до кода — Объём / Стандарты проверки / Исключения; рубрика оценщика оценками A–D. Пример: без наблюдаемости 45 минут и 3–4 переделки, с ней 15 минут и одна итерация (оценщик назвал измеренный контраст 2,1:1 против нормы 4,5:1).

**12. Почему каждая сессия оставляет чистое состояние.** Следующая сессия наследует весь беспорядок, а агент копирует и плохие образцы — энтропия растёт. «Чисто» = сборка проходит, тесты проходят, прогресс записан, нет мусора, путь запуска работает. Приём: чек-лист выхода в CLAUDE.md (сборка, тесты, список функций, нет отладочного кода, старт работает); уборка двух видов — в конце каждой сессии и периодическая целиком; «документ качества» с оценкой модулей — чинить худший первым; раз в месяц отключать один элемент обвязки и смотреть, нужен ли он ещё. Пример за 12 недель: без уборки сборка проходит в 68% случаев, с уборкой 97%.

**13. От ручных промптов к автономным циклам (loop engineering).** Запуск работы агента переходит от тебя, печатающей каждый промпт, к системе, которую ты спроектировала. Цикл = цель + способ проверки + условие остановки (проверяемое машиной, не «вроде достаточно»). `/goal` — цикл до достижения состояния; `/loop` — повтор действия по таймеру. Автор и проверяющий — разные агенты («кто-то в команде не должен тебе верить»); память — на диске, потому что модель между запусками забывает. Чек-лист первого цикла: взять дело, которое делаешь руками хотя бы 2 раза в неделю; цель и стоп, проверяемые машиной; разделить «делает» и «проверяет»; файл-память; таймер раз в сутки и наблюдать неделю. Предупреждение: цикл ускоряет и результат, и риск; четыре тихие цены — долг проверки, потеря понимания, «сдача» мышления, взрыв токенов.

**14. От одного цикла к графу (graph engineering).** Граф — несколько агентов, циклов, инструментов и кода как узлы со связями, общим состоянием и правилами маршрута. Единичный цикл прячет сбои внутри одного контекста; граф делает их видимыми. Три сбоя одного цикла: метрика растёт, а дело ухудшается (закон Гудхарта), цикл не ставит под сомнение цель, независимые циклы мешают друг другу. Приём: рисовать граф, только если выполнено хотя бы 3 из 5: работа делится независимо, есть ветки/откаты, промежуточное состояние стоит сохранять, результат проверяем, польза от координации больше затрат. Узел проверки получает свежий контекст, чтобы не наследовать рассуждения исполнителя. Предостережение: добавить узлы легко, а проверять результаты всё равно ты, последовательно («ты — GIL своих агентов»). Курс отмечает, что часть вирусных цифр (+18% точности, −85% стоимости) сравнивает разные базы и ненадёжна.

## 3. Проекты (8)

Все — на одном приложении (Electron + TypeScript, база знаний), делаются с Claude Code или Codex.

1. **P01 Baseline vs minimal harness.** Один и тот же заказ дважды: только промпт и с минимальной обвязкой (`AGENTS.md`, `init.sh`, `feature_list.json`). Меряют завершённость, время до первого запуска, число ручных повторов, преждевременные остановки. Тренируется: правила и критерии проверки, контролируемое сравнение. Итог — записи прогонов и заметка на 1–2 страницы.
2. **P02 Agent-readable workspace.** Сделать репозиторий читаемым для новой сессии: импорт документов, просмотр, сохранение между сессиями. Первый прогон на тонкой заготовке, второй — с документами об архитектуре и передаче сессии. Меряют, сколько нужно «заново открывать» и может ли свежая сессия продолжить только по репозиторию.
3. **P03 Multi-session continuity.** Контроль объёма и ворота проверки при работе через перезапуски сессий: нарезка документа на куски, метаданные, статус индексации, ответы с цитатами. Одна функция за раз в `feature_list.json`, «passing» только после проверки; журнал прогресса и передача сессии.
4. **P04 Incremental indexing.** Обратная связь времени работы: логи старта и индексации, состояния ошибок, правила границ слоёв. Сравнение заготовки со слабой диагностикой и намеренно посеянной ошибкой (большие файлы) и решения с логгером и проверкой границ; меряют, насколько быстрее агент находит причину. Итог — логи, правила границ, исправление, чек-лист чистого состояния.
5. **P05 Grounded Q&A verification.** Разделение ролей: исполнитель, оценщик, по желанию планировщик. Три варианта на одной задаче (история диалога в Q&A): одна роль / исполнитель+оценщик / планировщик+исполнитель+оценщик. Практика: самопроверка, доказательное завершение, рубрики оценки, контракт спринта.
6. **P06 Runtime observability and debugging (капстоун).** Собрать всё из предыдущих проектов в полную обвязку для куска продукта (импорт, индексация, Q&A с цитатами, наблюдаемость, перезапускаемое состояние). Тот же набор задач три раза: слабая база, сильная обвязка, после уборки; потом «абляция» — убирать по одному элементу и смотреть, что реально важно. (Страница описана так, как вернулась при чтении; название проекта и содержание на сайте частично расходятся.)
7. **P07 Loop engineering: first loop.** Три опыта: `/goal` на выбранной задаче, `/loop` по таймеру для мониторинга, цикл «делает + проверяет». Практика: цель с проверкой и стопом, файлы состояния, наблюдение долгих циклов. Итог — `goal.md`, лог двухчасового мониторинга, `loop-state.md` минимум за 5 кругов, итог «какие задачи подходят под цикл».
8. **P08 Graph engineering: first graph.** Превратить цикл «делает + проверяет» в явный граф (узлы, связи, общее состояние, правила маршрута). Три опыта на отдельных ветках: нарисовать граф; параллельные узлы через git worktree (отдельные рабочие копии ветки); условный откат и узел одобрения человеком. Итог — `graph.md`, список неявных связей, записи параллельных запусков, итоговое «каким задачам нужен граф».

## 4. Что применяем у нас

Сверка с существующими заметками: `vercel-agent-harness.md` (там уже есть: описание инструментов, «блокировка возвращает текст», отчёт «запустила/заблокировано», «мои ошибки ≠ старые», разведчик/исполнитель, один пункт «в работе», потолки вывода, прогрессивное раскрытие скиллов, JSONL-телеметрия, ревьюер ≤2 повторов) и `agents\proverka.md`.

1. **Проверяльщик `proverka` — «готово» решает не автор.** Лекции 9, 13: самоуверенность агента — системная, оценщик отдельный и строгий, с свежим контекстом (граф, узел проверки). **Уже есть у нас**: `proverka` не видит рассуждений автора, только читает, выносит вердикт по каждому утверждению. Новое из курса: добавить в запрос ему «рубрику» — оценка A–D по пунктам («что лежит», «цифры», «открывается») и «контракт» (Объём / Стандарты проверки / Исключения), написанный ДО работы, вместе с «готово». Тогда проверка идёт по заранее оговорённому, а не по отчёту.
2. **Каждая функция/шаг долгого сбора — запись «поведение + команда проверки + состояние», и `passing` ставит проверка, а не агент.** Лекция 8. Для сборщиков (tg_monitor, 1688, радар): файл-чеклист с тройкой на каждый шаг («собрано N каналов — команда подсчёта — passing»). **Частично есть**: наше правило «чеклист шагов отдельным файлом» и «N из M»; нет жёсткого правила «статус меняет только прогон проверки» и поля `evidence` (путь к логу/коммиту). Добавить.
3. **Файл прогресса и передачи (`PROGRESS` + `DECISIONS`, «приход/уход со смены»).** Лекция 5. Для долгих сборов 1688 и разборов: отдельно «что сделано», «что в работе», «почему выбрали так, а не иначе». **Частично есть** (память, табло agent_status, «споки» = сохранить всё). Нового: журнал решений «отвергнутая альтернатива + причина» и порог «задача заняла больше 60% окна — готовить передачу заранее» (у нас лимит 70% — остановка; курс советует раньше).
4. **Короткий входной файл + темы по требованию, правила с датой и сроком.** Лекции 3, 4. Скиллы и CLAUDE.md: входной файл 50–200 строк, не более ~15 жёстких правил, каждое правило — источник / когда применяется / когда убрать. **Частично есть** (прогрессивное раскрытие скиллов, `references/`, даты в правилах CLAUDE.md). Нового: пометка «когда убрать» и «аудит шума» (какая доля правил относится к этой задаче). Ради честности — у нашего общего CLAUDE.md уже много строк; кандидат на разбиение, предлагать ей, самой не переписывать.
5. **Определение «готово» с командой + чек-лист выхода из сессии.** Лекции 1, 9, 12. В начале задачи писать «готово = что лежит где, чем проверено» (**уже есть** в её CLAUDE.md). Добавить в конец долгих задач чек-лист чистого состояния: временные файлы убраны, табло закрыто (`done`), «Мои дела» сверены, итог записан. Сверка «Моих дел» **уже есть**; общий «чек-лист выхода» — нет.
