## Event-driven архитектура (EDA)
- **Синхронно**: сервис вызвал другой и ждёт ответ. Минусы: если сосед лежит — ждём/повторяем, ресурсы тратятся, сбой по цепочке A→B→C→D; клиент обязан знать адрес и API соседа.
- **Асинхронно** = отправил и пошёл дальше (письмо в почтовый ящик). EDA к этому подталкивает.
- **Событие** (event) — сообщение «что-то значимое случилось», без адресата, с именем в прошедшем времени (`OrderCreated`, `TaskCreated`); может быть без данных — просто сигнал. Каждое событие — сообщение, но не каждое сообщение — событие.
- Плюсы: (1) смена направленности — новый сервис просто подписывается на события, чужой код не меняем; (2) слабая связанность — API сервиса = набор событий, которые он выпускает; (3) надёжность — не ждём ответа, работает при падении части системы; (4) разделение чтения/записи (CQRS) — масштабируем отдельно, чтение идёт из своей локальной копии (реплика из событий, работает даже когда другие сервисы лежат).
- **Брокер сообщений** (Message Broker) — отдельная программа-«почта»: хранит на диске, гарантирует доставку (иногда «ровно один раз»), порядок, кластер из нескольких серверов, копии данных.
- Риск: локальные копии могут разойтись с «мастер»-данными → продумывать согласованность и обработку ошибок.

## Domain-Driven Design (DDD)
- Не один метод, а набор практик: код выражает предметную область (бизнес) её же словами; бизнес и разработчики говорят на одном языке.
- **Домен** — область бизнеса; **поддомен** — её части (бухгалтерия, юристы, маршруты…), у каждой своя специфика.
- **Ubiquitous Language** («вездесущий язык») — словарь терминов ОДНОГО поддомена, составляют вместе с экспертами. Как собирать: спрашивать, рисовать схемы (предметы, действия, направление), вести словарь, фиксировать синонимы и одинаковые слова с разным смыслом. Пример: «медсестра вводит вакцину пациенту» → в коде `nurse.administer(flu_vaccine, patient)`, а не `patient.vaccinate()`.
- **Bounded context** — граница, внутри которой каждый термин значит одно. Два смысла у слова → два контекста («сотрудник» для бухгалтерии ≠ для IT). Идеал: 1 поддомен = 1 контекст; контекст — основа границ модулей/микросервисов.
- **Event Sourcing** — храним не текущее состояние, а ленту событий об изменениях; состояние восстанавливаем из них. Мощно, но высокий порог входа. Дальше в курсе: агрегаты, сущности, доменные события.
