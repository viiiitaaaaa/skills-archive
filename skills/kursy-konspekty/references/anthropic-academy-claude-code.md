## 2. Ключевые идеи простыми словами

### 2.1. Описание (description) скилла — по этим словам Claude решает, звать ли скилл
- При старте Claude загружает **только имя и описание** каждого скилла; полный SKILL.md — когда запрос совпал
  **по смыслу** (semantic matching, «сопоставление по смыслу», а не по точным словам).
- Хорошее описание отвечает на **два вопроса: что делает скилл и когда его звать.** Пример из курса:
  > `description: Writes pull request descriptions. Use when creating a PR, writing a PR, or when the user asks to summarize changes for a pull request.`
  > (что делает + «Use when …» + 2–3 формулировки, которыми человек реально просит)
- Лимиты: `name` — строчные буквы, цифры, дефис, до 64 знаков, совпадает с именем папки; `description` — **до 1024 знаков**.
- Не срабатывает → почти всегда виновато описание. Проверить вариациями фразы («ускорь», «почему тормозит», «сделай
  быстрее»); какая не сработала — добавить её слова в описание.
- Срабатывает **не тот** скилл → описания соседей слишком похожи, развести их. Имена давать конкретные
  («sales-customer-renewal-prep», а не «meeting-prep»).
- Правило выбора: **если одно и то же объясняешь Claude второй раз — это скилл.** Если одну многошаговую инструкцию
  набрала дважды — тоже скилл.

### 2.2. Устройство скилла
- Поля: `name`, `description` (обязательные); `allowed-tools` — **заранее разрешает** перечисленные инструменты без
  вопроса до конца текущего хода (следующее сообщение — разрешение снимается); **не ограничивает** остальные.
  Ограничить — отдельным полем `disallowed-tools`. `Bash` целиком разрешать только в доверенном скилле, лучше узко:
  `Bash(git status *)`. `model` — какой моделью выполнять.
- **Прогрессивное раскрытие** (progressive disclosure): SKILL.md **до 500 строк**, подробности — в `references/`,
  код — в `scripts/`, шаблоны/картинки — в `assets/`. В SKILL.md писать, **когда** открывать файл («читай
  architecture-guide.md, только если спрашивают про устройство системы»).
- **Скрипт запускать, а не читать:** в контекст попадает только его вывод. Прямо писать в SKILL.md «запусти
  scripts/x.py», а не «посмотри скрипт». Скрипты — для повторяемых расчётов и проверок, где код надёжнее генерации.
- Четыре вида файлов (по Cowork): инструкции (SKILL.md как «регламент для нового сотрудника»), assets (логотипы,
  шаблоны), **references — примеры хорошего результата** («как выглядит “хорошо”»), scripts.
- Приоритет при одинаковых именах: Enterprise → личные (`~/.claude/skills`) → проектные (`.claude/skills`) → плагины.
- Не загружается: SKILL.md должен лежать **в своей папке**, имя файла ровно `SKILL.md`; ошибки видны в `claude --debug`.
  Сбой при запуске: зависимости, права на скрипт, **в путях — прямые слэши `/` даже в Windows**. После правки скилла
  курс советует перезапустить Claude Code.

### 2.3. Субагенты — как писать и когда звать
- Субагент получает **свой системный промпт** (тело файла `.claude/agents/<имя>.md`, у нас личные — `~/.claude/agents/`)
  и **задание, которое пишет главный агент**. Работает в отдельном контексте, назад приходит только итог; всё
  промежуточное выбрасывается. Плата — не видно, как он пришёл к выводу.
- Встроенные: general-purpose (искать + делать), Explore (быстрый поиск), Plan (исследование для режима плана).
- Поля файла: `name`, `description` (**одна строка**, переносы — `\n`; можно вписать примеры диалогов), `tools`,
  `model` (haiku — быстро и просто, sonnet — середина, opus — сложный анализ, inherit — как у главного), `color`,
  `skills`. Чтобы звался сам — слово **«proactively»** в описании.
- **Описание работает дважды:** (1) по нему главный агент решает, кого звать; (2) **по нему же главный пишет задание.**
  Если вписать в описание «You must tell the agent precisely which files you want it to review», главный начнёт
  перечислять файлы в задании. Для поиска в вебе: «return sources that can be cited» — и главный попросит источники.
- **Формат вывода — самое важное улучшение.** Он даёт точку остановки (заполнил все разделы — готово) и не даёт
  агенту исследовать бесконечно. Образец из курса для ревьюера:
  > Summary · Critical Issues · Major Issues · Minor Issues · Recommendations · Approval Status
  > (итог · критичное · серьёзное · мелочи · советы · «готово к выпуску или нет»)
- **Раздел «Obstacles Encountered»** («с чем столкнулся») — чтобы главный не открывал заново найденные обходы:
  > Obstacles Encountered: Report any obstacles encountered… setup issues, workarounds discovered or environment quirks.
  > Report commands that needed a special flag or configuration. Report dependencies or imports that caused problems.
  > (проблемы окружения, найденные обходы, команды с особыми флагами, сломанные зависимости/импорты)
- **Ограничение инструментов:** исследователь — только `Glob, Grep, Read` (ничего не сломает); ревьюер — плюс `Bash`
  (git diff), без `Edit/Write`; «правщик» — с `Edit/Write`. Меньше инструментов = нет побочных эффектов и роль понятнее.
- **Когда звать (правило одного вопроса): важен ли промежуточный путь?** Нет, нужен только итог → субагент. Да,
  каждый шаг зависит от предыдущего → в главном потоке. Хорошо: исследование, ревью, задачи с особым тоном
  (копирайтинг — у Claude Code по умолчанию сухой технический стиль), стилист с подгруженной дизайн-системой.
- **Ревью — только «чужими глазами»:** код, написанный в этой же сессии, Claude ревьюит слабо. Субагент или новая
  сессия без истории ловит то, что автор «оправдал себе».
- **Три антипаттерна:** (1) «ты эксперт по Python» — ничего не добавляет; (2) **конвейер** «воспроизведи → найди →
  почини» из разных агентов — теряется знание на передаче; (3) **субагент-запускатель тестов** — возвращает «тесты
  упали» без деталей; в замерах этот вариант оказался худшим.
- **Скиллы субагентам не передаются сами.** Встроенные агенты (Explore, Plan, Verify) скиллы не видят вообще; свой
  субагент — только перечисленные в поле `skills:`, и они грузятся **целиком при старте**, а не по требованию.

### 2.4. CLAUDE.md, которому подчиняются
- Это **подсказка, а не принудительная настройка**: каждая строка соперничает с остальными за внимание. **Чем короче,
  тем больше выполняется.** Строку, которую не можешь обосновать, — удалить.
- 4 места, грузятся все вместе: Managed (организация) · User (личный, `~/.claude/CLAUDE.md`) · Project (в репозитории)
  · Local (не в git, личные заметки к одному проекту).
- `@путь/файл.md` (импорт) — для порядка, но **контекст не экономит**: всё вставляется сразу при запуске.
- Формулировки: **конкретно и проверяемо** («новые API-маршруты — в src/api/handlers, по одному на файл», а не «следуй
  лучшим практикам»); **запрет + замена** («named exports, не default exports»); **акцент — бюджет**: «IMPORTANT / YOU
  MUST» только на 2–3 правила, иначе ничего не выделяется.
- Ошибку Claude считать **«багом в CLAUDE.md»**: попросить «добавь это в CLAUDE.md». Начинать проект **без** CLAUDE.md,
  смотреть, где приходится поправлять, потом `/init`.
- **Жёсткие правила — не в CLAUDE.md, а в хук.** «Никогда не пушь в main» в тексте выполняется «почти всегда»; хук
  блокирует всегда. Кто чем владеет: постоянные соглашения → CLAUDE.md; процедура под тип задачи → скилл; то, что
  нельзя пропустить → хук.

### 2.5. Хуки (hooks) — код, который срабатывает всегда
- Настраиваются в `settings.json` (или `/hooks`): событие + `matcher` (какие инструменты) + команда. Событий ~30, нужны:
  `PreToolUse` (до вызова — может запретить), `PostToolUse` (после — формат/линт), `Stop` (Claude хочет закончить —
  можно сказать «ещё не готово»; есть `SubagentStop`), `UserPromptSubmit`, `SessionStart`, `PreCompact/PostCompact`,
  `InstructionsLoaded` (что из CLAUDE.md реально загрузилось), `Notification`.
- **Коды выхода:** `0` — ок (JSON из stdout читается; на SessionStart/UserPromptSubmit простой текст добавляется в
  контекст); **`2` — блок**, stderr уходит Claude как объяснение; **любой другой, в т. ч. `1`, — НЕ блокирует.**
  PostToolUse блокировать поздно (инструмент уже отработал), но текст вернуть можно. Notification/SessionStart блок игнорируют.
- PreToolUse может вернуть JSON: `hookSpecificOutput.permissionDecision` = `allow | deny | ask` (+ `defer` для `-p`),
  `permissionDecisionReason`, и **`updatedInput` — переписать команду** (например, заменить секрет `sk_live_…` на
  заглушку и всё равно выполнить). `updatedInput` заменяет ввод целиком — неизменённые поля вернуть тоже.
- **После сжатия контекста вернуть память — хук `SessionStart` с matcher `compact`** (а не PostCompact): печатает
  короткую сводку «над чем работали» — она попадает обратно в разговор.
- Связка для работы без присмотра: auto-режим проверяет **намерение** (опасно ли действие), а `Stop`-хук с тестами —
  **правильность** (работает ли результат). Скрипты проекта адресовать через `$CLAUDE_PROJECT_DIR`.

### 2.6. Режимы, контекст, долгие сессии
- 6 режимов: Manual · Accept edits · Plan · **Auto** (отдельная модель-классификатор проверяет каждое действие: блокирует
  деплой в прод, force push, `curl | sh`, отправку чувствительных данных наружу, удаление файлов, которые были до
  сессии) · **Don't ask** (только заранее разрешённое, остальное молча отклоняется — для ночных/плановых запусков) ·
  Bypass (без проверок — только в изолированной VM). Классификатор **не проверяет, правилен ли код.**
- `/compact <на чём сосредоточиться>` — указание после команды задаёт, что сохранит сводка. `/clear` — новая задача
  без «хвостов». `/context` — что съедает контекст. Esc Esc → **rewind**: откатить код/разговор/оба, «сжать отсюда» или
  «сжать до сюда». Откат не возвращает то, что изменили shell-команды (например, установки пакетов).
- `/goal <проверяемое условие>` — Claude работает, пока условие не выполнено; судья читает **только переписку**, поэтому
  условие должно быть видно в выводе (результат теста, число). `/loop` — повтор по интервалу. Worktrees — каждой
  параллельной сессии своя копия файлов.
- Ревью своих правок: `/diff`, затем `/code-review` (чистый контекст, сам ничего не правит). Смотреть: **правки, о
  которых не просили; ослабленные тесты; новые пакеты и зашитые в код ключи/URL.** Каждую находку — в одну из кучек:
  **чинить сейчас / спросить «почему» / оставить**; к каждой починке просить доказательство («запусти и покажи вывод»).
- Проверка без присмотра: **чем меньше смотрела — тем строже проверка.** Начинать с diff, а не с красивой сводки
  («аккуратный отчёт ≠ аккуратный результат»); тесты — «воротами» (хук), а не обещанием; холодное второе мнение.
- Headless: `claude -p "…"` — одна команда без интерфейса; **не подгружает хуки, скиллы, плагины, MCP и CLAUDE.md**;
  `--output-format json --json-schema '{…}'` → объект в поле `structured_output`; `--resume <session_id>` — продолжить.
  Routines (`/schedule`, claude.ai/code/routines) — промпт + репозиторий + коннекторы по cron/HTTP/GitHub, не чаще раза
  в час, research preview.

### 2.7. MCP — tools, resources, prompts
- MCP переносит описание и выполнение инструментов на отдельный сервер; MCP ≠ tool use (tool use — как Claude
  вызывает, MCP — кто уже написал инструменты). Транспорт любой: stdio (локально), HTTP, WebSocket. Сообщения:
  `ListTools`/`CallTool`, `ReadResource`, `ListPrompts`/`GetPrompt`.
- **Три примитива и кто ими управляет:** **tools — модель** (Claude сам решает вызвать) · **resources — приложение**
  (данные только на чтение, как GET: список для автодополнения `@`, вставка документа в промпт без вызова инструмента;
  прямые `docs://documents` и шаблонные `docs://documents/{doc_id}`, с `mime_type`) · **prompts — пользователь**
  (готовые проверенные промпты, появляются как команды `/format`).
- Python SDK: `FastMCP("Имя")`, `@mcp.tool(name=…, description=…)`, параметры с `Field(description="…")` —
  схема собирается сама; ошибки — обычным `raise ValueError`. Описание параметра пишется для модели:
  «The text to replace. Must match exactly, including whitespace.» Проверка без приложения — `mcp dev server.py`
  (инспектор в браузере, http://127.0.0.1:6274).
- **Цена в контексте:** MCP-сервер держит описания всех своих инструментов в контексте, даже неиспользуемых. Если у
  инструмента есть CLI (`gh`, `aws`) — CLI дешевле. MCP > 10 % контекста → Claude Code включает поиск инструментов
  (tool search), он «может работать менее надёжно». Ненужные серверы — выключать в `/mcp`. Области: local / user /
  project (`.mcp.json` в репозитории).

### 2.8. Cowork — Claude Code «для остальной работы»
- **Чат — думать с Claude; Cowork — поручать Claude; Code — строить софт.** Cowork: папка (чтение и запись), коннекторы
  (Gmail, Drive, Slack…; многие только чтение/поиск), Chrome для сайтов без коннектора (входить в сайт сам человек).
- Разрешения: «Ask before acting» (по умолчанию: спрашивает перед отправкой, публикацией, «поделиться») и «Act without
  asking». **Безвозвратное удаление спрашивает всегда.** Задача с телефона/веба видит коннекторы, но не локальные папки.
- Хорошее поручение = **итог (формат, объём) + входы (папка, каналы, даты) + нюансы, которых Claude не знает**
  («базовый, лучший и худший сценарий с учётом 3 новых точек»). Уточняющие вопросы — не помеха, а закрытие пробелов.
  Сбился — поправить на ходу, а не ждать конца. Проверка итога: та ли цель; цифры — попросить список источников и
  сверить; дата/имя/цитата без источника — «флажок, а не фича».
- 4 слоя памяти: глобальные инструкции (кто я, сокращения, формат ответа) → проекты (инструкции + папки + расписание
  + память, которую Claude копит сам) → скиллы → плагины (набор скиллов + коннекторы + субагенты вокруг одной работы:
  «весь процесс» или «самые нужные скиллы команды»).
- Безопасность: **отдельная рабочая папка**, не «Документы/Загрузки»; копия незаменимого вне досягаемости; новый
  процесс — сначала **на копии**; **точные «разрушительные» глаголы** («убери раздел из черновика, файл оставь»;
  «добавь приложение, существующие разделы не переписывай»); границы в промпте («только 3 последних файла», «никому
  не пиши — только черновик»); задачи по расписанию сначала — **только черновики**; читать план и окна подтверждения.
- **Проверка скилла (evals) через skill-creator:** 2+ реалистичных запроса, на каждый пара ответов **со скиллом и без**;
  отзыв простыми словами («слишком официально», «пропустил резюме»), а не «не то». **Менять по одному**, 1–2 круга.
  Планка — нужные случаи заметно лучше, чем без скилла, а неподдерживаемые случаи **названы**.
- Общий плагин: один владелец; evals перед каждой публикацией; конкретные имена; пересмотр раз в квартал (что не
  используют — убрать).

### 2.9. Плагины (Claude Code)
- Плагин = скиллы + субагенты + хуки + MCP (+ немного settings.json) одной установкой; манифест
  `.claude-plugin/plugin.json` (обязательно только `name`), скиллы зовутся `/плагин:скилл`.
- **Читать до установки:** плагин работает с нашими правами, его хуки **складываются** с нашими и срабатывают на каждом
  вызове; ключ `agent` в его settings.json может подменить главного агента.

## 4. Не для нас / пропущено

- GitHub Actions, managed Code Review, worktrees, Agent SDK, `--bare` — для команд разработчиков с репозиториями и CI;
  у нас один человек и скрипты, нужно разве что `/code-review` локально.
- Enterprise managed settings, приватный маркетплейс плагинов, Claude для Microsoft 365, Compliance API — у неё нет
  организации и Office-процессов; из Cowork берём только принципы поручения и безопасности.
- Код MCP-клиента (`ClientSession`, `list_tools`/`call_tool`) — нам не писать клиента: Claude Code уже клиент.
