# Hur–Song: сборка ИИ-агента с нуля (черновик)

Как читать: «Если хочу X — шаги — (стр. N)». Всё взято из конспектов `knigi_kupleno\glubokiy\build_ai_agent_01..13.md`. Что добавлено не из конспекта — помечено «(не из конспекта)». Расшифровки терминов даны в скобках.

## Главная формула книги
- Агент = модель + обвязка (harness: память, инструменты, рабочая среда, безопасность) (стр. 36).
- LLM-агент = LLM (мозг) + инструмент (действия) + цикл (стр. 25–27).
- Контекст-инжиниринг (умно решать, что именно модель «видит») — часть обвязки (стр. 36).

## Часть 1. Что такое агент (гл. 1, стр. 1–40)

**Если хочу понять, нужен ли агент — шаги:** 1) нужен ли LLM: неструктурированные данные или непредсказуемые входы — да; обычный код справляется — LLM не нужен (стр. 30–31). 2) нужен ли агент: нужны инструменты, многошаговое рассуждение, цена LLM-запросов приемлема (стр. 30–31). 3) три условия: сложность (шагов заранее неизвестно), ценность результата покрывает расходы, ошибки не критичны/видны (стр. 31). Пример «агент не нужен»: «Кто президент Франции?» (стр. 31–32).

**Если хочу выбрать «workflow или агент» — шаги:** workflow = порядок задал разработчик (один вызов LLM, цепочка, роутер); агент = LLM сам решает шаги (стр. 28–30). Лучше смешивать: агент только в узле, где нужна гибкость; плюсы — проще, дешевле, есть запасной путь (стр. 30). Предупреждение: без лимита вызовов цикл дорогой и бесконечный (стр. 29–30).

**Если хочу тренироваться и мерить прогресс — шаги:** взять набор GAIA (вопросы с проверяемым ответом); цикл: прототип, смотреть сбои, разбирать причину, улучшать (стр. 32–33). Каждый шаг книги проверяется на GAIA (стр. 37).

**Если агент ошибается — диагностика:** 1) хватало ли «ума» модели; 2) был ли нужный факт в контексте. Главная причина реальных провалов — нехватка информации в контексте; менять модель при плохом контексте бессмысленно (стр. 33).

**Если хочу управлять контекстом — пять стратегий (стр. 35–36):**
- Generate (LLM пишет план/рефлексию в контекст) — гл. 7.
- Retrieve (принести внешнее: поиск, БД, файлы) — гл. 3, 5, 6.
- Write (сохранить вне контекста: память, файлы) — гл. 6, 8.
- Reduce (сжать: суммаризация, удаление) — гл. 6.
- Isolate (разделить среды: песочница, отдельные агенты) — гл. 8, 9.
- Предупреждения: длинный контекст не всегда лучше («контекст-рот» — качество падает; «потеря в середине») (стр. 34–36). Вместо целого PDF брать ключевые абзацы (стр. 34–35, пример).
- Дорожная карта книги: цикл (гл. 2–4), поиск (5), память (6), планирование (7), рабочая среда и навыки (8), много агентов (9), оценка (10) (стр. 37–38).

**Если хочу начать практику — требования:** Python (переменные, циклы, функции, классы), Python 3.12+, uv или pip, ключи OpenAI, Tavily, при необходимости Hugging Face; бюджет упражнений < 10 USD, Tavily бесплатно до 1000 запросов в месяц (стр. 38–39). Конспект расходится: гл. 1 помечена «стр. 1–30», а подраздел 1.1 «стр. 23» — номер сомнителен.

## Часть 2. Мозг агента — LLM (гл. 2, стр. 40–64)

**Если выбираю модель — шаги:** 1) сначала закрытая модель (OpenAI, Anthropic, Gemini): быстро проверить идею, готовые функции tool calling, structured output, кэш (стр. 41–42). 2) потом открытая (Llama, Mistral, Qwen, DeepSeek) ради цены и контроля; можно гибрид — сложное закрытой, простое открытой (стр. 41–42). 3) обязательно: tool calling (вызов функций), structured output (ответ по схеме JSON), длинный контекст (стр. 42–44). Книга берёт GPT-5 mini (стр. 44).

**Если хочу вызвать модель из кода — шаги:** окружение: клонировать репозиторий книги, `uv sync`, `uv run jupyter lab`, ключи в `.env` (стр. 44–45); вызов `client.chat.completions.create` с ролями system/user/assistant (стр. 45–46). Параметры: temperature 0–0,3 — предсказуемо, 0,7–1,0 — творчески (стр. 46). LiteLLM — единый вызов `completion` для разных провайдеров (стр. 46–47). API без памяти: историю хранить самому списком `messages` (стр. 47–48). Структурированный вывод — схема Pydantic в `response_format` (стр. 48–49). Много запросов сразу: `litellm.acompletion` + `asyncio.gather`, `num_retries`, `asyncio.Semaphore` (стр. 49–50).

**Если пишу системный промпт агента — правила (стр. 51–52):** задать личность, формат, ограничения, границы знаний. Автономность: если намерение ясно — действуй без подтверждения; вопрос — только при неясности; когда и какие инструменты звать — написать прямо; перечислить, в чём отказывать. Предупреждения: слабый промпт — агент блуждает; слишком длинный — детали игнорируются (стр. 52).

**Если хочу научить агента, когда звать инструмент — шаги (стр. 53–54):** 1) правило по умолчанию: «использовать проактивно, без разрешения»; быстро меняющееся (цены, новости) — искать сразу; медленно меняющееся — искать, если спрашивают про текущий статус. 2) список триггерных фраз («as I mentioned», «yesterday», «we decided», «my project»). 3) явно написать, когда НЕ искать (вечные факты, определения). 4) дать пары «запрос — действие — ответ», в том числе пример без инструмента (теорема Пифагора). Описание инструмента — полное: имя, описание, параметры, типы, ограничения (стр. 54–55).

**Если хочу измерить пользу инструментов — GAIA-опыт (стр. 55–64):** загрузить уровень 1 с Hugging Face (нужен `HF_TOKEN`) (стр. 55); ответ модели по схеме `GaiaOutput` (is_solvable, unsolvable_reason, final_answer) (стр. 56–57); лимиты по провайдеру через семафоры (пример: openai 30, anthropic 10, под свой тариф) (стр. 57–58); сравнение ответов без учёта регистра (стр. 59–60). Результаты без инструментов, из 20 вопросов: GPT-5 10, GPT-5-mini 4, Claude Sonnet 4.5 3, Claude Haiku 4.5 3 (стр. 62–63). Вывод: более 75 % даже простых задач нужны поиск/файлы/расчёт (стр. 63–64). Конспект в разных местах указывает «стр. 61–62» и «62–63» для запуска и результатов — границы приблизительны.

## Часть 3. Инструменты (гл. 3, стр. 64–98)

**Если хочу понять, зачем инструменты:** LLM не получает свежие данные, не действует во внешнем мире и не считает точно; типы: временные (поиск, новости), интерактивные (письма, бронь), функциональные (калькулятор, код) (стр. 64–67). Свои инструменты — полный контроль, но и поддержка на тебе; готовые провайдерские — быстро, но менее гибко (стр. 67–68). Свои полезны для отладки и уникальных функций (стр. 68–69).

**Если хочу вызвать инструмент через модель — цикл tool calling (стр. 69–74):** 1) отправить сообщение + описания инструментов; 2) модель решает и выдаёт `tool_calls`; 3) наш код выполняет функцию; 4) результат возвращаем сообщением роли `tool`; 5) модель пишет итоговый ответ. Для простого калькулятора ответ почти равен результату, для поиска нужен шаг синтеза (стр. 74). Модель этому обучена на данных «описание — вызов» (стр. 74–75).

**Если описываю инструмент — правила (стр. 75–77):**
- Чёткое имя и описание: `reserve_table` лучше, чем `book` (стр. 75).
- Не делать конфликтующих параметров: вместо `on`/`off` один `state` с `enum` [on, off] (стр. 76).
- Не заставлять модель передавать то, что код знает сам (например `order_id`) (стр. 77).
- Инструментов не больше ≈ 20; больше — риск ошибки выбора, тогда дообучение (стр. 77). В другой части сказано: при более чем 10 инструментах модель чаще ошибается (стр. 273) — цифры в конспектах расходятся; брать меньшую.

**Если хочу собственный веб-поиск — шаги (стр. 77–81):** Tavily (до 1000 запросов в мес бесплатно), ключ в `.env`, `uv add tavily-python`, функция `search_web(query, max_results=2)` (стр. 77–79); доп. параметры topic, time_range, country — больше параметров, тяжелее модели (стр. 79–80); ошибки — `try/except` с возвратом текста ошибки; для продакшена различать 401/429/таймаут (стр. 80–81).

**Если хочу автоматом получить описание инструмента из функции — шаги (стр. 81–84):** взять имя, docstring и сигнатуру через `inspect`; сопоставить типы Python и JSON (str→string, int→integer и т. д.); параметры без значения по умолчанию — в `required`. Предупреждение: без аннотаций тип считается string (стр. 84).

**Если хочу простой цикл агента — шаги (стр. 84–85):** `tool_execution` (по имени вызвать функцию из словаря), `simple_agent_loop` (послать сообщения, при `tool_calls` выполнить и добавить `tool`-сообщение, иначе вернуть ответ). Предупреждение: без счётчика шагов цикл может зациклиться (стр. 85).

**Если инструментов стало много — проблемы и MCP (стр. 85–94):** проблемы — незнакомые API, обработка ошибок разрастается с 10 до 50+ строк, нет единого формата (стр. 85–87). MCP (Model Context Protocol, единый стандарт описания и вызова инструментов): host (приложение с LLM), client (мост), server (хранит инструменты, отвечает на «список» и «выполнить»); транспорт stdio для локального, streamable HTTP для удалённого (стр. 87–90). Запуск готового сервера Tavily: Node ≥ 22, `TAVILY_API_KEY`, `npx @modelcontextprotocol/inspector npx -y tavily-mcp@latest` (стр. 90–92). Клиент на Python: `uv add mcp`, `stdio_client`, `ClientSession`, `list_tools`, `call_tool`; схемы MCP надо преобразовать в формат провайдера (стр. 92–94). Мин. версия Node 22.7.5 (стр. 92, по конспекту).

**Если хочу свой MCP-сервер — шаги (стр. 94–96):** `uv add mcp`; `FastMCP("имя")`; декоратор `@mcp.tool()` над функцией; `mcp.run(transport='stdio')`; запуск `uv run файл.py`. Без верного ключа — ошибка 401 (стр. 96).

**Итог части (стр. 97–98):** tool calling, описания в JSON-схеме, MCP — стандарт.

## Часть 4. Базовый ReAct-агент (гл. 4, стр. 99–132)

**Если хочу понять ReAct (Reason + Act — думай и действуй):** повторять Thought (что нужно знать), Action (вызов инструмента), Observation (результат в контекст) до Final Answer; сейчас это делается через tool calling, а не разбором текста (стр. 99–101).

**Если строю код агента — компоненты (стр. 102–104):** ExecutionContext (журнал выполнения), единый интерфейс инструмента, слой связи с LLM (LlmRequest, LlmClient, LlmResponse), Agent (оркестратор). `current_step` и `max_steps` защищают от бесконечного цикла (стр. 102–105). Пример запуска: `Agent(model=LlmClient(...), tools=[...], instructions=...)`, `await agent.run(...)` (стр. 104).

**Шаги по частям:**
- Типы данных (стр. 105–107): `Message`, `ToolCall`, `ToolResult`, обёртка `Event` (execution_id, author, timestamp, content); `ExecutionContext` хранит id, events, current_step, state, final_result. `ToolResult` привязывать к `ToolCall` через `tool_call_id`.
- Инструменты (стр. 108–112): абстрактный `BaseTool` с `execute(context, **kwargs)`; `FunctionTool` оборачивает обычную функцию, сам строит схему, передаёт context только если функция просит; декоратор `@tool`. MCP-инструменты тоже превращать в `BaseTool`; каждый вызов открывает новое соединение, в продакшене держать постоянный сеанс (стр. 111–112).
- Слой LLM (стр. 113–119): `LlmRequest` (instructions, contents, tools, tool_choice auto/required), `LlmResponse` (content, error_message, usage), `LlmClient.generate` через LiteLLM; при ошибке API возвращать `LlmResponse(error_message=...)`, а не исключение (стр. 115–119). Разные конспекты дают для этой части «113–118» и «115–119» — границы приблизительны.
- Класс Agent (стр. 119–125): `run` — создать контекст, записать вопрос как Event, цикл `пока нет final_result и шаг < max_steps` вызывать `step`; `step` = подготовить запрос, `think` (вызов LLM), записать, `act` (выполнить инструменты, при ошибке — `ToolResult(status="error")`), шаг +1. По умолчанию max_steps = 10 (стр. 119–120). Конспект даёт `step` на «124–125» при общем диапазоне «119–124» — номер сомнителен.
- Структурированный вывод (стр. 125–129): задать `output_type` (Pydantic), агент сам создаёт инструмент `final_answer`, ставит `tool_choice="required"`; финал = успешный результат этого инструмента. Если модель его не вызвала — цикл идёт до max_steps (стр. 129).
- Проверка на GAIA (стр. 130–132): агент с веб-поиском (через MCP), `max_steps=15`, семафор 3. Результат из 10: с поиском 7, $1.89; без поиска 2, $0.26 (стр. 131–132). Файлы (PDF, картинки) этот агент не умеет — это в гл. 5 (стр. 132).

## Часть 5. Знания: RAG и файлы (гл. 5, стр. 134–161)

**Если надо дать агенту свои данные — выбор (стр. 135–137):** один небольшой файл (до пары-тройки сотен строк) — прочитать целиком (стр. 136); архив из многих файлов — сначала разобраться в структуре: распаковать, дерево папок, поиск по именам, читать нужное (стр. 136–137); не читать всё подряд — выйдет за окно (стр. 137); очень большое — выборочное извлечение (стр. 137).

**Если выбираю способ поиска — таблица (стр. 142):** точное имя/код — keyword (BM25/TF-IDF, не знает синонимов, стр. 138–139); вопрос обычным языком — vector (смысловое сходство, стр. 139–140); связи и зависимости — graph (дорого строить, в книге не реализуется, стр. 140–141); структура папок — по метаданным файлов (стр. 141–142); в продакшене — hybrid (keyword + vector) (стр. 140, 142).

**Если делаю векторный поиск — шаги (стр. 142–150):** 1) эмбеддинг (текст в вектор, модель `text-embedding-3-small`), близость — cosine similarity (стр. 143–144). 2) чанкинг (резка на куски): ≈ 200–1000 токенов, перекрытие 10–20 % (стр. 144–145). 3) поиск: вектор запроса против векторов кусков, брать top_k (по умолчанию 3) (стр. 146). 4) при миллионах кусков нужна векторная БД: Chroma (локально), Pinecone (облако, платно), Weaviate, Qdrant, Milvus (стр. 146–147). Пример: из 37 312 токенов осталось 304 (экономия ≈ 99,2 %), куски по 500 токенов с перекрытием 50 (стр. 147–150).

**Если даю агенту работу с файлами — инструменты (стр. 150–159):** `unzip_file`, `list_files`, `read_file` (текст, CSV, Excel), `read_media_file` (картинки, аудио, PDF через модель) (стр. 154–158). В PDF берутся только первые 5 страниц и 3000 символов текста — иначе дорого (стр. 158). Перед тестом сбрасывать рабочую папку, чтобы старт был чистым (стр. 152–153). Агент с файлами: `max_steps=20`, потому что поиск по файлам — несколько шагов подряд (стр. 159).

**Если хочу вмешиваться в работу агента без правки ядра — callback (обратный вызов):** точки: до/после LLM, до/после инструмента, после всего запуска (стр. 160–161). Для инструмента: списки `before_tool_callbacks` и `after_tool_callbacks`; если колбэк вернул не `None` — это значение подменяет вызов (до) или результат (после); срабатывает первый такой (Early Exit) (стр. 161–162).

## Часть 6. Callbacks, память, сессии (гл. 5–6, стр. 161–220)

**Если опасное действие должно идти только после «да» человека (простой вариант) — шаги (стр. 163–164):** список опасных инструментов (`delete_file`, `send_email`, `execute_sql`); колбэк до инструмента спрашивает y/n; «да» — вернуть `None`, иначе вернуть строку отказа. Синхронный `input()` блокирует процесс, для веб-сервиса не подходит (стр. 164, 167).

**Если результаты поиска слишком большие — сжатие (стр. 165–166):** колбэк после `search_web`: если результат короче 2000 символов — не трогать; иначе резать на куски, найти векторным поиском топ-3, подменить результат. Следить за `tool_call_id`, иначе сожмёшь чужой запрос (стр. 166).

**Если нужна память — три слоя (стр. 168–173):** краткосрочная (внутри ExecutionContext), сессия (события между запусками), долгосрочная (выбранные факты, векторный поиск). Две беды без памяти: взрыв контекста и потеря истории между сессиями (стр. 169–171). Сессию (один чат) не путать с долгосрочной памятью (общая для всех сессий) (стр. 171). Соответствие стратегиям: слои 1–2 = Reduce + Write, слой 3 = Write + Retrieval (стр. 172).

**Если контекст растёт — управление размером (стр. 174–186):**
1. Хранилище (`ExecutionContext.events`) не менять; менять только копию запроса (`LlmRequest.contents`) в `before_llm_callback` (стр. 174–176).
2. Считать токены, а не сообщения: tiktoken; на сообщение +4 токена (стр. 176–177).
3. Порог по умолчанию 50 000 токенов (стр. 174, 185); в примерах для подсчёта встречается ≈ 20 000 (стр. 177) — цифры расходятся.

**Если хочу сессии — шаги (стр. 186–194):** класс `Session` (session_id, user_id, events, state, created_at, updated_at) (стр. 186–187); абстрактный `SessionManager` (create, get, get_or_create, save; всё `async`, чтобы подменять на базу данных) (стр. 188); `InMemorySessionManager` — после выхода из программы всё теряется (стр. 189); в `run()` принять `session_id`, получить сессию, создать контекст, в конце сохранить (стр. 189–191). Не хранить в `state` большие бинарные данные (стр. 187); Pydantic-модели в `state` — через `model_dump()` / `model_validate()` (стр. 196–197).

## Часть 7. Планирование и рефлексия (гл. 7, стр. 220–235)

**Если ReAct теряется в длинной задаче — причины (стр. 221–222):** теряет направление, забывает результаты, спешит с ответом, не восстанавливается после ошибок. Сравнение: вождение без GPS (стр. 220–222).

**Если хочу, чтобы агент работал как эксперт — шаги (стр. 222–223):** 1) разложить вопрос на пункты; 2) исследовать по порядку, фиксируя результат; 3) менять подход при неожиданном; 4) проверить полноту перед ответом. Планирование и рефлексия относятся к стратегии Generate (стр. 223).

**Если решаю, нужен ли план (стр. 224–225):** нужен при многошаговом поиске и сборе из разных источников; не нужен для «погода в Сеуле», «переведи текст» (лишние запросы).

**Если делаю инструмент планирования — шаги (стр. 225–229):** 1) один план; 2) при каждом изменении переписывать план целиком (иначе рассинхрон индексов); 3) статусы: `[ ]` ожидает, `[>] **...**` в работе, `[x] ~~...~~` сделано; 4) в docstring инструмента писать WHEN TO USE / WHEN NOT TO USE / HOW TO USE (стр. 225–227). Пример: `create_tasks` + `search_web`, `max_steps=10`, вопрос про Кипчоге (стр. 226–227). Слишком мелкие задачи — лишние вызовы (стр. 227). Расширения: критерии завершения, иерархия, зависимости; вопросы в описание: что нужно знать, какой порядок, как узнаю, что шаг готов (стр. 228–229).

**Если делаю рефлексию — когда звать (стр. 229–230):** после значимого шага, при ошибке инструмента, при сведении многих источников, перед финальным ответом. Не после каждого простого вызова. Инструмент `reflection(analysis, need_replan=False)`; при `need_replan=True` ставится метка REPLAN NEEDED (стр. 231–232). Ценность — при сбоях: без рефлексии агент повторяет сломанный вызов до конца шагов (стр. 232–233). Пример с `max_steps=5` (стр. 233). Для исследования: после серии поисков записать «собрал достаточно» и переходить к ответу (стр. 233–234).

**Если соединяю план и рефлексию — цикл (стр. 234–235):** план, действие, рефлексия, при `need_replan=True` — новый план. Предупреждение: забыть про `need_replan` — план не изменится даже при серьёзной ошибке (стр. 234).

## Часть 8. Запуск кода, рабочее место, навыки (гл. 8, стр. 236–271)

**Если фиксированных инструментов мало — причины (стр. 237–239):** действия ограничены списком; 10 файлов = 10 вызовов; сотни инструментов портят выбор (стр. 238–239). Код даёт управление потоком, хранение промежуточных данных и сборку инструментов за один запуск (стр. 239–241). Исследование CodeAct на M3ToolEval (82 задачи): код 74,4 % успеха и 5,5 взаимодействий; JSON 52,4 % и 7,6; текст 53,7 % и 7,7 (стр. 242–243).

**Если запускаю код модели — песочница (изолированная среда):** без неё код может удалить файлы, зависнуть, съесть память. Два уровня защиты: безопасность (закрыть чувствительные файлы и переменные) и лимиты (CPU, память, время) (стр. 244–245).

**Если использую E2B — шаги (стр. 244–248):** регистрация на e2b.dev, `E2B_API_KEY` в `.env` (не показывать ключ никому), `uv add e2b-code-interpreter`, `Sandbox.create(timeout=300, envs={...})` («30 сек» в конспекте есть, но что это именно значение по умолчанию — не подтверждено), `run_code`, результаты `logs.stdout` / `results` / `error`, `kill()` (стр. 244–245). Подключение к агенту: поле `code_env` в контексте, параметр `code_execution="e2b"` авто-добавляет инструмент `execute_python`, песочницу создать один раз в начале `run`, закрыть в `finally` (стр. 247–248). Ошибка в коде не убивает песочницу, агент видит `execution.error` и может исправить (стр. 244–245, 249–250). Тест: 100-е число Фибоначчи (стр. 249–250).

**Если инструмент нужно вызывать много раз — перенос в песочницу (стр. 250–256):** вместо 31 вызова с 31 запросом к LLM один код-цикл внутри песочницы (стр. 250–251). Флаг `sandbox_executable=True` у `FunctionTool`; нельзя вместе с функциями, которым нужен context (ValueError) (стр. 252). Такая функция: без context, импорты внутри, чёткий тип результата (стр. 253). Агент хранит `_sandbox_tools`, регистрирует их исходный код в песочнице и добавляет их описания в системный промпт; без `code_execution="e2b"` — ValueError (стр. 254–255). Пример: подсчёт упоминаний Twitter/X по дням в правках Wikipedia (стр. 256).

**Если нужна полноценная рабочая среда — шаги (стр. 257–261):** `bash_tool` (`sandbox.commands.run`, вывод со stdout, stderr, error, exit_code) и `upload_file` (по умолчанию в `/home/user/<имя>`). Пример: загрузить Excel, поставить pandas, посчитать продажи по городам (стр. 257–261).

**Если инструментов и описаний слишком много — Agent Skills (навыки) (стр. 262–271):**
- Идея: в промпте только имя и одна строка на навык, подробности в `SKILL.md` читаются по требованию (стр. 262).
- Три уровня раскрытия: 1) список навыков ≈ 50 токенов на 100 навыков; 2) `cat SKILL.md`; 3) дополнительные файлы и скрипты (стр. 263).
- Реализация: YAML-шапка `name`, `description`; разбор шапки, поиск навыков, раздел «Available Skills» в промпте, загрузка папок в песочницу, параметр `skills_path` (стр. 264–267). Без `name`/`description` навык игнорируется (стр. 267).
- Пример `pdf-merge` на `pypdf` (стр. 268–269).
- Три уровня инструментов: ядро (`execute_python`, `bash_tool`, `upload_file`), устанавливаемые (навыки), генерируемые (код «на лету») (стр. 270–271).
- Номера страниц у 8.1.3 и 8.2 в конспектах перекрываются («242–244» и «244–245») — номер сомнителен.

## Часть 9. Несколько агентов (гл. 9, стр. 272–307)

**Если один агент перегружен — шаги (стр. 272–273):** выделить роли (исследователь, кодер, писатель, ревьюер); у каждого короткий промпт и только его инструменты; связать паттерном. Беда одного универсала: длинный промпт путает, много инструментов — ошибки выбора (стр. 273).

**Если выбираю способ сотрудничества — три паттерна (стр. 274–277):**
- Workflow: порядок задаёт разработчик; лучше для предсказуемого конвейера.
- Agent as Tool: LLM решает, кого вызвать; контекст изолирован; контроль у главного; лучше для сведения результатов нескольких экспертов.
- Transfer: LLM передаёт управление; контекст общий; лучше для чётко разделённых областей (таблица 9.1, стр. 275).

**Если делаю workflow — шаги (стр. 277–287):**
- Все виды наследуют `Agent` и реализуют `run()`, поэтому вкладываются друг в друга (стр. 277–278).
- Sequential: первому агенту дать запрос и контекст, остальным только контекст; перед каждым очищать `final_result` и `current_step`; не передавать запрос повторно (стр. 278–280).
- Parallel: `asyncio.gather`, затем собрать общий контекст: события до старта + только новые события каждого агента, убрать дубли пользовательских сообщений, сохранить автора; итог с заголовками `[имя_агента]` (стр. 281–283). Пример: оптимист, пессимист, реалист.
- Loop: `stop_condition(result, iteration)`, `max_iterations` по умолчанию 10; пример: оценка ≥ 80 из 100, или слово «APPROVED» (стр. 284–286).
- Композиция: последовательный → параллельный → цикл → редактор (стр. 286–287).

**Если хочу агента-инструмент — шаги (стр. 286–291):** `AgentTool(agent)` делает агента инструментом: описание из имени и описания агента, вход — `request: string` или схема Pydantic; запуск `await agent.run(request)`; возвращается только итог (стр. 287–288). Плюсы изоляции: главный не видит внутренней кухни, в его контекст идёт одна строка, сбои дочернего не ломают родителя; минус: отладка отдельно, для промежуточного статуса лучше workflow (стр. 289–290). Пример: оркестратор + researcher + coder (стр. 290–291). Конспект даёт 9.4 как «стр. 284–290», что перекрывает 9.3.4 — номер сомнителен.

**Если нужен перевод разговора специалисту (Transfer) — шаги (стр. 291–300):**
1. Отличия: управление переходит, контекст общий, отвечает специалист напрямую (стр. 291–292).
2. Передача — тоже инструмент `transfer_to_agent` (стр. 292–293).
3. Дерево агентов: `sub_agents`, у каждого родитель; имена уникальны (иначе ValueError); цели передачи: дети, родитель, при `disallow_transfer_to_peers=False` — соседи (стр. 294–295).
4. Инструмент: `agent_name` с `enum` из имён целей; записывает `context.transfer_to`; повторный запрос — «Transfer already requested» (стр. 296–298).
5. В запросе LLM: добавить transfer-инструмент из `context.transfer_tools`; после каждого шага проверять `context.transfer_to`, СБРОСИТЬ флаг и вызвать целевого агента с тем же контекстом; не сбросить — бесконечная передача (стр. 299–300).
6. Конспект 11 обрывается на середине реализации `run()` (стр. 298 и далее) — остальное см. конспект 12.

**Если агент живёт на другом сервере — A2A (Agent-to-Agent, открытый HTTP-протокол) (стр. 301–306):** карточка агента по адресу `/.well-known/agent.json` (name, description, url, version, capabilities) (стр. 301–302); сервер: `AgentExecutor.execute` берёт ввод, запускает агента, кладёт ответ в очередь событий; `AgentCard`, `DefaultRequestHandler`, `A2AStarletteApplication`, `uvicorn` (пример порт 9999) (стр. 303–304); клиент `RemoteAgent`: при создании читает карточку, `run` делает POST с `{"input": ...}` и читает `output`; обрабатывать ошибки HTTP (стр. 305–306). Все три паттерна можно комбинировать (стр. 307). Нумерация «9.1–9.5» в конспекте 12 не совпадает с книгой (это счёт самого конспекта).

## Часть 10. Оценка агентов (гл. 10, стр. 308–328)

**Если хочу видеть, что происходит внутри агента — наблюдаемость (стр. 308–312):** оценка нужна из-за огромного пространства действий и ради проверки хода рассуждения, не только ответа (стр. 308–309). Метрики: задержка на вызов инструмента, время задачи, число вызовов API, токены, стоимость, доля ошибок LLM (стр. 310). Три опоры: метрики (что), трассы (как; состоят из spans — единиц работы, и events — мгновенных событий), логи (подробности); писать селективно, не всё (стр. 310–311). OpenTelemetry (OTel) — стандартная выгрузка по протоколу OTLP в Langfuse, LangSmith, Arize, Weights & Biases (стр. 311–312).

**Если хочу оценивать правильно — три измерения (стр. 313–314):** итоговый ответ, компоненты, траектория (разумность пути). Оценка одного ответа скрывает системные ошибки (стр. 314).

**Если собираю тестовый набор — шаги (стр. 315–317):** три источника — benchmark (GAIA, HotpotQA, SWE-bench), custom (сценарии бизнеса, начать с нескольких десятков примеров), production (реальные запросы, часто без эталона); лучше комбинировать. Разбор ошибок — по 50–100 примеров за проход (стр. 317). Риск: подгонка под benchmark (стр. 315–317).

**Если разбираю ошибки — шаги (стр. 318–319):** 1) open coding (читать трассы, записывать коротко, что пошло не так); 2) собрать таксономию (виды сбоев, например «неверная цитата», «ошибка рассуждения»); 3) повторять, пока новые типы не перестанут появляться; 50–100 примеров за цикл (стр. 318–319).

**Если нужна понятная метрика — рубрика (стр. 320–321):** пункты PASS/FAIL: релевантность ответа, надёжность цитат, соблюдение требований. Общий процент = все PASS / число оценок. Шкалу 1–5 не рекомендуют — бинарные пункты проще автоматизировать (стр. 320–321). `overall_pass` = PASS только если все три пункта PASS (стр. 323).

**Если оцениваю моделью-судьёй (LLM-as-a-Judge) — шаги (стр. 321–324):** 1) режим одного ответа (запрос, ответ, пакет источников `evidence_pack`, рубрика, PASS/FAIL по пунктам) или попарное сравнение A/B/Tie; 2) вход судьи — один JSON; 3) правило «использовать только evidence_pack, без внешних знаний»; 4) ответ судьи — один валидный JSON (`overall_pass`, поля рубрики, `failure_reasons`); 5) судью брать сильнее проверяемой модели (стр. 322–324). Не подавать «эталон», если его нет; следить за лимитом токенов (стр. 324). Конспект 12 даёт раздел судьи как «322–324» и вход судьи как «321–324» — границы перекрываются.

**Если встраиваю оценку в выпуск — CI/CD (стр. 323–326):** 1) этап до слияния (при открытии PR): юнит-тесты, линтинг, проверка зависимостей и уязвимостей, при изменении промптов — малый набор ≈ 20–50 кейсов и сравнение с прошлой версией (стр. 324). 2) этап проверочной среды (staging) после слияния: нагрузка, долгие прогоны, интеграции с удалёнными сервисами, большой набор. 3) Ворота качества: `overall_pass` ниже порога (число порога в книге не найдено) — блок деплоя; вручную — прикладывать результат оценки к PR как артефакт (стр. 323–325). 4) Маховик качества: определить качество, собрать телеметрию, оценить, обновить наборы и рубрики, вернуться к шагу 1 (рис. 10.4). Ошибки: оценивать один раз; держать один неизменный набор (стр. 325–326). Конспект 13 называет раздел «10.4 Operations», а конспект 12 «10.4» называет разделом о том, что оценивать — нумерация расходится.
