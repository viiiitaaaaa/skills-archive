## Gulli «Agentic Design Patterns» (5)


### Новости, данные, Claude Code и агенты

- **Исполнитель и критик — разные вызовы.** Проверку результата субагента/Hermes делать отдельным агентом с другой инструкцией («ищи ошибки против исходника»), а не тем же, кто делал. Зачем — модель плохо видит свои ошибки. (гл. 4, стр. 66; гл. 11, стр. 192) → hermes
- **Hermes — «быстрая» модель, я — «сильная».** Это и есть паттерн «маршрутизатор ресурсов»: простое/объёмное — дешёвой модели, сложное — сильной; критик (я) проверяет и уточняет правило маршрутизации со временем (запись в скилл hermes). (гл. 16, стр. 246, 259) → hermes
- **Запасной путь при отказе модели.** Если Ollama/Hermes лежит или 429 — не ждать: задача переходит ко мне или ставится в очередь, с пометкой в табло. (гл. 16, стр. 246, 256) → hermes
- **Больше «времени подумать» слабой модели.** Для Hermes на важных извлечениях: 2–3 прогона и голосование (self-consistency) или прогон + самопроверка — дешевле, чем отдавать мне. (гл. 17, стр. 275–278; прил. A, стр. 361–362) → hermes
- **Разделители в длинных заданиях.** Задание, данные и примеры разделять тегами (`<задание>`, `<текст>`, `<<<ТЕКСТ … ТЕКСТ>>>`) — так уже сделано в hermes_pereskaz.py; применять везде, где в запрос вставляется чужой текст. (прил. A, стр. 355) → hermes

## Chip Huyen «AI Engineering» (4)


### Новости, данные, Claude Code и агенты

- **Лёгкое — Hermes, сомнение — проверить.** Книга поддерживает «роутер»: дешёвая модель для простой подзадачи, сильная для сложной; а оценивать результат слабой модели проще, чем создавать — значит, проверять работу Hermes выборочно (spot-check) и сильной моделью. (гл.3, стр. 292–293; гл.5, стр. 447) → hermes
- **Проверка ответов Hermes тремя способами.** (а) Сверить цифры и названия с оригиналом; (б) два прогона и сравнить расхождения (self-consistency); (в) попросить вторую модель найти утверждения без опоры в источнике. Именно так в этой сверке найдены ошибки (см. раздел «Проверка пересказа Hermes»). (гл.4, стр. 328–331) → hermes
- **Судья не должен быть автором.** Модель завышает свои ответы (GPT-4 +10%, Claude-v1 +25%): проверку работы Claude лучше поручать другой модели/Hermes или человеку, а порядок вариантов в сравнении менять. (гл.3, стр. 289–290) → hermes
- **Запасная модель (шлюз).** Одна точка входа к моделям (Claude, Hermes/Ollama, API), с запасным вариантом при лимите или ошибке; ключи — только в шлюзе, не в каждом скрипте. (гл.10, стр. 866–870) → hermes

## Hur, Song «Build an AI Agent (From Scratch)» (16)


### Новости, данные, Claude Code и агенты

- **Три признака «агент оправдан».** Число шагов непредсказуемо + ценность выше цены и задержки + ошибку можно заметить и она не опасна. Где ошибку не заметить (юр. текст, область, которую она не проверит) — агенту только черновик. (гл. 1, стр. 31) → hermes
- **Провал Hermes — сначала проверить контекст, потом модель.** Когда Hermes/субагент ошибся, первый вопрос: было ли в его контексте всё нужное (файл, правило, пример)? Значительная часть провалов — нехватка информации, а не ума. (гл. 1, стр. 33) → hermes
- **«Агент = модель + обвязка»: улучшать обвязку Hermes, а не ждать модель.** Та же gpt-oss работает лучше с хорошей обвязкой: текст в запросе (наш урок 13.10), короткая выборка, схема ответа, поле «не могу», журнал попыток, лимит шагов. (гл. 1, стр. 36) → hermes
- **Перенос задачи на Hermes — только после замера.** Сначала задача сделана сильной моделью (мной) и есть эталон → тот же промпт на Hermes → сравнить на 10–20 примерах → если потеря качества допустима, тип задачи уходит Hermes. Гибрид «ядро — Claude, простое — открытая модель» — рекомендованная схема книги. (гл. 2, стр. 41) → hermes
- **Поле «не могу — причина» в задании слабой модели.** В формат ответа Hermes/субагента добавлять `можно_решить: да/нет` и `почему_нет`. Откалиброванная модель честно отказывается, «амбициозная» выдумывает; без поля отказа выдумка маскируется под ответ. (гл. 2, стр. 55–63) → hermes
- **Отказ модели — отдельная ветка.** Проверять `finish_reason == "refusal"`/пустой ответ и превращать в понятное «модель отказалась» + запасной путь (другая модель/я). Отказы разные у разных моделей и меняются с обновлениями. (гл. 2, стр. 58, 62) → hermes
- **Блок «пределы знаний» в промпте агента.** Дата среза + «честно скажи, что не знаешь о событиях после; предложи поиск». Для Hermes (gpt-oss) и бота — чтобы не выдавали устаревшее за текущее (цены, тарифы, правила площадок). (гл. 2, стр. 52) → hermes
- **Свой MCP-сервер за 20 строк.** Если наш сборщик (радар, tg_monitor, база поставщиков) нужен и мне, и Hermes — обернуть функцию `@mcp.tool()` в FastMCP (stdio) вместо копирования кода; ошибки — строкой. Ставить только после её «да». (гл. 3, стр. 95–97) → hermes
- **Структурированный итог через инструмент `final_answer`.** Если модель через API должна вернуть JSON — объявить схему как инструмент «финальный ответ» и требовать его вызова (`tool_choice="required"`); ошибка валидации уходит модели на исправление. Ср. Гулли №50 — здесь конкретный механизм. (гл. 4, стр. 124–126) → hermes
- **Скользящее окно с «якорем» задачи.** Если урезаем историю — всегда сохранять всё до первого сообщения с задачей, а из остального — последние N. Иначе агент «забывает, что делает». (гл. 6, стр. 175) → hermes
- **Вход субагента — схемой, не свободным текстом.** Для повторяющихся поручений (Hermes-пересказ, поиск на 1688) описывать вход полями (путь, формат, что вернуть, лимит), а не абзацем: `AgentTool` с `input_schema` проверяет поручение до запуска. Ср. Гулли №33 (договор подрядчика) — здесь машинная проверка полей. (гл. 9, стр. 286–288) → hermes
- **Разбор ошибок Hermes — открытое кодирование, 50–100 примеров.** Проверяя пересказы/классификацию Hermes: сначала своими словами записывать, что не так; потом сгруппировать в типы (номера страниц, выдуманный код, пропуск раздела, неверный перевод); повторять, пока не появляются новые типы; самые частые → правило в промпт Hermes. (гл. 10, стр. 315–316) → hermes
- **Судья сильнее исполнителя: Hermes проверяю я.** Правило книги «агент на Haiku — судья на Opus» = наш порядок: Hermes делает, Claude судит; массово — модель-судья, выборочно — она. Наоборот (слабая судит сильную) не делать. (гл. 10, стр. 318–319) → hermes
- **Судья «только по пакету» для пересказов.** Проверка пересказа Hermes: судья получает пересказ + куски оригинала и ставит FAIL на утверждение без опоры в оригинале, «вставку» (код/цифра, которых нет в тексте), ссылку на страницу, где этого нет. Ровно такие ошибки нашлись в пересказе этой книги. (гл. 10, стр. 320–322) → hermes
- **Выбор модели — по Artificial Analysis и LMArena, потом свой тест.** При смене модели для Hermes/Ollama сначала сравнение качества/скорости/цены (artificialanalysis.ai) и предпочтений людей (lmarena.ai/leaderboard), потом — свой малый тест-набор. (гл. 2, стр. 42) → hermes
- **LiteLLM — один интерфейс к Ollama и Claude (справочно).** Если будем писать скрипты, зовущие разные модели, — один вызов `completion(model=...)` для всех провайдеров, смена модели одной строкой. Ставить только после её «да». (гл. 2, стр. 42, 47) → hermes

## Mollick «Co-Intelligence» (3)


### Новости, данные, Claude Code и агенты

- **Карта задач: моё / поручаю / автомат.** Для каждой повторяющейся работы записать категорию: «только она» (решения, вкус, её правила), «поручаемая» (Hermes/Claude делает — она или Claude проверяет), «автоматическая» (только если есть проверка системой). - **Кентавр для конспектов.** ИИ пересказывает (он сильнее в сжатии), человек проверяет понимание и точность по оригиналу (он сильнее в понимании) — ровно наш процесс «Hermes пересказ → сверка Claude». (гл. 6, стр. 120) → hermes

## Whalen «Design for How People Think» (2)


### Новости, данные, Claude Code и агенты

- **Разбор отзывов по шести колонкам.** Любую пачку отзывов (конкуренты, наш магазин, боли Frivent) раскладывать на 6 колонок: Зрение (не заметила / не нашла), Ориентирование (не поняла, как перейти/вернуться), Память («ждала как на Amazon»), Язык (непонятные слова, её термины), Решения (вопросы-блокеры: доставка, размер, оплата), Эмоции (страх, недоверие, «обожаю»). Каждую находку — в одну главную колонку. Раскладку можно отдать Hermes, выводы — Claude. (гл. 8, стр. 97–99; гл. 15) → hermes
- **Слова в ловушке у Hermes.** Пересказы Hermes проверять в первую очередь там, где он «округляет» смыслы: кейсы и цифры. В этой книге он выдумал целый блок с процентами (см. «Проверка пересказа») — правило: цифра из пересказа без проверки по оригиналу в итог не идёт. (проверка пересказа) → hermes

### Новости, данные, Claude Code и агенты

## «The 0→1 Loop Engineering Playbook» (2026) (7)


### Новости, данные, Claude Code и агенты

- **Дедупликация вызовов + фраза-переключатель.** В циклах с моделью (скрипты Hermes, сборщики) помнить «инструмент + аргументы»; повтор → не выполнять, а вставить «You already tried this exact call. Try a different approach.»; 3 одинаковых подряд → стоп и к ней с журналом. (гл. 4, стр. 33, 36; гл. 11, стр. 135; гл. 12, стр. 157) → hermes
- **Правило 70 % окна для Hermes.** Текст куска + задание ≤ 70 % окна модели, 30 % — место «подумать»; иначе модель теряет инструкции из середины. (гл. 8, стр. 79) → hermes
- **Ролевая карточка: + формат выхода и поведение при сбое.** Дополнить карточку агента (Gulli №69): модель, инструменты, системный промпт, формат входа, **формат выхода**, **что делать при сбое**; хранить в git. (гл. 7, стр. 76) → hermes
- **Налог на координацию 30 %.** Если постановка задачи Hermes/субагенту + проверка занимают > 30 % всей работы — делать самой. (гл. 7, стр. 76) → hermes
- **Ступенчатое доверие к Hermes по типам задач.** Вести счёт ответов, прошедших мою проверку без правок: первые 20 — проверять всё; ≥ 85 % на 50+ — выборочно; ≥ 95 % на 100+ — только цифры, имена, пути. Отдельно для пересказа, подсчёта, перевода. (гл. 9, стр. 90) → hermes
- **Пакеты по 10 в одном вызове.** Вместо 100 вызовов Hermes по одному посту — 10 групп по 10: накладные токены (задание, правила) −90 %, легче держать лимит 3 потоков Ollama. (паттерн 79, стр. 296) → hermes
- **Длина ответа по типу задачи.** Потолок вывода: да/нет и классификация ~100 токенов, извлечение ~500, сводка 500–1000; выход в 5–10× дороже входа. (гл. 13, стр. 163–164; паттерн 85) → hermes

## Agrawal, Gans, Goldfarb «Prediction Machines» (7)


### Новости, данные, Claude Code и агенты

- **Прогноз — машине, суждение — ей, действие — скрипту.** Пересказ, классификация, поиск, извлечение = прогноз (Hermes или Claude); «что важнее, что хуже пропустить» = её суждение, записанное правилом; запись в таблицу и отправка = скрипт. - **Нужна ли проверка результата — по ставкам.** Черновик пересказа, сводка новостей, список кандидатов — низкие ставки: выборочная проверка. - **Hermes сам помечает неуверенные случаи («по исключениям»).** В задании Hermes требовать поле «уверен / не уверен + почему»; неуверенное уходит Claude или ей, остальное идёт дальше без внимания. Зачем — человек тратит внимание только на исключения. Когда — массовые классификации (посты, товары, отзывы). (гл. 7, ч. 15) → hermes

Важную классификацию прогонять двумя исполнителями (Hermes и Claude или Hermes с двумя формулировками); расхождение — на проверку. Когда — отбор приёмов, разметка, спорные посты. (гл. 4, ч. 12) → hermes

- **Её роль — «инженер функции вознаграждения».** В Moneyball главным стал аналитик, который говорит машине, что предсказывать, и решает, как использовать прогноз. При раздаче задач ей оставлять: что считать успехом, какие ошибки хуже, где граница «берём / не берём»; остальное — машинам. Когда — раскладка ролей в новом проекте. (гл. 17, ч. 28) → hermes
