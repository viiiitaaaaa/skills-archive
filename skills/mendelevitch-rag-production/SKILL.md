# Mendelevitch — «Hands-On RAG for Production» (черновик)

Как читать: каждая строка = правило из конспекта + (стр. N) оттуда. «стр. нет в конспекте» = конспект страницу не назвал.
Расшифровка слов: RAG = система сначала ищет факты в твоих данных, потом модель пишет ответ только по ним. Чанк = кусок текста после нарезки. Эмбеддинг = текст, превращённый в набор чисел (вектор), по которому ищут «по смыслу». Ретривер = часть, которая ищет. LLM = большая языковая модель (как Claude).

## 0. Что такое RAG и когда он, а не другое
- RAG = 2 шага: R (поиск в частных данных) → G (модель отвечает по найденному) — «экзамен с учебником» вместо «экзамена по памяти» (стр. 27–30)
- Два потока: загрузка (Ingestion: источник → парсинг → нарезка → эмбеддинги → индекс) и запрос (Query: запрос → вектор → поиск → промпт → ответ → проверка) (стр. 31–33, 49–52)
- RAG против дообучения (fine-tuning, менять веса модели): RAG обновляется мгновенно, видно источник, можно ограничить доступ; дообучение дорого (GPU), нужен эксперт, данные не обновить быстро, нет контроля доступа — знания сливаются в один «blob» (стр. 36–38)
- RAG против «Chat with PDF» (вставить весь текст в окно): дорого, медленно, не масштабируется на тысячи документов (стр. 36)
- Плюсы RAG: меньше галлюцинаций, можно сослаться на источник `[1, 2]`, знания обновляются заменой документа, права доступа (стр. 12–14, 39)
- Но RAG снижает галлюцинации, а не убирает (стр. 114–120)
- Сначала решить: DIY (всё сам) или платформа RAG-as-a-service (стр. 2–26; 159–164)

## 1. Если хочу превратить файлы в текст (парсинг)
- PDF сложный (текст = координаты символов, нет логической структуры); библиотеки PyMuPDF, pdfminer.six, Adobe API; сканы — OCR (Tesseract, Azure/Google OCR) (стр. 54–63)
- DOCX/HTML проще (это XML): python-docx, Beautiful Soup (стр. 54–63)
- Сложные макеты (слайды, инфографика) — VLM (модель, «видящая» картинку) только как крайняя мера: дорого и галлюцинирует (стр. 56)
- Правило: «сначала самый дешёвый успешный парсер»: библиотеки → OCR → VLM (стр. 57)
- Две колонки в PDF при простом извлечении перемешиваются (стр. 55)
- В чатах не терять, кто сказал: метаданные в JSON, например `{"who": "AI"}` (стр. 56)
- Грязные данные: ошибки OCR (0 вместо O), повторяющиеся шапки/подвалы, кодировка UTF-8/ISO. Решение: многоэтапная очистка — триаж (сортировка) → маршрутизация → очистка (стр. 96)
- Огромный PDF (тысячи страниц): нельзя грузить в память целиком (вылет OOM); читать постранично или раздать диапазоны страниц разным воркерам (стр. 97)
- Пример разбиения PDF: узнать число страниц → число кусков = страниц / страниц на кусок → цикл создания новых PDF → сохранить в папку; в примере по 50 страниц (стр. 98–100)

## 2. Если хочу нарезать текст (чанкинг)
- Зачем: чтобы влезть в окно модели и повысить точность поиска (стр. 63–69)
- 5 способов (стр. 63–69):
  1) фиксированный размер с нахлёстом (overlap), чтобы не терять смысл на границе;
  2) по абзацам `\n\n` или предложениям (spaCy, NLTK);
  3) рекурсивный: абзац → предложение → фраза (LangChain `RecursiveCharacterTextSplitter`);
  4) по заголовкам Markdown (#, ##);
  5) семантический: группировать предложения по смыслу (кластеризация)
- Пример чисел из LangChain: `chunk_size=1000`, `chunk_overlap=200` (стр. 34); в примере агента: 1000 символов, нахлёст 100 (стр. 237–239)
- Фиксированная резка может рвать слова — шум для эмбеддингов (стр. 68)
- «Lost in the middle»: модель лучше помнит начало и конец контекста, чем середину (стр. 67)
- Время до первого токена растёт квадратично от длины контекста (стр. 64)
- Размер чанка сверять с окном модели эмбеддингов (см. раздел 3)
- Таблицы обычной нарезкой ломаются: шапка в одном чанке, данные в другом (стр. 268–269); см. раздел 12
- Аудио: реплики группировать в блоки, например до 512 токенов, сохраняя границы предложений (стр. 292 по книге)

## 3. Если выбираю эмбеддинги (векторы)
- Шаги выбора: 1) смотреть рейтинг MTEB; 2) решить размерность (точность против затрат); 3) сверить размер чанка с окном модели (стр. 69–75)
- Окна эмбеддингов: Qwen3 32k, OpenAI/Gemini ~8k, BGE-M3 1k (стр. 65, 71)
- Если чанк длиннее окна, библиотека (HuggingFace) молча обрежет — данные потеряются (стр. 72)
- MRL (Matryoshka): вектор можно обрезать до меньшей размерности без большой потери смысла (стр. 71)
- Векторы передавать в Base64, не в JSON (JSON больше и теряет точность) (стр. 72)
- Для нормализованных векторов (длина 1) скалярное произведение = косинусное сходство (стр. 53, 75)
- Эмбеддинги семантические: «США» и «Америка» близки, хоть слова разные (стр. 69–75)
- Для больших объёмов: распределённая генерация эмбеддингов (Ray, Dask, Spark, несколько GPU) (стр. 94)

## 4. Если выбираю и настраиваю векторную базу
- Мало данных: хранить в памяти и перебирать, сложность O(n); много — специальная векторная БД (стр. 75)
- ANN (приблизительный поиск ближайших соседей) вместо полного перебора: находит «очень близкий», не обязательно самый близкий — цена за скорость (стр. 76–78)
- HNSW — основной алгоритм ANN: многослойный граф, верх «грубый», низ «детальный» (аналогия: страна → штат → город → район) (стр. 76–78); библиотека FAISS (Meta) (стр. 77)
- Векторная БД = ещё хранение, обновление, удаление, фильтр по метаданным (ID, дата, автор) (стр. 77–79)
- Пре-фильтрация: сначала отсечь по метаданным («отчёты за 2023»), потом дорогой векторный поиск — быстрее и точнее (стр. 78)
- Параметр k (сколько вернуть): мало — пропустим ответ; много — шум, перегрузка окна, дороже и медленнее (стр. 78)
- Снижение размерности ускоряет, но может снизить качество; `pgvector` — до 2000 измерений для 32-битных float (стр. 78)
- Пример pgvector: 1) эмбеддинги (`all-MiniLM-L6-v2`, размерность 384); 2) таблица с `VECTOR(384)`; 3) индекс HNSW (m=16, ef_construction=64); 4) загрузить (массивы NumPy → списки float); 5) искать оператором `<=>` (стр. 79–81)
- Ловушка: `<=>` даёт различие, не сходство; сходство = `1 - (embedding <=> query_vector)` (стр. 81)
- Не забыть: хранить чанк как объект «вектор + сырой контент + метаданные»; иначе «сироты» — вектор без ссылки на источник (стр. 299)

## 5. Если хочу точный поиск (гибрид + reranking)
- Простого векторного поиска в продакшене часто мало (стр. 31, 90, 101–104)
- Схема из 2 этапов (стр. 101–104):
  1) кандидаты: фильтры по метаданным, вектор или слова; цель — высокая полнота (recall), пусть с лишним;
  2) reranking (переранжирование) малой группы точной моделью
- Гибридный поиск = вектор (смысл) + лексический (точные слова, термины, артикулы). Лексический = инвертированный индекс (слово → документы), чаще BM25 (стр. 103). Помогает с редкими токенами и опечатками (стр. 53–54)
- Как слить два списка (стр. 101–104):
  1) RRF (Reciprocal Rank Fusion): сумма 1/позиция, оценки нормализовать не надо;
  2) взвешенное среднее: оценки привести к 0–1 и сложить с весами (пример 60% вектор + 40% слова)
- Виды reranking (стр. 105–109):
  1) по релевантности — cross-encoder (смотрит пару «запрос + чанк» целиком), например `bge-reranker-v2`;
  2) MMR — баланс релевантности и разнообразия, убирает чанки-близнецы (стр. 108; MMR с 1998 г., стр. 53);
  3) своё по бизнес-логике, например свежие выше
- Модели reranking (стр. 106): открытые — Sentence Transformers, BGE Reranker, Mixedbread; платные — Cohere Rerank, Voyage AI, Jina Reranker
- Не делать reranker из обычной LLM (GPT-4o и т.п.): проще, но галлюцинации, задержка, цена (стр. 106)
- Query rewriting: переписать запрос в «запрос для поиска», отделив команду («напиши стих») от сути («поездки в 2025») (стр. 52–54)
- Если в топ-k лезет шум при росте базы — гибрид и reranking (стр. 90)

## 6. Если пишу промпт для RAG
- Базовый шаблон: «Ты помощник по вопросам. Используй фрагменты контекста. Если не знаешь — скажи, что не знаешь. <вопрос>…</вопрос> <контекст>…</контекст>» (стр. 29)
- В примерах шаблонов запрос стоит перед контекстом (стр. 29, 84); явного совета «ставить запрос перед контекстом» в книге не найдено
- Части промпта разделять XML-тегами `<context>…</context>` (стр. 84)
- Против галлюцинаций: «Если ответа нет в контексте, скажи "Я не знаю"» (стр. 84, 135)
- Сложное — Chain-of-Thought («думай пошагово») (стр. 84)
- Сборка контекста (context engineering): факты из поиска + история пользователя + системные инструкции → один запрос; ограничивают стоимость, задержка и «lost in the middle» (стр. 342–343)
- Данные от команд отделять тегами `<query>`/`<context>`, чтобы модель отличала данные от инструкций (стр. 113)

## 7. Если надо защитить систему (guardrails, инъекции, приватность)
- Guardrails (ограничители) нужны против токсичного, галлюцинаций и атак (стр. 109–114)
- Три слоя (стр. 109–114): 1) разные точки зрения в данных; 2) запреты в системном промпте; 3) модели-аудиторы ShieldGemma, Llama Guard перед показом ответа (стр. 110)
- Prompt injection (внедрение команд): прямая («забудь инструкции») и косвенная (вредный текст спрятан в скачанном документе) (стр. 109–114)
- Защита (стр. 113): 1) санитизация — искать «игнорируй инструкции» в запросах и документах; 2) чёткие разделители в промпте
- Визуальная инъекция: команды спрятаны в картинке для VLM (стр. 300)
- Персональные данные (PII): типизированное маскирование — имя заменить на `<PERSON>`, смысл остаётся (стр. 141–144)
- Хранение: шифрование (и при передаче) (стр. 33, 141–144), RBAC (доступ по ролям), минимум нужных данных (GDPR) (стр. 141–144)
- Фильтр прав доступа встраивать в запрос — человек видит только свои документы (стр. 141–144)
- Не хочешь, чтобы данные ушли провайдеру LLM — своя модель (Llama, Qwen, DeepSeek) в своём облаке (VPC) (стр. 141–144)
- В сканах размывать лица/подписи при загрузке (LayoutLM, YOLO) (стр. 300)
- Право «быть забытым»: у каждого фрагмента метаданные, чтобы удалить без полной переиндексации (стр. 345–347)
- Журнал аудита, неизменяемый: запрос → версия документа → ответ → цитаты; связь «запрос → версия документа → ответ с цитатами» (стр. 344); имён полей JSON `{prompt_id, doc_version_id, …}` в книге нет — это пример составителя конспекта
- Данные по регионам: запрос немца → индекс во Франкфурте (стр. 345–347)

## 8. Если борюсь с галлюцинациями
- Причины (стр. 116): 1) ретривер не нашёл нужное или нашёл противоречивое; 2) в базе старое/неверное; 3) LLM проигнорировала контекст, взяла свои знания или неверно склеила факты
- Виды (стр. 117): сомнительные (неоднозначность, сдвиг времени), безобидные (вывод по здравому смыслу, в тексте нет), нежелательные (прямое искажение)
- Обнаружение (стр. 118): 1) LLM-судья ставит 1–5 по источнику; 2) специальная модель HHEM (`vectara/hallucination_evaluation_model`) даёт вероятность 0–1
- Исправление (стр. 121): 1) детектор находит; 2) вероятность высока → «Не знаю» или отправка в модель коррекции; 3) корректор переписывает по исходным фрагментам. Минус: цепочка добавляет задержку
- Vectara: `correct_hallucinations` исправляет ложные факты и объясняет правки; Factual Consistency Score — оценка точности (стр. 179–180)
- Для картинок: «визуальное поддакивание» (VLM видит ржавчину там, где грязь). Blind Verification: 1) показать фото с нейтральным промптом («Опиши поверхность»); 2) сравнить с вопросом отдельной текстовой LLM (стр. 301–302)

## 9. Если оцениваю качество
- Сначала оптимизировать поиск, потом генератор. При охвате поиска 40% промпт не поможет (стр. 184)
- Офлайн-оценка (до запуска, глубокая) и онлайн (на живом трафике, лёгкая) (стр. 183)
- Сбои (стр. 184–188): низкий охват (нужное есть, не найдено); низкая точность (много шума); неверность (противоречит источнику); контекст использован плохо; ответ верный, но не по вопросу; ошибки парсинга (таблицы стали кашей); устаревшие версии документов
- Метрики поиска (нужен «золотой набор» — вручную эталонные чанки к вопросам) (стр. 195–198):
  Precision@k — доля полезных среди k (важно при малом окне); Recall@k — сколько нужных нашли; F1 — баланс; MRR — позиция первого верного; MAP — штраф за низкий ранг; nDCG — учитывает степень пользы (0–3).
  Конфликт: больше данных — выше Recall, ниже Precision (стр. 196)
- UMBRELA без золотых наборов: LLM-судья даёт 0–3 (0 не по теме; 1 по теме, ответа нет; 2 ответ нечёткий или спрятан; 3 точный ответ). Recall посчитать нельзя — пришлось бы прогнать всю базу (стр. 199–201)
- Метрики генерации (стр. 201–204): использование контекста (AutoNuggetizer: «наггеты» Vital и OK); точность ответа; верность (каждое утверждение подтверждено чанками — главное против галлюцинаций); точность ссылок; стабильность (тот же ответ при повторе)
- Безопасность: Llama Guard, ShieldGemma; red teaming — человек намеренно ищет уязвимости (стр. 204)
- LLM-судья (стр. 190–195): 1) подать запрос, контекст, ответ; 2) чёткая рубрика (фактологичность, релевантность 1–5); 3) ответ строго JSON.
  Риски: судья любит «ИИ-звучащие», вежливые, длинные ответы (стр. 191–192); нестабильность — запускать несколько раз и усреднять или сравнивать пары (стр. 191)
- Судья дорогой и может галлюцинировать; маленькие модели (HHEM, Luna) быстрее и дешевле; человек — самый точный, самый дорогой (стр. 85)
- Инструменты (стр. 205–208): Open RAG Eval (бесплатный, без золотых наборов: UMBRELA, AutoNuggetizer, HHEM); Ragas (делает синтетические тесты); DeepEval (как pytest); Amazon Bedrock (облако)
- Лайки/дизлайки: User Satisfaction Rate = 👍 / все голоса; смотреть, какие темы получают больше дизлайков → править данные там (стр. 209–210)
- В продакшене: офлайн-тест на фиксированном наборе как «ворота качества» перед обновлением (стр. 212); онлайн — асинхронно, проверять 5–10% запросов (стр. 213)
- Системные метрики (стр. 213–214): задержка (P95/P99), запросов в секунду, доступность ≥ 99.9%, стоимость (токены ответа + токены судьи)
- Для картинок: recall@k на «золотом наборе» пар текст-картинка; VLM-судья 1–5 (стр. 302)

## 10. Если нужно быстро и дёшево
- Цели (стр. 135): поиск (вектор/гибрид/reranker) ≤ 300 мс в среднем; генерация 2–3 с (малые модели) до 5–10 с (флагманские)
- Параллельно: оркестратор запускает вектор и слова одновременно (fan-out) — время = самый медленный, не сумма (стр. 135–141)
- Ускорение модели: vLLM, TensorRT-LLM, TGI (continuous batching, paged attention) (стр. 135–141); квантование (float32 → int8/int4), FlashAttention, vLLM/Ollama (стр. 82)
- ANN-индексы HNSW, IVFPQ (стр. 135–141)
- Кэш (Redis/Dragonfly), 4 уровня (стр. 135–141): готовый ответ по хешу запроса; результаты поиска по эмбеддингу; тексты чанков; семантический кэш (порог сходства в примере 0.85, стр. 140)
- Беда кэша: данные в базе сменились, в кэше старое. Решение: события (Pub/Sub) при обновлении (стр. 135–141)
- Каскад: простой запрос → дешёвая модель, сложный → дорогая (стр. 92; LLM Router, стр. 150)
- Mixture-of-Agents: простое отдать дешёвой модели (GPT-4o-mini) — расходы ниже на 80–90% (стр. 252)
- Разрыв между открытыми и закрытыми LLM на задачах RAG невелик; правило: открытая модель больше 70 млрд параметров «достаточно хороша» (стр. 83). «Маленькая не хуже большой» в книге не найдено
- Реальный бюджет: затраты в проде часто в 3–5 раз выше первых оценок DIY (стр. 148–151). Контроль (стр. 150): алерты на 50%, 80%, 100% бюджета; rate limiting против «атаки на кошелёк» и багов кода; каскад моделей
- Стоимость векторной БД растёт нелинейно с объёмом (стр. 148–151)

## 11. Если запускаю в продакшен (из прототипа)
- Качество плохое — 4 причины (стр. 132–135): 1) нет данных → следить за запросами, обновлять базу, стейджинг (новые данные сначала в тестовой коллекции); 2) слабый поиск → гибрид + reranker; 3) галлюцинации → модель с низким уровнем + коррекция; 4) плохой промпт → «не знаешь — скажи, не выдумывай» (стр. 135)
- Отчёт по прототипу (стр. 154–158): модели, как собирали данные, какие промпты сработали, где галлюцинации и задержки
- KPI (числа из примера, стр. 154–158): задержка 7.5 с → 4.5 с; аптайм ≥ 99.99%; уровень галлюцинаций ≤ 0.05; метрики точности контекста и релевантности
- Ресурсы: CPU/GPU, CI/CD, RBAC (стр. 154–158)
- После запуска: если после пика первых дней запросы падают — система медленная или отвечает плохо (стр. 154–158)
- Эталон (стр. 151–154): развязанные микросервисы. Загрузка: текст → нарезка → эмбеддинг → векторная БД и лексическая система. Запрос: эмбеддинг → параллельный поиск → reranking → маскирование PII → LLM → guardrails → ответ. Кэш на всех уровнях
- MLOps (стр. 32–33): CI/CD для данных и оценки; версионировать промпты, модели эмбеддингов, логику нарезки как код; трассировка каждого запроса; RBAC
- Обновление данных (стр. 98–100): не переиндексировать всё — искать изменённые/новые/удалённые; CDC (Change Data Capture) — триггеры или журнал транзакций; для real-time — параллелить, быстрые эмбеддинги, асинхронность. Не обновлять = система деградирует (стр. 99)
- Загрузка большими объёмами (стр. 94–95): оркестрация Apache Airflow (упавшую задачу перезапустить, не весь процесс); идемпотентность (повтор без дублей); наблюдаемость (мониторить зависшие и отброшенные документы)
- Пользовательский опыт (стр. 122–128): ссылки на источники прямо в тексте; показывать, что система сейчас ищет; выбор источников (только Google Drive, без Slack); 👍/👎 и комментарии; если данных нет — предложить другой путь; многошаговый диалог с памятью. Инструменты: assistant-ui, Streamlit, Gradio, vectara-answer
- Четыре столпа (стр. 128–129): надёжная загрузка → точный поиск → guardrails → детекция и исправление галлюцинаций

## 12. Если в документах таблицы, картинки, аудио, видео
**Таблицы** (стр. 264–275)
- Извлечь Vision-моделью → поячеечный OCR (данные не «перетекают» между колонками) и роли (шапка/данные) → нормализация (убрать валюты, «$ (1,000)» → число) (стр. 264–275)
- Инструменты (стр. 266): облачные Amazon Textract, Azure Document Intelligence, Google Document AI (сканы, рукописи); LlamaParse (Markdown); открытые Docling (IBM), Unstructured, Gmft (только таблицы)
- Решение «безголовых» чанков: таблица → JSON (строки с ключами = названия колонок) → краткое резюме → индексировать резюме → при запросе дать в LLM ВСЮ таблицу (стр. 269–270). Огромная таблица — отфильтровать колонки (стр. 270)
- Таблица на нескольких страницах (стр. 272–274): 1) страницы соседние; 2) совпадают число колонок и типы; 3) убрать повторные шапки; 4) склеить в один DataFrame до индексации

**Картинки** (стр. 276–291)
- Резюмирование (стр. 278–284): VLM пишет описание 4–6 предложений → чанк; оригинал в S3, ссылка в метаданных; при ответе — текст или файл Base64. Плюс: дёшево, работает с простыми LLM. Минус: упустило деталь — не найдёшь. Подходит для схем, графиков, документов с цифрами
- Общее пространство CLIP/SigLIP/ImageBind (стр. 284–291): картинка и текст в одном векторе, поиск по косинусу (стр. 286). Быстро, без описаний; плохо с точными цифрами и мелким текстом. Подходит для фото, каталогов, стилей
- Цитатой должен быть сам фрагмент картинки/видео, не ссылка (стр. 299)

**Аудио и видео** (стр. 291–297; номер диапазона у аудио сомнителен)
- Аудио: 1) транскрибация (Whisper, Chirp, Deepgram); 2) диаризация (кто говорит) — обязательна; 3) метки времени начала и конца для «глубоких ссылок»; 4) чанки (стр. 292). Без имён спикеров текст бесполезен (стр. 292)
- Видео — текст не передаёт действия в кадре. Три способа (стр. 294–297): 1) кадр раз в N секунд (подпись VLM или вектор CLIP); 2) клипы по 20 с с нахлёстом 10 с; 3) ключевые кадры (смена сцены), описание добавить к транскрипту
- Частота кадров (стр. 295): 1 FPS — базово; 2–5 FPS — быстрое движение; 1 кадр в 5–10 с — лекции и «говорящие головы»
- «Красная кнопка»: «нажмите это» + кадр. Без описания кадра запрос «как остановить машину» не найдёт (стр. 295)
- Тяжёлое: энкодеры и OCR дороже текстовых — параллельная архитектура (стр. 298)

## 13. Если делаю агента поверх RAG
- Агент = LLM как «мозг» + оркестрация + инструменты. Цикл: наблюдение → рассуждение/план → действие (стр. 218–223; цикл ReAct «рассуждай → выбери инструмент → действуй → посмотри результат» — стр. 218)
- RAG как инструмент: Retrieval-as-a-tool (инструмент даёт куски, агент синтезирует — больше контроля) и RAG-as-a-tool (инструмент возвращает готовый ответ с цитатами — стабильнее) (стр. 229)
- Названия инструментов: смысловые (`get_weather`, не `data_lookup`), типы аргументов и границы описать (стр. 230–231)
- Современные модели могут вызвать несколько инструментов сразу (стр. 231)
- Один агент быстрее на 30–50% и дешевле (стр. 221–223). Начинать с одного. Мультиагент, если: разные уровни безопасности; слишком много инструментов (агент путается, «размытие инструментов»); разные команды поддерживают части. Схема «оркестратор → рабочие» (рабочие друг с другом не говорят). Минус мульти: больше задержки и токенов, риск зацикливания (стр. 221–223)
- Ограничители обязательны: лимит итераций и бюджет (стр. 340); в примере «не более 5 итераций» — это пример составителя конспекта, в книге цифр нет (не из конспекта-книги)
- Для прода: таймауты, повторы, логирование всех вызовов, мониторинг, чтобы не зациклиться (стр. 240)
- Агент-цикл Agentic RAG (стр. 339–340): 1) расплывчатый запрос; 2) разбить на план; 3) вызывать инструменты; 4) после каждого шага оценить результат; 5) мало — новый запрос; 6) хватает — ответ. Минус: 2 с превращаются в 30 с+
- Долго-горизонтные задачи (много шагов) плохи — ошибки копятся; деньги и здоровье — человек подтверждает (human-in-the-loop) (стр. 224–228)
- MCP (стр. 232–236): отделяет «мозг» от инструментов; три основы — инструменты, ресурсы (ссылки на данные по URI), промпты-шаблоны. A2A (стр. 236–237): агенты общаются между собой через «карточку агента»
- Памятка по LangChain-агенту ReAct (стр. 237–239): RAG-конвейер → обернуть в инструмент с описанием → ReAct-агент (рассуждай + действуй) → сложный вопрос режется на два подзапроса
- LlamaIndex (стр. 240–245): `FunctionTool` → LLM → `FunctionAgent` с `system_prompt` → `agent.run` с `ctx` (история) → `stream_events()`. Для веб-поиска — агентские сервисы Tavily, Exa (отдают Markdown/JSON) (стр. 240)
- CrewAI (стр. 249–253): роли (`role`, `goal`, `backstory`) → `Task` с `expected_output` → зависимости через `context` → `Crew` (процесс `sequential`). Плюсы: меньше инструментов на агента, малые контексты, отказоустойчивость
- Vectara-агент (стр. 245–249): `upload_file` → `tool_configurations` → агент одним запросом → сессия
- Память агента (стр. 253–255): краткосрочная (скользящее окно истории); долгосрочная (векторная БД). Улучшения: консолидация сессий (сжимать историю в резюме), семантический поиск по старому. Риски: приватность (удаление), отравление памяти (вторая лёгкая LLM проверяет перед записью), устаревание (политика «затухания»)
- Сбои агентов (стр. 255–264): инструментальная/ответная галлюцинация, ошибки плана, не тот инструмент, остановка слишком рано или зацикливание. Контроль: трассировка (spans), расход токенов, задержка, доля передач человеку, успешность вызовов. Стандарт OpenTelemetry; Langfuse, Arize Phoenix, LangSmith
- Данные не копировать в одну векторную базу, а ходить за ними на место (federated retrieval) через инструменты-обёртки (MCP, SQL); компании это ломает комплаенс (стр. 340–341)
- Длинный контекст (1–10 млн токенов) RAG не отменяет: дорого, медленно (60 с, стр. 342), lost in the middle; RAG = фильтр до «шортлиста» (пример — нарративный чанк 2–4k токенов) (стр. 341–342)

## 14. Если думаю про графы знаний (KG) и GraphRAG
- Векторный поиск не справляется с: фактами по времени (кто был CEO в октябре 2022?), пересечением условий, многошаговыми вопросами (стр. 305–310)
- Термины: узлы (сущности), рёбра (связи), онтология (правила), схема (реализация в БД); языки Cypher, SPARQL (стр. 308–310)
- Два способа (стр. 310–316): 1) обогащение чанков — вектор нашёл чанк → по сущностям из него взять факты из графа → в LLM «чанк + факты»; 2) гибрид — LLM переводит вопрос в Cypher/SPARQL (зная схему) → точные узлы → смешать с векторными
- Выбор (стр. 317–319): семантические вопросы → обогащение (<1 мс, риск низкий, подходит для MVP); структурные многосвязные → граф (задержка и риск выше: LLM может написать неверный запрос, проверять синтаксис). Не брать гибрид граф-поиск, если вопросы в основном семантические
- Построение KG (стр. 319–322): 1) схема узлов и связей; 2) подготовка данных; 3) загрузка через `MERGE` (идемпотентно). Entity explosion: одна сущность — несколько узлов («007», «Bond») — нужна дедупликация
- Автоматизация (стр. 320–321): 1) найти сущности и тип; 2) связи (тройки: Apple, FOUNDED_BY, Steve Jobs); 3) сведение дублей. Только-LLM шумно: LLM → правила/модели → человек
- Entity linking (стр. 321–322): нормализация (lowercase), кандидаты (один тип, Jaro-Winkler, векторы); онтология = каноническое имя + алиасы; при низкой уверенности — человек; не одним алгоритмом
- Готовые онтологии (FIBO — финансы, DrugBank — медицина) экономят время, но привязывают к формату и лицензии; «более 50% подобных проектов проваливаются» (стр. 322–324)
- GraphRAG (Microsoft, стр. 324–328): 1) граф из текстов LLM; 2) сообщества; 3) иерархия резюме; 4) `local_search` (от seed-узлов 1–2 прыжка) и `global_search` (по сообществам). Цена индексации: 20 фильмов ≈ $6.32, 1800 фильмов > $560; 20 фильмов ≈ 45 мин на M4-Mac. Не для часто меняющихся данных; резюме не дословны — плохо для точных цитат
- Графовая БД (стр. 329–332): on-prem/регуляции → Neo4j, TigerGraph; нет экспертизы → managed (Neo4j Aura, Amazon Neptune); малый почти-только-чтение граф (< 10–20 ГБ) → встроенный (Kuzu, DuckDB). ETL: `MERGE`, батч-коммиты каждые 1000 узлов; `chunk_id` синхронизировать с векторным хранилищем; не грузить всё в одну транзакцию; бэкап и RBAC
- Обновление графа (стр. 332–335): CDC (Debezium) для структурных данных; event-driven для новых файлов; при слиянии дублей перенести связи к «выжившему», не оставлять «зомби-узлы»; устаревшее помечать `status:"inactive"` вместо удаления
- Нужен ли KG? Хватит ли 4 «да» из 6 (стр. 333–334): 1) повторяются multi-hop/временные запросы, где обычный RAG падает; 2) нужно 100% детерминированное обоснование (суд, медицина); 3) есть готовая онтология; 4) данные сами как граф (иерархии, цепочки); 5) есть кому поддерживать схему и ETL; 6) прирост точности связан с деньгами/риском/законом
- Таблица подходов (стр. 335–336): Standard RAG — дёшево, но плох в multi-hop и точных фактах/SKU; Keyword hybrid (вектор + BM25) — дёшево-средне, надо подбирать веса; KG-hybrid — дорого, для точных запросов с условиями; GraphRAG — очень дорого, для обзоров тем, без дословных цитат; Agentic RAG — для итеративных исследований, задержка и риск зацикливания

## 15. Если выбираю платформу или свой сервер
- Чек-лист вендора (стр. 146): API (стабильность, лимиты, батчи, OAuth/ключи); данные (форматы, слой трансформации); безопасность (шифрование, PII, SOC 2, HIPAA, GDPR); производительность (P95/P99, автоскейлинг, SLA); мониторинг; поддержка (время ответа при сбое)
- Много вендоров = ты координатор; «под ключ» — одна точка контакта (стр. 146, 145–149). Сборка из разных сервисов хрупкая: каждый компонент добавляет сложность, задержку и риск (стр. 145–149)
- Нужные навыки (стр. 147–148): ML, данные (ETL), DevOps/MLOps, безопасность; знания в LLM устаревают очень быстро
- DIY: полный контроль, но всё обслуживание на тебе; платформа даёт гибрид и reranking «из коробки», единый стандарт промптов (стр. 159–164). DIY кажется дешевле (только токены), но скрытые затраты делают TCO непредсказуемой (стр. 168)
- «RAG sprawl»: каждый отдел строит своё → хаос, дыры, дубли; платформа даёт единый путь, централизованное удаление PII, один патч на всех (стр. 167–168)
- Коннекторы (стр. 165–166): форматы, обновление, пропущенные файлы, синхронизация прав. DIY: Airbyte, LlamaIndex, LangChain (130–600+ коннекторов). Коннектор Gmail может не работать с Outlook
- Платформы для разработчиков: бесплатные уровни или подписки $50–$500/мес (стр. 168)
- Развёртывание (стр. 169–171): SaaS (быстро; HIPAA, GDPR, SOC-2); VPC (в AWS/Azure/Google, нужны MLOps); on-premises (полный контроль, GPU A100/H100, только open-weight — Llama 4, Mistral, DeepSeek, самому OCR/эмбеддинги/reranker/Kubernetes; air-gapped без интернета для сверхсекрета)
- Маленькие модели (SLM: «часто меньше 32 млрд, нередко 4 или 8 млрд») на обычном железе: локально/без интернета, без зависимости от чужого API (стр. 343); там же: вместо платы за токены — фиксированная плата за железо (flat fee)
- Vectara в примере (стр. 171–182): корпус → API-ключ (Personal, Query-only, Query+index) → файлы (сам OCR, нарезка, эмбеддинги) или JSON → запрос с гибридом (`lexical_interpolation`) и reranker одной командой
- Не привязываться к одному стеку или векторному хранилищу (стр. 347–349)

## Как применять с Витой
