# Polzer «RAG with Python Cookbook» — как делать (ЧЕРНОВИК)

Расшифровка: RAG = модель отвечает, опираясь на найденные в твоих документах куски (поиск + генерация).
Chunk (чанк) = кусок текста. Эмбеддинг = текст, превращённый в список чисел (вектор), по которому ищут «похожее по смыслу».
Все числа и шаги ниже — только из конспектов; «(стр. N)» — страница из конспекта.

## 1. Если хочу решить, стоит ли делать RAG
- Выбор задачи — шаги: 1) список проблем с неструктурированными данными (контракты, записи встреч, тикеты) 2) оценить каждую по «RAG-fit» (1–5) и «ценность» (1–5) 3) брать те, где обе оценки ≥ 4 (стр. 18)
- Не брать задачи, которые решает обычный regex (поиск по шаблону) или SQL-запрос (~95 % покрытия) — только лишняя сложность и цена (стр. 18)
- Простой конвейер НЕ годится для многошагового рассуждения и для смеси источников (SQL + вектор) (стр. 31)

## 2. Если хочу подготовить рабочее место
- Окружение — шаги: 1) Python 3.9+ (тестировалось на 3.10) (стр. 20) 2) `python3 -m venv .venv` и активировать 3) `pip install ...` 4) `pip freeze > requirements.txt` (стр. 23)
- Зависимости держать отдельно по главам (`requirements_chXX.txt`), не ставить всё сразу — конфликты версий (стр. 35, 36)
- Ноутбуки (Jupyter) — для экспериментов; НЕ для боевого кода: порядок ячеек сбивается, JSON тяжело сравнивать (стр. 23)
- Код от AI-помощника проверять: может быть неверным или небезопасным (стр. 21)
- Ключи — шаги: 1) `pip install python-dotenv` 2) файл `.env` в корне с ключами 3) в `.gitignore`: `.env`, `.venv`, `.vscode`, `env/`, `venv/` 4) `load_dotenv()` один раз, потом `os.getenv("OPENAI_API_KEY")` (стр. 24–26)
- `.env` — только для локальной работы; в боевой среде — менеджер секретов (AWS Secrets Manager, Azure Key Vault, HashiCorp Vault); не слать `.env` по почте/в чат (стр. 26)

## 3. Если хочу быстрый минимальный RAG (4 шага)
- Шаги: 1) нарезка ~1000 символов с перекрытием ~200 2) эмбеддинги OpenAI `text-embedding-3-small`, пачками по 100 кусков 3) хранение в Chroma (`PersistentClient`, коллекция, `ids/documents/embeddings/metadatas`) 4) поиск `top_k = 3` и ответ моделью с промптом «Отвечай только по контексту ниже» (стр. 27–31)
- Нарезка по умолчанию режет по абзацу `\n\n` или по `. `, чтобы не рвать мысль (стр. 27–31)
- Плохие куски в ответе — чинить на этапе ПОИСКА, а не генерации (стр. 27–31)
- Повторный запуск даёт конфликт ID — удалить `chroma_db` или сменить имя коллекции (стр. 27–31)

## 4. Если хочу выбрать фреймворк или голые библиотеки
- Типы библиотек (стр. 33): оркестрация (LangChain, LangGraph, LlamaIndex); модели/эмбеддинги (OpenAI, Anthropic, HuggingFace, Sentence-Transformers); векторы (Chroma, FAISS, Pinecone, Milvus, Weaviate); данные (pandas, PyPDF2, python-docx, Unstructured, openpyxl); мультимодальность (Pillow, pytesseract, MoviePy, pdf2image); поиск по словам (Rank-BM25); оценка (Ragas, Phoenix, LangSmith); веб (Streamlit, Gradio, Flask, Django)
- С фреймворком ≈ 100+ зависимостей, без ≈ 5–10 (стр. 33) — больше конфликтов и уязвимостей; для простого «вектор + LLM» фреймворк не подключать (стр. 33)
- При использовании LangChain/LlamaIndex: фиксировать версии и прятать их в небольшие «адаптеры» — API часто ломается (стр. 59–60)

## 5. Если хочу выбрать модель (LLM)
- Промпт для RAG — 4 части: роль, инструкция («только по контексту; если нет — скажи, что нет»), контекст, требования к ответу (напр. до 120 слов) (стр. 38–40)
- Слишком свободный шаблон — модель выдумывает; слишком жёсткий — отказывается отвечать (стр. 38–40)
- Уровни и цена за 1 млн входных токенов (стр. 41–43): сверхлёгкие 0,05–0,20 $; обычные 0,25–0,60 $; флагманы 1–5 $; «рассуждающие» 2–30 $
- Выбор — шаги: 1) требование к скорости 2) сложность (классификация — лёгкая; глубокий анализ — флагман) 3) сравнить цену в одном уровне у разных провайдеров 4) взять САМУЮ лёгкую, что подходит (стр. 40–44)
- Не ставить «рассуждающую» модель на классификацию; не переплачивать без замера выгоды (стр. 40–44)
- Gemini: тот же клиент OpenAI, меняются `base_url` и ключ; контекст до ≈ 1 млн токенов — для длинных документов; на коротких запросах OpenAI обычно быстрее (стр. 46–48)
- Anthropic (Claude): `pip install anthropic`, `client.messages.create(model, max_tokens, messages)`; консервативный вывод — право, код; медленнее и дороже при большом потоке (стр. 48–52)
- Локально через Ollama: `ollama pull <модель>`, клиент OpenAI с `base_url="http://localhost:11434/v1"`; на ноутбуке без GPU — модели ≤ 13 B, ~70 B нужно ≥ 16 ГБ видеопамяти; медленнее облака, зато конфиденциально (стр. 52–55)
- Строгий ответ-объект: схема Pydantic (описание полей) + `client.responses.parse(..., response_format=Схема)` — получаешь проверенный объект (стр. 55–58). Минус: задержка выше, жёсткая схема «зажимает» модель (стр. 55–58)
- Лимиты запросов (rate-limits) учитывать при больших объёмах (стр. 44–46)

## 6. Если хочу загрузить данные
- Общая схема: индексация (загрузка → эмбеддинги → векторная база), потом рантайм (поиск → ответ) (стр. 59–60)
- Word: `python-docx` — быстрый текст, теряет заголовки и списки; `Unstructured` (`partition_docx`) — сохраняет тип элемента (Title, NarrativeText, ListItem), нужен для разных весов заголовков, но дольше и больше памяти (стр. 61–63)
- PDF цифровой: `PyPDF2.PdfReader`, по страницам текст + метаданные; сканы так НЕ читаются — нужен OCR (стр. 64–66)
- Таблицы Excel/CSV, 3 подхода (стр. 66–70):
  1) строка → предложение (row-to-text): нет агрегаций
  2) вся таблица в промпт (Markdown): только маленькие, дорого
  3) text-to-SQL (модель пишет SQL): нужна БД и разбор результата
  Выбор зависит от размера таблицы и типа вопросов (найти строку или посчитать)
- PostgreSQL: `SQLAlchemy` + `psycopg2-binary`, `pd.read_sql`; годится и как векторное хранилище (pgvector) (стр. 71–72)
- Аудио: Whisper API (`whisper-1`) — быстрый старт, 80+ языков; Whisper локально — данные не уходят наружу, дешевле на больших объёмах; GPT-4o точнее, но дороже за минуту (стр. 73–74). Если политика не позволяет слать аудио наружу — только локально (стр. 73–74)
- OCR Tesseract: ставить программу + `pdf2image`, `pytesseract`, `Pillow`; `pdf2image` требует Poppler; сохранять путь PDF, номер страницы (стр. 75–78). Хуже на сложных макетах, таблицах, рукописи (стр. 77)
- Текст с картинки мультимодальной моделью: картинку в base64, промпт «Extract the text…», `max_tokens=500` (стр. 79–81). Может «галлюцинировать» цифры на плохих сканах (стр. 79–81)
- Описание картинки (для поиска/alt-текста): промпт «ассистент для слабовидящих», `max_tokens=150`; хранить с путём файла и номером страницы (стр. 82–84)
- Таблицы из PDF: `unstructured.partition.pdf` → строка → резюме моделью, `temperature=0.7`, `max_tokens=150` (стр. 84–87). НЕ для справочных таблиц (каталоги, прайсы), где нужен точный поиск по ячейкам (стр. 84–87)
- Сложный PDF (текст + картинки + таблицы) — шаги: 1) Poppler 2) Tesseract и `OCR_AGENT=tesseract` 3) `partition_pdf(..., extract_images_in_pdf=True)` 4) разделить элементы по типам 5) текст/заголовки — рекурсивная или смысловая нарезка; картинки — OCR или описание моделью; таблицы — текст + резюме (стр. 88–90). Если картинка уже описана в соседнем абзаце — не обрабатывать дважды (стр. 88–90)
- Видео — шаги: 1) `moviepy` 2) кадр каждые 10 сек, 3) аудио-кусок между метками в MP3 4) Whisper по аудио 5) описание кадров моделью 6) эмбеддинги + метаданные (время начала, путь) (стр. 91–96)
  Способы нарезки видео: фикс. интервал — лекции; детекция сцен — фильмы; по транскрипту — встречи, интервью; по главам, если есть (стр. 81 — номер в конспекте не совпадает с 91–96)
  Слишком короткие интервалы — дорого; слишком длинные — теряется детализация (стр. 91–96)

## 7. Если хочу улучшить данные до нарезки
- Метаданные (автор, дата, путь, размер, число страниц, длина текста) хранить рядом с вектором — позволяет фильтровать до смыслового поиска (стр. 99–103)
- Метаданные через модель + Pydantic: ≈ несколько минут и 1–5 $ на 1000 документов (стр. 103). Пустое поле в PDF — проверять до запроса (стр. 99–103)
- Раскрыть сокращения: `re.sub` по словарю («NLP → Natural Language Processing (NLP)») или модель с просьбой раскрыть и коротко пояснить (стр. 104–108). Не раскрывать общеизвестные (HTTP) (стр. 104–108)
- Гипотетические вопросы к кускам — шаги: 1) нарезать 2) на каждый кусок 5 вопросов от модели 3) индексировать вопросы 4) запрос сравнивать с вопросами, но модели отдавать исходный кусок (стр. 109–112). НЕ для FAQ и когда время индексации критично (стр. 109–112)

## 8. Если хочу нарезать текст (chunking)
- По символам: окно + перекрытие, `step = max(1, size - overlap)`; пример 100/20; перекрытие улучшает контекст, но раздувает хранилище; для текста со структурой не годится (стр. 113–115)
- Рекурсивная (`RecursiveCharacterTextSplitter`): режет по абзацу → переносу строки → пунктуации → пробелу; пример `chunk_size=200`, `chunk_overlap=0` (стр. 116–119). Для документов с чёткими абзацами, формат заранее неизвестен (стр. 116–119). Не для разметки (Markdown, LaTeX, HTML) (стр. 116–119)
- По разметке: `.py` → `PythonCodeTextSplitter(500, 50)`; `.tex` → `LatexTextSplitter(500, 50)`; `.md` → `MarkdownHeaderTextSplitter` с уровнями `#`, `##`, `###` (в куске поля header_1..3) (стр. 119–122). Не для обычного текста и не для PDF/Word после перевода в чистый текст (стр. 119–122)
- Смысловая (`SemanticChunker`, `percentile`, порог 90): для расшифровок и чатов без разделителей (стр. 122–124). Минусы: два прохода эмбеддингов, 0,02 $ за 1 млн токенов, пакет экспериментальный — в бою лучше свой чанкер по исходному коду LangChain (стр. 122–124)
- Агентная (LLM делает «пропозиции» — самостоятельные утверждения): шаблон `hub.pull("wfh/proposal-indexing")`, `with_structured_output`; слияние похожих при косинусе > 0,9 (стр. 126–129). Цена: 30–60 мин и 15–40 $ на 500 фрагментов, 2–3 вызова модели на кусок (стр. 129). Не для больших корпусов и реального времени; не нужна, если абзацы уже самостоятельные (стр. 126–129)
- Размеры из примеров книги: 1000/200 (мини-RAG), 200/0, код 500/50, окно-соседи 250 токенов — это примеры, не правило (стр. нет в конспекте: общего «лучшего размера»)

## 9. Если хочу эмбеддинги
- Получить: OpenAI `text-embedding-3-small` (1536 чисел) или открытая `all-MiniLM-L6-v2` (384) (стр. 131–135)
- Таблица (стр. 132): text-embedding-3-small — 8191 токен, 1536; voyage-large-2-instruct — 16000, 1536; Google text-embedding-005 — 2048, 768; all-MiniLM-L6-v2 — 512, 384. Кусок не должен превышать лимит токенов (стр. 131–135)
- OpenAI дороже, открытые менее точны, но локальны (стр. 131–135)
- Проверка глазами: PCA до 2 чисел и график; только для разработки, в бою — метрики (precision@k). UMAP/t-SNE точнее по соседям, но медленнее (стр. 136–139)
- Близость: косинусное сходство `dot(a,b)/(norm(a)*norm(b))`; манхэттен не рекомендован; косинус не учитывает длину (стр. 140–144)
- Выбор модели эмбеддингов — шаги: 1) смотреть рейтинги MTEB (для многоязычного — MIRACL) 2) решить, облако или локально 3) 50–100 типовых запросов, замерить релевантность на базовой модели 4) при нужде попробовать `text-embedding-3-large` 5) время ответа < 100 мс для интерактива 6) посчитать стоимость (пример 0,02 $ за 1 млн токенов) (стр. 145–146)
  Правила (стр. 146): > 1 млн документов или > 1000 запросов в день — приоритет скорость и цена; юридика/медицина — большие модели; реальное время — < 50 мс. +2 % точности редко стоят двойной цены; бенчмарков мало — тестировать на СВОИХ данных
- CLIP (картинка и текст в одном пространстве, `openai/clip-vit-base-patch32`): плохо читает текст на картинке; для RAG проще описать картинку словами и взять обычные текстовые эмбеддинги (стр. 147–150)
- Классификатор по эмбеддингам (Random Forest) для маршрута запроса в тему: нужно минимум 100–200 размеченных кусков на категорию; при пересекающихся темах лучше фильтр по метаданным; ошибка классификации теряет нужные документы (стр. 154, 151–152). Не стоит, если документов < 10 000 (стр. 154 — по конспекту, формулировка двусмысленна)

## 10. Если хочу гибридный поиск (слова + смысл)
- Вариант Python — шаги: 1) BM25 (`rank-bm25`, `BM25Okapi`) → ранг по словам 2) эмбеддинги → ранг по смыслу 3) Reciprocal Rank Fusion: `1/(k+ранг_слова) + 1/(k+ранг_смысла)`, k = 60 4) сортировать по сумме (стр. 155–159)
- k = 10–20 — упор на верхние места; 60–100 — учитываются и нижние (стр. 159)
- Подходит при точных кодах (SKU, ICD-10, URL) вместе с живыми вопросами; НЕ нужен для чисто «естественных» запросов без терминов (стр. 158–159)
- Вариант SQL в PostgreSQL — шаги: 1) колонка `tsv = to_tsvector(текст)` 2) `text_score = ts_rank(tsv, plainto_tsquery(...))` 3) `vector_score = 1 - (embedding <=> запрос)` 4) `hybrid_score = 0,5·text + 0,5·vector` (можно 0,7/0,3) 5) `WHERE tsv @@ plainto_tsquery(...)`, `ORDER BY hybrid_score DESC LIMIT 10` (стр. 188–190)
  Плохой полнотекстовый индекс портит итог; не использовать, если смысл важнее точных слов; подходит для права, техдокументации, медицины (стр. 190)

## 11. Если хочу выбрать векторную базу
- Дерево выбора (стр. 162–163): 1) живой сервис не нужен, только офлайн → FAISS/Annoy (или Chroma для локального прототипа) 2) живой, и векторы должны жить рядом с бизнес-данными → имеющаяся СУБД (PostgreSQL+pgvector, MongoDB, Redis, Cassandra) 3) миллионы–десятки миллионов, фильтры, доступы → Weaviate, Qdrant, Milvus, Pinecone 4) сверить практические вопросы
- Таблица 6-1 (стр. 162–163): данные можно в облако → Pinecone или облачный PostgreSQL; уже есть PostgreSQL/MongoDB → pgvector/MongoDB; нужен и поиск по словам → Elasticsearch, OpenSearch, Weaviate; минимум настройки → Chroma или Pinecone
- Выбирать по рабочему процессу, не по бенчмаркам; для нескольких тысяч векторов тяжёлый сервис не нужен (стр. 164)
- FAISS: `pip install faiss-cpu`, `float32`, `IndexFlatL2(размерность)`, `index.add`, `index.search(q, k)`; всё в памяти, нет метаданных и доступов; для разового анализа (стр. 165–168)
- Chroma: `PersistentClient(path)`, `get_or_create_collection`, `collection.add(embeddings, documents, ids)`, `collection.query(query_embeddings, n_results=3)`; режимы Ephemeral (память) и Persistent (диск); по умолчанию сама использует `all-MiniLM-L6-v2` (стр. 169–172). Не для > ≈ 300 000 векторов, контроля доступа, задержек в доли миллисекунды — тогда pgvector или управляемая база (стр. 172)
- pgvector — шаги: 1) PostgreSQL + pgvector (Docker `ankane/pgvector`) 2) `psycopg2-binary` 3) `CREATE EXTENSION IF NOT EXISTS vector;` 4) таблица с `embedding vector(1536)` 5) вставка эмбеддингов (стр. 173–176). Без расширения тип `vector` не работает; на миллиардах векторов медленнее специализированных баз (стр. 176)
- Поиск в pgvector: операторы `<=>` косинус, `<->` евклид, `<#>` скалярное произведение, `<+>` манхэттен; сходство = `1 - (embedding <=> запрос)` (стр. 177–180). Без индекса — полный перебор; не делать тяжёлые JOIN вместе с `<=>` без предфильтра (стр. 181)
- Индексы для ≥ 100 000 векторов (стр. 181–185):
  IVFFlat — `WITH (lists = 30)`, `SET ivfflat.probes = 3`
  HNSW — `WITH (m = 16, ef_construction = 200)`, `SET hnsw.ef_search = 50` (m ≈ 16–64, ef_search ≈ 10–50)
  Пример замера: полный перебор ≈ 85 мс, HNSW ≈ 13 мс (стр. 183–184). Проверять `EXPLAIN ANALYZE`, для проверки отключать `SET enable_seqscan = off` (стр. 183). При < 100 тыс. строк индекс часто не даёт выигрыша; HNSW хранит граф в памяти (стр. 185)
- Как устроены индексы: IVF — найти ближайший центр раздела, искать внутри; возможна ошибка, если лучший вектор в соседнем разделе (стр. 186). HNSW — многослойный граф: наверху «магистрали», внизу «улицы»; памяти больше (стр. 186–187)
- Метаданные-фильтр (JSONB): `metadata JSONB`, `WHERE metadata->>'topic' = %s ORDER BY similarity DESC LIMIT 5` (стр. 195–197). Не нужен при однородных данных или без метаданных (стр. 198)

## 12. Если хочу улучшить поиск (приёмы)
Номера страниц в этом блоке у конспекта 6 местами сбиты — см. «Не дочитано».
- HyDE (гипотетические документы) — шаги: 1) модель пишет 3 документа в стиле корпуса (схема Pydantic) 2) эмбеддинги этих текстов 3) поиск настоящих документов 4) гипотезы в ответ НЕ включать (стр. 198–187: номер сомнителен; стр. 200). Нужен, когда стиль вопросов не похож на стиль базы («починить машину» против «сервисный бюллетень»); не нужен при похожем стиле или когда важны задержка и цена
- Multi-query — шаги: 1) 2–3 перефразировки вопроса (стр. 204) 2) поиск по каждой 3) объединить результаты 4) отдать модели (стр. 188–191: номер сомнителен). Задержка и цена растут почти в N раз; не для узких вопросов или жёсткого времени (стр. 205)
- Маршрутизация запросов — шаги: 1) список источников (напр. 3: общие знания по футболу, по теннису, SQL со свежими результатами) 2) Pydantic с `Literal[...]` — модель выбирает только название 3) системный промпт 4) вызвать функцию выбранного источника (стр. 206–209). Добавляет 0,5–2 сек; не нужна при одном источнике; при размытых вопросах ошибается (стр. 195 — номер сомнителен)
- Auto-merging (листья и родители) — шаги: 1) листья по 250 символов, родитель = 4 листа ≈ 1000 символов 2) таблица: `leaf_node_id, leaf_chunk, parent_node_id, parent_chunk, leaf_chunk_embedding` 3) искать по листьям 4) если ≥ 2 листа одного родителя в топе — отдать модели родителя (стр. 211–214). Не для плоских документов; хранилище вдвое больше (стр. 214)
- Окно соседей (sentence window) — шаги: 1) куски ≈ 250 токенов, `chunk_id` растёт по порядку документа 2) найти ближайший кусок 3) взять по 1 (иногда 2) соседа с каждой стороны ≈ 750 токенов 4) отдать модели (стр. 215–217). Не при больших кусках (> 500 токенов) и не для FAQ; промпт растёт (стр. 217)
- Reranking (второй проход) — шаги: 1) собрать кандидатов из всех источников 2) модель ставит оценку 1–5 каждому (Pydantic) 3) оставить топ (часто 3; общий совет 5–10) (стр. 218–205: номер сомнителен; стр. 219, 220). Применять при ≥ 20 шумных кандидатах; пропускать при одном хорошем источнике или если цена вызова не оправдана (стр. 220). Это второй шаг, а не замена быстрого первичного поиска (стр. 220). Готовые: LangChain `RankLLM Reranker`, LlamaIndex `ColbertRerank`, Haystack `SentenceTransformersSimilarityRanker` (стр. 220)
- Сложный вопрос на подвопросы — шаги: 1) модель режет вопрос (`response_format=Questions`) 2) на каждый поиск и ответ 3) финальный промпт собирает ответы в один (стр. 221–224). 2 вызова модели + N поисков; для «сравни X и Y»; не для простых вопросов (стр. 223)

## 13. Если хочу агента
- Свой инструмент: обычная Python-функция с подробным docstring (цель, параметры, типы, результат) — это «договор» для модели; один инструмент — одна задача; готовое (веб-поиск, запуск кода) не писать заново; обрабатывать таймауты и лимиты API (стр. 229–230)
- 5 схем (стр. 230–235): цепочка (выход одного — вход другого); маршрутизация (удобна при 5–10 типах сценариев); параллельные задачи (упор в лимит токенов API); оркестратор + исполнители (больше задержка); оценщик + оптимизатор (ставить максимум итераций). Выбор — зависят ли шаги друг от друга
- Фреймворк (стр. 235–239): no-code (Copilot Studio, Zapier) — 2–5-шаговые внутренние процессы, мало контроля; агентные библиотеки (OpenAI Agents SDK, LangGraph) — баланс; с нуля — нужны сильные разработчики. Не начинать с тяжёлого, если нужен быстрый прототип; каждая зависимость — больше поверхность атак
- Function calling без фреймворка — шаги: 1) функции с docstring 2) словарь `tools` (`type: function`, имя, описание из `__doc__`, схема параметров) 3) запрос с `tools=tools` 4) читать `tool_calls`, вызывать функцию 5) цикл, пока `finish_reason == "tool_calls"` (стр. 239–244). Каждый вызов — лишний круг к модели; арифметику модели не доверять (стр. 244)
- asyncio: `async def`, `await asyncio.gather(...)`, `asyncio.run(main())`, для модели — `AsyncOpenAI`; время ≈ самый долгий вызов; не для зависимых шагов; сложнее отладка и частичные ошибки (стр. 245–250; 235 для предупреждения)
- Агент-переговорщик (Agents SDK + Chroma): `@function_tool` над `query_database`; агенты продавец, клиент, модератор (`as_tool`); запуск `Runner.run`; трассы видны в консоли OpenAI (стр. 250–258). Каждая передача = вызов модели, стоимость растёт с числом ходов; не при строгой задержке (стр. 258). Перед перезаписью Chroma удалить старую папку (стр. 252)
- MCP (готовые инструменты без своего кода): `pip install openai-agents`, сервер Playwright через `npx @playwright/mcp@latest`, подключение `MCPServerStdio`; таймаут по умолчанию 5 сек, в примерах 30 (браузер) и 60 (файлы); на Windows бывают ошибки — лучше Linux/WSL; нужен Node.js (стр. 259–264)
- LangGraph — шаги: 1) State (`TypedDict`, `messages` с `add_messages`) 2) инструменты `@tool` + Pydantic-схемы 3) `llm.bind_tools([...])` 4) узлы `call_model`, `call_tool` 5) условный переход: есть `tool_calls` — в инструменты, иначе конец 6) `StateGraph`, `add_node`, `add_conditional_edges`, `add_edge("tools","llm")`, `compile()` (стр. 264–272). Не для простых линейных цепочек; следить за бесконечными циклами; код сильно привязан к графовой модели (стр. 272)

## 14. Если хочу граф знаний (Neo4j) для контрактов
- Модель: узлы `Company`, `SLA`, `Clause`, `ClauseType`; связи `HAS_CLAUSE`, `NEXT`, `OF_TYPE` (стр. 277–284)
- Шаги: 1) Neo4j + `pip install neo4j python-dotenv`, доступы в `.env` 2) ограничения уникальности (`CREATE CONSTRAINT ... REQUIRE ... IS UNIQUE`) 3) разобрать файл по заголовкам `##` в пункты (id вида `{sla_id}_C{idx}`) 4) записать через `MERGE` 5) тип пункта по ключевым словам 6) проверить запросом (стр. 277–284). Без ограничений будут дубли; `.env` не в репозиторий

Эмбеддинги делать один раз и обновлять при новых пунктах
- Оптимизация графа (стр. 295–296; 297–298): сначала собрать базовый граф и замерить, потом по одной добавлять: резюме пунктов (`gpt-4o-mini`, `max_tokens=120`, `WHERE cl.summary IS NULL`), агрегаты (число пунктов по типам), эмбеддинги уровня SLA. После каждой — проверять скорость, токены, точность. Исходный текст пункта хранить и давать в итоговый ответ (резюме только фильтруют/ранжируют). Минус: больше хранилища и времени загрузки, нужна синхронность

## 15. Если хочу оценить RAG
- Оценка нужна, иначе улучшения — догадки; тестовые вопросы — как у реальных пользователей, но не дословно из данных (стр. 299–300)
- Выбор метрик — шаги: 1) есть эталонные ответы → сравнение ответов 2) есть размеченные куски → precision/recall поиска 3) нет ни того, ни другого → faithfulness, релевантность, связность 4) минимум две метрики: одна на поиск, одна на генерацию (стр. 303–304). Группы: генерация (faithfulness, correctness, coherence, fluency, safety), поиск (recall, precision, F1), общие (скорость, токены). Нельзя оценивать только одну часть
- Люди (стр. 307–309): два ответа рядом и ранжирование; или палец вверх/вниз + текст при минусе; пассивно: время, ID пользователя, лог запросов, найденные документы; задержку мерить `time` на каждом этапе. Дорого и медленно — для целевых проверок после крупных изменений; оценки у людей расходятся
- Синтетический тест (стр. 310–315): взять случайные куски, модель пишет «естественный фактологический» вопрос + ответ (Pydantic); хранить `question, answer, context`. Нужно 50–100 пар (для прототипа хватит 5); вручную проверить 10–20. Вопросы слишком простые; не оценивают тон, ясность, диалог; при обновлении знаний — пересоздать
- Context Precision@k (стр. 316–322): на каждый найденный кусок судья-модель даёт verdict 1/0 + причину; precision = сумма вердиктов / k; добавлять ε = 1e-10 против деления на ноль. Не использовать только BLEU/ROUGE; при слишком большом k шум — подбирать k по precision
- Faithfulness (держится ли ответ на контексте) (стр. 323–329): 1) разбить ответ на утверждения 2) судья: поддержано контекстом или нет 3) доля поддержанных. Цель ≥ 80 % в бою; < 70 % — серьёзные выдумки. Высокая верность не значит, что ответ по делу; слишком строгая модель утаивает нужное — смотреть вместе с релевантностью
- Answer relevancy (стр. 330–336): 1) по ответу модель придумывает N = 3 вопроса 2) эмбеддинги вопросов и исходного 3) среднее косинусное сходство 4) «уклончивый» (noncommittal) ответ → 0: жёстко `score = среднее × int(нет уклончивых)`, мягко `среднее × (1 − доля уклончивых)`. Пример высокой оценки 0,87 (стр. 335). Одним косинусом не видно неполных ответов — нужна ещё точность (стр. 336)

## 16. Если хочу сделать веб-приложение (Streamlit)
- Streamlit перезапускает весь скрипт при каждом действии: ≈ 50 одновременных пользователей; для тысяч — Django/Flask/FastAPI (стр. 337)
- Минимум: `pip install streamlit`, файл `streamlit_app.py`, `streamlit run ...`, порт 8501 (стр. 338–340)
- Чат — шаги: 1) `st.chat_message`, `st.chat_input` 2) `st.session_state["messages"] = []`, если нет (иначе KeyError) 3) вывести историю циклом 4) на новый ввод — сохранить, вызвать RAG, сохранить и показать ответ (стр. 340–345, 348)
- Правила (стр. 349): состояние хранить в `session_state`; тестировать в двух браузерах (утечка состояния между пользователями); скрипт Streamlit < 100 строк, логику — в отдельный модуль; `print` идёт не по порядку — отладчик VS Code

Цена в 10–100 раз выше обычного извлечения; для 100 страниц ≈ 0,05 $ (обычное) против 0,50–2,00 $ (мультимодальное) (стр. 354). Только когда есть таблицы, картинки, формы; не для чисто текстовых PDF и не для тысяч страниц; проверять Pydantic-схемой — модель может выдумать поля или пропустить страницы (стр. 354–355)
- Text-to-SQL через Vanna AI + Chroma + SQLite (стр. 355–360): `pip install vanna chromadb`, класс `MyVanna(ChromaDB_VectorStore, OpenAI_Chat)`, обучить на DDL (`SELECT sql FROM sqlite_master`), `generate_sql` → `run_sql` → ответ моделью по данным. Обучать можно 4 видами данных: DDL, документация, SQL-примеры, пары вопрос+SQL (стр. 358). Сначала показывать пользователю SQL (стр. 360). Могут выдумать имена колонок при неполной документации; запросы на > 5 таблиц — таймауты или ошибки; не давать, если пользователь не может проверить SQL; для строгой повторяемости — агент с шаблонами запросов (стр. 360–361)
- Деплой Docker + AWS (стр. 361–365): файлы `Dockerfile`, `requirements.txt`, `streamlit_app.py`, `entrypoint.sh`; `FROM python:3.9-slim`, `EXPOSE 8501`; `docker build -t ... .`, `docker run -p 8501:8501 ...`; потом AWS ECR (`aws ecr create-repository`) и ECS Fargate (≈ 30–40 $/мес за 1 vCPU + 2 ГБ) (стр. 364); альтернативы Google Cloud Run, Azure Container Apps (стр. 363). Ограничить число задач в ECS, иначе неожиданный счёт; ключи не зашивать в образ (утечка через реестр); без IaC (Terraform/CDK) и CI/CD (GitHub Actions) конфигурация «плывёт» (стр. 364–365)
