# Loop Engineering Playbook — как делать (черновик)

Источник: конспекты 8 частей книги (`C:\Users\User\knigi_kupleno\glubokiy\loop_engineering_playbook_01..08.md`).
Правило: всё ниже — из конспектов; «(не из конспекта)» — мелкая добавка. Номер в скобках — страница по конспекту.
Цены и названия моделей в книге — 2026 года, считать ориентиром, не истиной.

Цикл агента (loop) = агент сам крутится: смотрит → думает → действует → проверяет цель, пока не готово (стр. 6–12).

## 1. Если хочу построить цикл агента — шаги
- Основной цикл: 1) задать MAX_STEPS (потолок шагов) 2) в каждом шаге: собрать данные → подумать → выбрать действие → выполнить → обновить состояние 3) если «решено» — выйти 4) если шаги кончились — передать человеку (`escalate_to_human`) (стр. 6–12)
- Без MAX_STEPS цикл бесконечный; пример потерь: 20 шагов × $0.05 = $1 за запуск, при 10 000 одновременных запросов = $10 000 в минуту (стр. 6–12)
- Любая запись (возврат, отправка, запись файла) сначала проверяет «отпечаток» (fingerprint) — не делали ли уже. Пример беды: 2 400 дубликатов возврата (стр. 6–12; по книге: 2 400 дублей за 18 минут, убыток $340 000)
- Четыре части цикла (как термостат): датчик (что видим) → контроллер (LLM решает) → исполнитель (инструменты) → обратная связь (близко ли к цели) (стр. 21–28)
- Агент как конечный автомат: IDLE → THINKING → ACTING → EVALUATING → SUCCEEDED / FAILED / ESCALATED (стр. 21–28)
- Логировать каждую траекторию (путь шагов), смотреть, растёт ли качество; при отклонении искать: переполнение окна (число ~100 K токенов в книге не найдено), неверный сигнал оценки, повтор состояний (стр. 21–28)
- Проверять только итог нельзя: так пропускается ~80 % ошибок в промежуточных шагах (стр. 21–28)
- «Кодекс» (CREED): 1) MAX_STEPS обязателен 2) каждое действие в журнал 3) любой сбой — восстановить или передать человеку 4) стоимость — жёсткое ограничение 5) «готово» только после мониторинга в работе (стр. 21–28)
- Минимальный ReAct-агент ≈ 50–70 строк: цикл по MAX_STEPS, вызов модели с инструментами, ответ без вызова инструмента — финал (стр. 314; код цикла — стр. 30–31)

## 2. Если хочу ReAct (мысль → действие → наблюдение) — шаги
- 1) задать модель, инструменты, MAX_STEPS 2) в шаге: модель пишет мысль (THOUGHT) → вызывает инструмент (ACTION) → результат (OBSERVATION) идёт в историю 3) нет вызова инструмента = финальный ответ 4) шаги кончились — отдать частичный ответ (стр. 30–40)
- Мысль стоит 50–100 токенов (≈ $0.001 за шаг) и снижает ошибки на 20–30 % (стр. 30–40)
- Защита от повтора: хранить «имя инструмента + аргументы»; если вызов был — ответить «Ты уже пробовал именно это. Попробуй иначе» (стр. 30–40)
- Проверка бюджета ДО каждого вызова модели: расход > 90 % бюджета — стоп; 10 % оставить на финальный ответ (стр. 30–40)
- Типичные сбои и лекарство (стр. 30–40):
  - тот же вызов 3+ раза → хеш-проверка + «попробуй иначе»
  - ответ без доказательств → требовать минимум доказательств перед финалом
  - один инструмент всегда → перетасовать порядок, «рассмотри все инструменты»
  - выдуманный инструмент → проверять имя до запуска
  - качество падает после N шагов → сжимать состояние
  - уход в сторону → «держись исходного вопроса»
- Не делать: MAX_STEPS = 10 или 20 «с потолка» без анализа; ставить чуть выше 95-го перцентиля обычной длины запуска (+30 % запас) (стр. 13–20; 30–40)

## 3. Если задача большая — «план и выполнение»
- Шаги: 1) сильная модель (Opus-класс) пишет план 2) средняя (Sonnet-класс) выполняет шаги 3) после КАЖДОГО шага дешёвая (Haiku-класс) отвечает «CONTINUE» или «REPLAN» 4) в конце — синтез (стр. 41–45; 46–49)
- План 3–7 шагов, каждый — одно предложение с критерием успеха (стр. 41–45; 49)
- Фазы: 1 — параллельные независимые шаги; 2 — последовательные; 3 — условные ветки; 4 — синтез. Для каждой фазы — критерий успеха и условие перепланирования (стр. 46–49)
- Цифры: ≈ $0.12 против ≈ $0.25 у ReAct, экономия ≈ 52 % на задачах > 5 шагов (стр. 46); параллель режет задержку на 40–60 % (стр. 49)
- Не делать: игнорировать результат, противоречащий плану (STALE PLAN); план слишком детальный (ломается) или слишком общий (исполнитель теряется) (стр. 41–45)

## 4. Если хочу сделать инструменты — шаги
- 5–15 инструментов; при > 30 точность выбора заметно падает (стр. 50–67; 53)
- Описание: короткое имя; «когда использовать / когда НЕ использовать»; типизированные параметры; пример. Точность выбора растёт на 30–40 % (стр. 53)
- Ошибки инструмента возвращать структурой: успех / ошибка / сообщение (стр. 52)
- Результат инструмента сжимать до лимита 2 000 токенов (обрезка + пометка про продолжение, суммаризация, обрезка списка) (стр. 58–59)
- Каждый инструмент тестировать отдельно: обычный ввод, пустой, SQL-инъекция, таймаут, неверная категория (стр. 61–62)
- 10 шаблонов: читать до записи; ворота подтверждения; постраничность; единая «обёртка» ответа; группировка; ограничитель частоты; проверка схемы вывода; журнал действий; пробный запуск (dry-run); суммаризация результата (стр. 60)
- Ещё приёмы (стр. 287–289): лёгкая модель выбирает инструмент (экономия 50–70 %); запасной инструмент; проверка аргументов до запуска; кэш одинаковых вызовов (15–30 % попаданий); ограничитель частоты; песочница (код в Docker, файлы в ограниченной папке, БД только чтение); описание инструмента в промпт только когда нужен (экономия 40–60 %); «сначала только читать»; идемпотентные инструменты; проверка здоровья инструментов до цикла; сжатие большого вывода (500 строк → 3 метрики, экономия 60–80 %); инструмент подтверждения перед необратимым

## 5. Если хочу остановку и защиту от зацикливания — шаги (стр. 284–286)
- Bounded Loop: жёсткий потолок 10–25 шагов; без него «сожжёт $50 за минуту»
- Early Exit: после каждого шага «цель достигнута?» → выйти; экономия 30–50 %
- Cost Circuit Breaker: суммарные токены/деньги > бюджета (пример $0.50 за запуск) → выйти с лучшим промежуточным результатом
- Convergence Check: новый вывод почти как прошлый (сходство по эмбеддингам ≥ 0.95) → стоп
- Oscillation Detector: «отпечаток» состояния встречался в последних 5 шагах → вставить «выбери другой подход»
- Timeout Guard: потолок по часам (пример 5 мин) независимо от шагов; вернуть лучший частичный результат
- Checkpoint: сохранять полное состояние каждые 3–5 шагов, после падения продолжить с него
- Nested Loop: у подзадач свои лимит шагов и бюджет
- Warmup: 1–2 дешёвых шага оценить сложность; Cooldown: финальная проверка (ловит 10–15 % ошибок, пропущенных циклом)
- Adaptive Step Limit: старт ≈ 20; через 5 шагов ≥ 80 % сделано → оставить 3; ≤ 20 % → до 25
- Ещё: Priority Loop (при нехватке бюджета откладывать мелкое); Parallel Loop (ускорение 60–80 %); Backoff Loop (паузы 0→1→2→4 с, максимум 30 с)
- Предупреждения: не ставить слишком высокий MAX; Early Exit без Convergence Check может вернуть неполный ответ (в книге не найдено, добавка)

## 6. Если хочу проверку шага и защиту — шаги
- Проверки качества (стр. 282): самокритика; оценка по 4 осям (точность, полнота, ясность, формат) 1–10; второй LLM ищет дефекты; проверка источников; проверка JSON по схеме с повтором при ошибке; фильтры запрещённого; проверка противоречий; уверенность 0–1 (< 0.7 → человек, > 0.9 → авто); вычистка личных данных ([EMAIL_1]); неизменяемый журнал; пауза при резком росте правок (> 5 файлов, > 20 записей); пробный запуск без побочных эффектов; канарейка (5 % трафика на новую версию, сравнение 24–48 ч); «стоп-кран» (kill switch), проверять раз в квартал
- Не делать: авто-исправление при обнаружении предвзятости (нужен человек); полагаться на один фильтр (в книге не найдено)
- Самокоррекция: критика ≤ 2 раундов; в критике «APPROVED» → готово; стоимость критики ≈ как генерации, два раунда ≈ втрое — только для важного (стр. 148–149)
- Слой безопасности (стр. 155–157): требуют подтверждения — delete_file, send_email, make_payment, modify_permissions, deploy_to_production, update_database, create_account; запрещены навсегда — format_disk, drop_database, rm_rf, disable_firewall, expose_credentials; лимит выгрузки данных 10 МБ; проверка на prompt-инъекции («ignore previous instructions»)
- Не использовать память модели как источник свежих фактов: ответ без ссылки = «не проверено», добавлять «по данным обучения на [дата]» (стр. 199)

## 7. Если хочу память — шаги
- 4 уровня: рабочая (окно модели), краткосрочная (последние + сводки), долгая (векторное/KV-хранилище), процедурная (постоянные подсказки) (стр. 78–88)
- Правило 70 %: на историю не больше 70 % окна, 30 % — на рассуждения; превышение портит точность и выполнение инструкций (стр. 80; 82)
- Сжать старое в сводку, полное — в долгую память (в коде примера книги: max_context_tokens=100000, сжатие при > 80 % (стр. 78–79); но жёсткое правило — 70 %, сводка каждые 5 итераций (стр. 79, 81))
- «Ориентиры» (landmarks): ключевые решения, ошибки, дорогие операции — не удаляются никогда. Пять сигналов: смена плана, отзыв пользователя, смена состояния, восстановление после ошибки, расход > $0.01 (стр. 82–83)
- Не делать: слать всю историю в каждый вызов (стр. 80)
- Бюджет окна (стр. 290–291): 40 % рабочее, 20 % ориентиры, 20 % найденное, 20 % система+инструменты
- Ещё (стр. 290–291): скользящее окно 5–10 сообщений; сжатие каждые 5–10 шагов (−60–80 %); черновик отдельно от диалога; хранилище предпочтений; кэш проверенных фактов; не удалять сообщения пользователя и ориентиры; версии состояния; состояние в типизированных объектах, не в тексте; проверка правил после каждого изменения; откат к последнему «хорошему» состоянию. Предупреждение: слишком частое сжатие теряет важное

## 8. Если нужен журнал и наблюдение — шаги
- 5 «столпов»: трассировка, метрики, логи, оповещения, повтор (replay) (стр. 125–126). Одну платформу трассировки, не две (стр. 126; 136)
- Трассировка: оборачивать запрос в «след», внутри — вложенные «отрезки» на каждый вызов модели/инструмента; ошибка помечает отрезок (стр. 129–131). Не печатать просто print — не поискать (стр. 129–133)
- Автоанализ сбоев: циклы, лишние шаги, всплески расходов, один инструмент > 60 %, цепочки ошибок. Пороги: max_steps 20; предупреждение бюджета 0.8; падение качества 0.7; доминирование инструмента 0.6; цикл — повтор последовательности действий длиной от 3 (cycle_min_length); ошибок 0.1 (стр. 130–132)
- Replay: воспроизвести рабочий след (записанный / живой / смешанный режим) и считать расхождения; самый ценный инструмент отладки (стр. 134–135; 142)
- Пороги тревог (стр. 140–141): успех < 93 % warning, < 85 % critical; P95 задержки > 10 с / > 30 с; цена запуска > 2× / > 5× обычной; ошибки инструментов > 3 % / > 10 %; циклы ≥ 1 / ≥ 5 в час; дневной бюджет > 80 % / > 95 %
- Метрики-триггеры (стр. 133–134): шаги P95 > 2× обычных; цена P95 > 0.8 бюджета; падение успеха > 10 %; P95 задержки > 3× медианы
- Падение успеха — 5 шагов: проверить исход → найти точку расхождения → классифицировать причину → найти похожие падения за 7 дней → предложить исправление (стр. 139–140)
- Хранить следы 90 дней, раз в неделю делать из них наборы проверок (стр. 136–138)

## 9. Если хочу ошибки и восстановление — шаги
- 5 категорий (стр. 144): 1) временные (таймаут, лимит) — повтор с паузой; 2) инструментальные — поправить аргументы / запасной инструмент; 3) модельные (галлюцинации) — перезапрос, 1–2 шага; 4) состояния (переполнение) — откат к чекпойнту; 5) логические (плохой план, зацикливание) — пересмотр плана или человек. Логические опаснее всех; ≈ 80 % усилий на категории 3–5
- Повтор с нарастающей паузой: `delay = min(1 с × 2^попытка, 60 с)`, плюс случайный множитель 0.5–1.5 (jitter); по умолчанию до 3 повторов (стр. 144–146)
- Не делать: повторять НЕ-идемпотентное действие без проверки результата (стр. 146)
- Таблица повторов (стр. 147): 429 — да, до 5, по `Retry-After`; 500 — да, до 3; 401 и 400 — НЕТ, исправить ключ/запрос; таймаут — до 2, упростить ввод; обрыв связи — до 3; отказ модели — 1 раз, переформулировать; выдуманный инструмент — до 2
- Цепочка запасных путей: поиск 1 → поиск 2 → знания модели с оговоркой (стр. 147–148)
- Circuit breaker: CLOSED / OPEN / HALF_OPEN; 5 ошибок → OPEN; через 60 с пробует HALF_OPEN; 2 успеха → CLOSED (стр. 149–151)
- Деградация: отдать лучший возможный ответ и честно написать ограничение («по данным обучения, возможно устарело», «код не проверен», «бюджет исчерпан, вот что нашёл») (стр. 152)
- Не глотать ошибки молча: восстановить с записью, или передать человеку, или деградировать (стр. 155–156)
- Дерево решений (стр. 158): временная → повтор ≤ 3; есть запасной → включить и записать; можно частичный результат → отдать с оговоркой; известный сбой → исправить и добавить тест; иначе → человеку с полным следом

## 10. Если хочу человека в цикле (HITL) — шаги
- Паттерны: ворота подтверждения, пороги уверенности, журнал, постепенная автономия (стр. 89)
- Лестница автономии (стр. 97): первые 20 действий под надзором; ≥ 85 % одобрений (в тексте книги — на 50+ действий) → полуавто; ≥ 95 % на 100+ действий → авто
- Цель: человек смотрит < 10 % действий, но ловит > 95 % ошибок (стр. 92; 97)
- Усталость от подтверждений: медиана времени одобрения < 3 с → «штамп без чтения», пересмотреть (стр. 90; 96)
- Таймаут запроса: низкий риск → авто-одобрить, средний → отложить, высокий → отказать (стр. 93; 97)
- В юридическом, финансовом, медицинском — человек обязателен независимо от уверенности (стр. 97)
- Запрос человеку: кнопки Одобрить / Отклонить / Изменить, с контекстом; пакетное одобрение рутины (стр. 92–95). Не делать: запрос без контекста, только «да/нет» без «изменить» (стр. 94–95)

## 11. Если хочу проверить агента (eval) — шаги
- Свой набор проверок: 1) критерии успеха (формат, вред, задержка, цена) 2) набор случаев: обычные 40–50 %, крайние 20–30 %, атаки 15–20 %, регрессия 10–15 % 3) раннер с лимитом задержки и цены (стр. 102–105)
- «Прошёл» = оценка ≥ 0.8 и задержка в лимите и цена в лимите (стр. 119)
- Способы оценки: точное совпадение; нечёткое; по смыслу (сходство > 0.85); по правилам; LLM-судья 1–10 (стр. 106–107). Для кода — pytest (стр. 112)
- Любое изменение агента — A/B на полном наборе, 3 прогона на случай; внедрять при p < 0.05 и улучшении (стр. 108–109)
- «Eval — это продукт»: каждый баг → тест; деплой только после прохождения набора; не откладывать eval на конец (стр. 109–110)
- Цикл REFINE: записать → выделить 5 частых ошибок → превратить в тесты → улучшить и проверить A/B → следить за трендом → добавлять ≈ 10 кейсов в неделю (стр. 111–112)
- 92 % успеха ≠ «готово»: разобрать 8 %, насколько опасны сбои; норма — обычные случаи > 95 % и нет опасных видов сбоев (стр. 113–114)
- Нестабильные тесты: повторять 10 раз, искать причину (температура > 0, время инструмента, строгая оценка); удалять нельзя; цель < 2 % нестабильных из 50 за 2 недели (стр. 123)
- Подводные камни: недетерминизм; сравнение только итога пропускает качество пути; опаснее всего «правдоподобный неверный ответ с высокой уверенностью» (стр. 99–100)

## 12. Если хочу экономить деньги — шаги
- Формула: `(токены_вход × цена_вход + токены_выход × цена_выход) × итерации` (стр. 163–164). Месяц: запросы/день × итерации × токены/1000 × цена за 1K × 30 (стр. 13–20)
- Не считать выход бесплатным: он в 5–10 раз дороже входа; ставить `max_tokens` под задачу (стр. 164)
- Маршрутизация: классификация, извлечение, роутинг — дешёвая модель (max_tokens 50–500, temperature 0); рассуждение, план, синтез — средняя; судья и сложное — премиум (стр. 164–165)
- Кэш: точный (SHA-256, TTL 1 ч); по смыслу (порог 0.95, ошибок < 1 %; 0.90 даёт +12 % попаданий, но 8 % ложных); кэш системного промпта до 90 % экономии входа (стр. 165–171)
- Бюджет-сторож: лимит на запуск (в примере $1) и на день ($500); при превышении — принудительный синтез или отложить на завтра (стр. 168–170). Делёж: план 10 %, исследование 60 %, синтез 20 %, буфер 10 %; жёсткий обрыв на $1.00 (стр. 172–173)
- Оценки эффекта (стр. 170–171): роутинг 40–70 %; кэш промпта 15–40 %; точный кэш 20–50 %; сжатие промпта 10–30 %; ранний выход 15–25 %; пакеты 30–50 %; дообучение 50–80 %
- Первые 50 % экономии почти даром, дальше — торг с качеством (стр. 175)
- Тревоги по дневному бюджету: 50 %, 80 %, 100 % (стр. 296)

## 13. Если хочу нескольких агентов — шаги
- Паттерны: иерархия, равноправные, конвейер (стр. 68–78). Каналов связи `N·(N−1)/2` (5 агентов → 10, 10 → 45) (стр. 71)
- «Налог на координацию»: > 30 % токенов на общение → меньше агентов/каналов (стр. 71; 75)
- Для каждой роли — карточка: уровень модели, инструменты, промпт, форматы, поведение при ошибке (стр. 75)
- Разногласия: голосование → арбитраж → человек (стр. 74)
- Начинать со своего кода; фреймворки — для прототипов (стр. 72)
- Шаблон «Супервизор» (стр. 330–331): max_steps 12, общий бюджет $2.00; разбить → запустить параллельно → проверить каждый вывод → провал: один повтор, потом решать самому; бюджет на каждую подзадачу
- Не делать: свободный обмен всех со всеми (стр. 71)

## 14. Если хочу запуск с нуля — план 30 дней (стр. 257–272)

## 16. Если хочу кодового агента — шаги (стр. 176–190)
- Цикл write-test-fix: понять (собрать контекст) → план → писать → тесты → при провале исправить план; максимум 3 попытки, потом отчитаться, не зацикливаться (стр. 177–180; 186; 193)
- Главные сбои — из-за выбора контекста, не из-за генерации (стр. 181)
- Правка: по умолчанию «найти и заменить»; файл целиком — только новые (< 200 строк); номера строк избегать (стр. 182)
- Бюджет контекста: упомянутые файлы 30 %, импорты 25 %, grep 20 %, тесты 15 %, карта проекта 10 %; не читать лишнее, функции вместо всего файла, тест к каждой правке (стр. 182–184)
- Сначала тест, потом исправление: меньше «сломанных» правок (≈ 40 %) (стр. 188; 193)
- После 3 неудач добавлять в контекст полный diff: повторные ошибки 70 % → < 20 % (стр. 188)
- Деплой-агент (Devin): 4 фазы 10–60 мин; ждать 5–10 ошибок; эскалация, если застрял > 5 мин на шаге (стр. 191)

## 17. Если хочу исследовательского агента — шаги (стр. 194–209)
- Цикл: разбить вопрос → искать → читать и извлекать → синтез → проверка → итог с цитатами (стр. 194–195)
- Проверка цитат: пара «утверждение — ссылка» → открыть URL → SUPPORTED / CONTRADICTED / NOT_FOUND → не подтверждено: найти источник или убрать. +$0.30, точность 97 % против 80 % (стр. 200–201). Без проверки — 15–25 % выдуманных ссылок (стр. 199; 208–209)
- Противоречие: показать обе цифры, причины различий, оценить надёжность (рецензируемое > отраслевое > новости > блог), взять третий источник, дать диапазон (стр. 197–198)

## 18. Если хочу бизнес-процесс — шаги (стр. 210–222)
- Цикл: триггер → извлечь и проверить → правила → действия → исключения/эскалация → запись результата (стр. 211–212)
- Стоит ли автоматизировать: 6 факторов по 1–5 (объём, однотипность, данные, цена ошибки, ручное время, интеграции); ≥ 25/30 — полностью, 15–24 — с человеком, < 15 — не стоит (стр. 210–212)

## 19. Когда НЕ применять
- Креативный агент: не для новых идей, глубокой экспертизы, эмоционально чувствительного текста, уникального бренда — агент делает черновик и поиск, финал человеку (стр. 233)
- Цикл правок: не больше 3–4 ревизий (прирост 30 % → 10 % → 3 %); стоп, если улучшение < 0.05 (стр. 228–230)
- Не автоматизировать процесс с оценкой < 15/30 (стр. 210–212)
- Фреймворк не брать, если нужно > 30 % обходов, нужен мелкий контроль или ≥ 100 K запросов/день (стр. 317)
- Если берём фреймворк — оборачивать своим слоем для миграции (стр. 317). Выбор: несколько агентов → CrewAI; сложные ветки → LangGraph; простая цепочка/RAG → LangChain; максимум контроля → свой Python 50–200 строк (стр. 318)
- Не включать все защитные паттерны сразу: они добавляют токены и задержку; брать нужные (в книге дословно не найдено — вывод из стр. 12 «петли добавляют сложность и цену»)
- Перед автоматизацией проверить: часто ли повторяется, приемлема ли цена отказа, есть ли измеримый успех, доверят ли пользователи; хоть одно «нет» — пересмотреть (стр. 240)
- Продукт: ошибки пользователю по-человечески, не сырые (стр. 242); цель успеха ≥ 98 % до масштабирования (стр. 243; 246)
