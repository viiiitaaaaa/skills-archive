# Agentic Design Patterns (Gulli) — «как делать»

ЧЕРНОВИК. Всё ниже взято из конспектов `knigi_kupleno\glubokiy\agentic_design_patterns_01..16.md`. Конспекты писали открытые модели (gpt-oss:120b через Hermes), с книгой они НЕ сверены. Страница в скобках — как указано в конспекте. «Номер сомнителен» = номера в конспектах разных частей расходятся. Термины в скобках расшифрованы.

Формат строки: «Если хочу X — шаги — (стр.)».

## 0. Что такое агент и уровни (часть 1)
- Агент выполняет 5-шаговый цикл — шаги: 1) задать цель 2) собрать данные (почта, календарь) 3) построить план 4) выполнить 5) разобрать результат и поправиться (стр. 14)
- Выбрать сложность системы — уровни: 0 — LLM без инструментов, знания только из обучения; 1 — подключены инструменты (поиск, API, RAG); 2 — планирует, управляет контекстом (контекст-инжиниринг = выбор и упаковка информации для модели); 3 — команда специализированных агентов (стр. 16–18)
- Расти по ступеням: добавляй инструменты, память, планирование, связь между агентами (стр. 16–18; шаги «переходить от 0 к 3» — формулировка конспекта)
- В книге 21 паттерн и три «каркаса»: LangChain/LangGraph, Crew AI, Google ADK (стр. 13)
- Три принципа ответственности: чёткая задача, предвидеть сбои, быть открытым и отвечать за результат (стр. 9). Слепо доверять нельзя; грязные данные дают «правдоподобный мусор» (стр. 8–9; конспект части 1)

## 1. Цепочка промптов (Prompt Chaining) — гл. 1
- Разбить сложную задачу на малые запросы, вывод шага — вход следующего — шаги: 1) выделить подзадачи 2) свой промпт на каждую 3) идти по очереди 4) независимые шаги — параллельно 5) собрать итог 6) при нужде между шагами вставить инструмент (калькулятор, OCR — распознавание текста с картинки) (стр. 26–35; номер сомнителен: в части 1 глава на стр. 23–25)
- Образец из 3 шагов: сводка отчёта → 3 главных тренда с цифрами → письмо команде (стр. 23–25)
- Между шагами передавай JSON/XML, не свободный текст: иначе ошибка с первого шага разрастается (стр. 25; формулировка «Ошибки» в конспекте)
- Зачем: один длинный запрос → игнор части инструкций, потеря контекста, размножение ошибки, выдумки (стр. 24–25)
- Когда применять: задача слишком сложна для одного запроса, нужно несколько фаз, внешние инструменты или состояние (стр. 33)
- Можно дать шагам роли (аналитик, редактор) (стр. 24)
- Проверяй промежуточный результат: слабая проверка = ошибка в итоге (стр. нет в конспекте)
- Арифметику отдай калькулятору, не LLM (стр. нет в конспекте)
- Примеры цепочек из конспекта: вопрос по частям (подвопросы → поиск → синтез); извлечение полей из счёта + проверка + повтор по недостающим; идея → план → черновик → правка; код: псевдокод → код → анализ → исправление → тесты/документация (стр. 33–34)
- В LangChain цепочка пишется как `prompt | llm | StrOutputParser()` (стр. нет в конспекте)

## 2. Маршрутизация (Routing) — гл. 2
- Агент должен выбрать ветку по смыслу запроса — шаги: 1) определить тип запроса 2) сопоставить метку с обработчиком 3) передать ему 4) при желании обновить состояние 5) метка «unclear» → переспросить (стр. 36–49; номер сомнителен)
- Способы определить тип: через LLM («выведи только одну метку»), через эмбеддинги (векторы смысла запроса против прототипов), по правилам if/else (быстро, негибко), обученным классификатором (стр. 37–38)
- Образец промпта: «Analyze the user query and output only the category: Order Status / Product Info / Technical Support / Other» (стр. 36–37)
- Применять, когда веток ≥2 и выбор зависит от намерения, состояния или результата прошлого шага (стр. 37–38)
- Обязательно запасная ветка «unclear», иначе система зависнет без ответа (стр. нет в конспекте; это вывод из «Ошибок» конспекта)
- Плохая классификация или пересекающиеся метки = запрос уйдёт не туда (стр. нет в конспекте)
- Код-образцы: LangChain RunnableBranch (стр. 40–42), Google ADK «Coordinator» с делегированием (стр. 43–46)

## 3. Параллель (Parallelization) — гл. 3
- Ускорить, если шаги не зависят друг от друга — шаги: 1) найти независимые подпроцессы 2) каждый — своя цепочка 3) собрать в `RunnableParallel` 4) отдать всем один вход 5) дождаться всех 6) один итоговый шаг синтеза (стр. 50–57 и 57–64; номер сомнителен — две части дают разные диапазоны)
- Асинхронность в Python даёт «конкурентность» (одновременное ожидание сети), не настоящий параллелизм из-за GIL (стр. 51–53)
- Применять, когда ≥2 независимых внешних вызова (стр. 51–53). (цифра «выигрыш 2–5 раз» в конспекте не найдена — убрана)
- Пример: исследователь одновременно берёт новости, котировки, соцсети, базу компаний (стр. 52–53)
- Риски: лимиты API, ошибка в одной ветке виснет вся цепочка, подзадачи на деле зависимы (гонки данных), отладка сложнее (стр. нет в конспекте / стр. 62–64)
- В Google ADK: `ParallelAgent` с под-агентами, потом `SequentialAgent([параллель, слияние])` (стр. 58–61)

## 4. Рефлексия (Reflection) — гл. 4
- Улучшить результат самопроверкой — шаги: 1) сделать черновик 2) отдельный запрос-«критик» оценивает 3) если критик пишет маркер «CODE_IS_PERFECT» — стоп, иначе замечания идут в новую генерацию 4) повторять до стопа или до лимита 5) сохранить итог (стр. 66–68)
- Лимит итераций в примерах — 3 (`max_iterations = 3`) (стр. 66–68)
- Два вида: «проверь свою работу» и «внутренний критик» (отдельный агент или запрос по критериям) (стр. 478)
- Применять, когда качество важнее скорости и цены (стр. 66–68)
- Цена и задержка растут с каждым кругом, контекст заполняется историей (стр. нет в конспекте)
- Простая передача вывода в следующий запрос — это не рефлексия, часто лишь перефразирование (стр. 478)
- Тот, кто пишет, может не увидеть своих ошибок — лучше отдельный проверяющий (стр. 192)
- Номера страниц: главу даёт конспект 3 как 65–78; повтор в итогах части 16 — стр. 478–479

## 5. Инструменты (Tool Use / вызов функций) — гл. 5
- Дать агенту внешние действия — шаги: 1) описать инструмент (имя, параметры, типы, описание) 2) подключить к фреймворку (LangChain `@tool`, CrewAI `@tool`, ADK `tools=[…]`) 3) LLM решает, нужен ли вызов, и выдаёт JSON 4) оркестратор выполняет 5) результат возвращается модели 6) модель отвечает (стр. 79–88; ещё 97–99)
- Цикл вызова: определение → решение LLM → вызов → исполнение → наблюдение → обработка (стр. 80)
- Нужна модель с поддержкой вызова функций (стр. нет в конспекте / формулировка части 3)
- Кривое описание параметров = кривой JSON-вызов (стр. нет в конспекте)
- Исключения инструмента ловить, иначе прервут запуск (стр. нет в конспекте)
- При ошибке: распознать, решить — повторить, взять другой инструмент или спросить пользователя (стр. 479)
- Огораживай права инструмента или проси подтверждение человека — безопасность (стр. 479)
- ReAct = мысль → действие → наблюдение (стр. 479)
- Готовые в Google ADK: `google_search` (стр. 89–90), `BuiltInCodeExecutor` для кода в «песочнице» (стр. 91–94; `instruction`: выдавать только число), Vertex AI Search по своей базе, `temperature=0.0` (стр. 95–96)
- Vertex Extensions выполняются платформой сами, не вручную (стр. 96–97)
- Для Jupyter/Colab: `nest_asyncio.apply()`, иначе `RuntimeError` о запущенном цикле (стр. 90)

## 6. Планирование (Planning) — гл. 6
- Нужно решить задачу, где «как» заранее неизвестно — шаги: 1) убедиться, что нужен план 2) агент строит план (список шагов, например JSON-массив) 3) исполнять по порядку, передавая результат вперёд 4) при сбое или новых ограничениях — перепланировать 5) при желании дать человеку утвердить план (стр. 100–101; 478–479)
- Если процесс полностью известен — не планируй, а зафиксируй рабочий процесс (стр. 101)
- Без проверки статуса шага агент «застрянет» (стр. нет в конспекте)
- Пример Crew AI: один агент «планировщик и автор», задача «сначала список пунктов, потом текст», `Process.sequential` (стр. 102–103)

## 7. Мульти-агент — гл. 7
- Разделить многодоменную задачу между специалистами — шаги: 1) разбить на подзадачи 2) завести агентов-специалистов с целью, ролью, инструментами 3) выбрать схему общения: передача по цепочке / параллель / дебаты и согласие / иерархия (менеджер раздаёт и собирает) 4) договориться о форматах сообщений (JSON) 5) собрать в фреймворке (Agent, Task, Crew) 6) обработать падение агента: запасной или продолжить остальными (стр. 113–121; 129–131)
- Применять, когда один агент не справляется и задача делится на независимые куски с разной экспертизой (стр. 129; 480–481)
- Роль оркестратора: получает цель, разбивает, назначает, собирает и синтезирует; связь через него или общий «блокнот» (scratchpad) (стр. 480–481)
- Плюсы: модульность, проще отладка, разные взгляды (стр. 481). Минус: сложная координация и протоколы обмена (стр. нет в конспекте)
- Образец Crew AI: исследователь + автор, `context=[research_task]`, `Process.sequential` (стр. 119–121)
- В ADK: свой `BaseAgent` для обычного кода (стр. 122–123); `LoopAgent` с `max_iterations=10` и сигналом остановки `escalate=True` (стр. 123–124); `SequentialAgent` — передача через `output_key` в `session.state` (стр. 124–125); `ParallelAgent` — у каждого свой `output_key` (стр. 125–126); агент как инструмент через `AgentTool` (стр. 126–129)
- Нет `output_key` у шага — результат не сохранится в state (стр. 124–126)
- `LlmAgent` без `model` — ошибка при создании (стр. 122–124)
- Пятёрка командных ролей для кода (раздел 21 ниже)

## 8. Память — гл. 8
- Два уровня: краткая (окно контекста, `session.state`) и долгая (БД, векторные хранилища, граф) (стр. 132–133; 151–152)
- Хранить текущие шаги — в `state`, постоянные знания — в `MemoryService` (стр. нет в конспекте; вывод из стр. 151–152)
- В ADK: Session (id, события, state), State с префиксами `user:` (на пользователя во всех сессиях), `app:` (на всё приложение), `temp:` (только на ход, не сохраняется) (стр. 135–139)
- Какой SessionService брать: `InMemory` — разработка и тесты; `Database` (пример `sqlite:///my.db`) — продакшен; `VertexAi` — облако Google (стр. 135–138)
- Менять state только через `output_key` или `EventActions.state_delta`, не прямо в `session.state` — иначе обходит журнал событий и не сохранится (стр. 137–141)
- Долгая память: `InMemoryMemoryService` (тесты), `VertexAiRagMemoryService` с `similarity_top_k=5` и `vector_distance_threshold=0.7` (стр. 142–144)
- LangChain/LangGraph: `ChatMessageHistory`, `ConversationBufferMemory` (`return_messages=True` для чат-моделей), `InMemoryStore`; `VertexAiMemoryBankService` сам вытаскивает факты из диалогов (стр. 143–151)

## 9. Обучение и адаптация — гл. 9
- Виды: RL (награды/штрафы), с учителем, без учителя, few/zero-shot, онлайн, на памяти (стр. 154)
- PPO: 1) собрать траектории (состояние, действие, награда) 2) цель с «обрезкой» отклонения 3) маленькие шаги обновления (стр. 155)
- DPO (прямая оптимизация по предпочтениям): без отдельной модели-награды — 1) пары «лучше/хуже» от людей 2) поднять вероятность лучшего, снизить худшего (стр. 155–156)
- SICA (агент, правящий свой код): 1) архив версий и результатов 2) выбрать лучшую по успеху, времени, затратам 3) она правит код 4) бенчмарк 5) повтор (стр. 157). Есть «надзирающий» LLM, который по журналу ловит зацикливание и может прервать (стр. 160–162)
- AlphaEvolve/OpenEvolve: LLM предлагает варианты, автооценщик меряет, лучшие мутируют (в OpenEvolve `iterations=1000`) (стр. 161–163). Цифры из конспекта: -0,7% ресурсов дата-центров, ядро +23%, FlashAttention до 32,5% (стр. 161) — не проверено по книге
- Трудно заставить агента придумывать действительно новые правки (стр. 161)

## 10. MCP (Model Context Protocol) — гл. 10
- Подключать внешние сервисы единым способом — клиент-сервер: сервер объявляет resources (данные), tools (действия), prompts (шаблоны); клиент сам обнаруживает их и вызывает (стр. 167–172)
- Простая задача — хватит вызова функций; много меняющихся инструментов — MCP (стр. 169–171)
- Учесть: аутентификация, коды ошибок, транспорт (локально — STDIO/JSON-RPC, удалённо — HTTP/SSE), данные должны быть удобны агенту (PDF → Markdown) (стр. 168–173)
- Файловый агент ADK: `MCPToolset` + `StdioServerParameters` (npx, пакет `@modelcontextprotocol/server-filesystem`, абсолютный путь), ограничить набор `tool_filter`, запуск `adk web`, нужен `__init__.py` (стр. 174–176)
- Свой сервер на FastMCP: `pip install fastmcp` → `@mcp_server.tool` → `run(transport="http", host="127.0.0.1", port=8000)` → на стороне агента `HttpServerParameters`; типы и docstring нужны, иначе модель не поймёт (стр. 177–180)
- Удалённый сервер — обязательно аутентификация (стр. 177–180)

## 11. Цели и мониторинг — гл. 11
- Чтобы агент знал, достиг ли цели — шаги: 1) задать цель (SMART: конкретная, измеримая, достижимая, релевантная, ограниченная по времени) 2) определить исходное состояние 3) план 4) выполнять 5) постоянно сверять метрики 6) при угрозе цели перепланировать (стр. 183–185; 191–195)
- Чек-лист качества для кода: «просто», «работает», «краевые случаи» (стр. 191–195)
- Цикл «генератор кода»: 1) собрать промпт (use case + цели + прошлый код + замечания, «верни только код») 2) получить код 3) отдельный запрос-рецензент 4) вопрос «цели достигнуты? только True или False» 5) False → передать код и замечания, повторить 6) максимум 5 итераций (стр. 186–188)
- Параметры примера: `temperature=0.3`, имя файла: короткое имя до 10 символов + случайный суффикс 1000–9999 (стр. 186–188)
- Ловушки: LLM может ошибочно сказать True — код проверять вручную; без лимита цикл бесконечен; пример «не для продакшена» (стр. 187–192)

## 12. Ошибки и восстановление — гл. 12
- Обнаруживать: сбой ответа инструмента, HTTP 404/500/503, таймаут, не тот формат (стр. 196–197)
- Обрабатывать: лог, повтор (retry), запасной путь (fallback), урезанная работа (graceful degradation), уведомить человека (стр. 196–203)
- Восстанавливать: откат состояния, самокоррекция плана, эскалация человеку (стр. 196–203)
- Образец ADK: `SequentialAgent([primary_handler, fallback_handler, response_agent])`; запасной смотрит флаг `state["primary_location_failed"]` (стр. 199–200)
- Ставить тайм-ауты и лимит попыток, иначе зависнет (стр. нет в конспекте / «Ошибки» части 7)
- Правило-ориентир на надёжность: чекпоинты и откат после значимых шагов (стр. 302–305)

## 13. Человек в контуре (HITL) — гл. 13
- Роли: наблюдение, правка ошибок, обратная связь для обучения, помощь в решении (ИИ советует, человек решает), правила эскалации (стр. 204–212)
- Точки пауз: утверждение плана; подтверждение действия с последствиями или затратами; снятие неясности; проверка финала (стр. 480)
- Шаги: 1) определить чекпоинты 2) приостановить 3) запросить одобрение 4) продолжить или изменить план (стр. 480)
- Агент сам просит человека, если неуверенность выше порога (инструмент `escalate_to_human`) (стр. 208–210)
- Минусы: не масштабируется, нужны квалифицированные операторы, данные перед передачей анонимизировать (стр. 206)
- Слишком частые паузы убивают эффективность (стр. 480)

## 14. RAG (поиск знаний) — гл. 14
- Как работает: 1) нарезать документы на куски (chunking) 2) эмбеддинги (векторы смысла) 3) положить в векторную или графовую базу 4) по запросу найти топ-K похожих 5) добавить в промпт 6) LLM отвечает, можно с цитатами (стр. 213–218)
- Параметры примера: `SIMILARITY_TOP_K = 5`, `VECTOR_DISTANCE_THRESHOLD = 0.7` (стр. 222); нарезка `chunk_size=500, chunk_overlap=50` (стр. 223–225)
- Гибридный поиск: BM25 + смысловой (стр. 213–216)
- Проблемы: плохая нарезка = шум; противоречия в источниках; ответ разбросан по кускам — неполный ответ; индекс надо обновлять; нужна поддержка базы (стр. 215–217)
- GraphRAG (граф знаний вместо векторов): склеивает разбросанное, лучше для сложных вопросов, но дорого и медленно (стр. 217–218)
- Agentic RAG (агент проверяет найденное): проверить дату и авторитетность, решить конфликты, разбить вопрос, при пробеле позвать веб-поиск; минус — сложнее, дороже, свои баги (стр. 218–220)
- Применять, когда нужен свежий или доменный контекст, которого нет в обучении LLM (стр. 226)
- Номера сомнительны: часть 7 даёт RAG на стр. 213–216, часть 8 — на 217–229

## 15. Связь агентов (A2A) — гл. 15
- A2A = общий протокол агентов разных стеков поверх HTTP и JSON-RPC 2.0 (стр. 231–232)
- Участники: пользователь, A2A-клиент, A2A-сервер (стр. 232)
- Agent Card — JSON-визитка: name, description, url, version, capabilities, authentication, skills (стр. 232–233)
- Найти агента: `/.well-known/agent.json`, каталог, ручная настройка (стр. 233–234)
- Задача (Task): submitted, working, completed, failed; сообщение (Message), результат (Artifact), `contextId` группирует задачи (стр. 235–236)
- Способы: синхронный `sendTask`, опрос по `taskId`, поток SSE `sendTaskSubscribe`, push-вебхуки (стр. 236–238)
- Безопасность: mTLS, журнал аудита, схемы авторизации в карточке (стр. 236–237)
- MCP даёт контекст и инструменты модели; A2A — связь между агентами; не заменяет MCP (стр. 237–238; 244–245)
- Применять, когда оркестрируешь нескольких специализированных агентов разных фреймворков (стр. 242–244)

## 16. Экономия ресурсов (Resource-Aware) — гл. 16
- Выбирай модель по сложности: простое — дешёвая и быстрая (Gemini Flash), сложное — мощная (Pro) (стр. 246–247)
- Запасной вариант (fallback) при перегрузе или таймауте (стр. 246–247)
- Роутер из примера: если слов в запросе меньше 20 — Flash, иначе Pro (стр. 248–250). Улучшать роутер можно подбором промпта или дообучением
- Критик-агент: если дорогая модель решила простой запрос, роутер учится слать такие дешевле (стр. 250–251)
- Классификатор запроса возвращает один из трёх: `simple` (факт), `reasoning` (логика, математика), `internet_search` (свежее) в JSON (стр. 252). Модели из примера: simple → gpt-4o-mini, reasoning → o4-mini, поиск → gpt-4o + результаты Google (стр. 253–254)
- OpenRouter: `"model": "openrouter/auto"` — сам подберёт; или список `models` — переключится при ошибке; не указывать `model` и `models` вместе (стр. 256–257)
- Приёмы: смена модели, выбор дешёвого инструмента, обрезка и сжатие контекста, прогноз нагрузки, учёт цены общения агентов, энергосбережение, параллель, обученные политики, мягкая деградация (стр. 258–261)
- Применять, когда бюджет API ограничен, нужна малая задержка или устройство слабое (стр. 259)

## 17. Рассуждение — гл. 17
- Дай модели больше «времени на подумать» на сложное (стр. 262–264)
- CoT (по шагам): скелет из 5 шагов — разобрать запрос; составить поисковые запросы; представить найденное; собрать; проверить и отшлифовать (стр. 265–267). Zero-shot CoT = «Let's think step by step»; ответ ставить ПОСЛЕ рассуждения; для однозначных задач `temperature=0` (стр. 360–361)
- Самокоррекция, 5 шагов: перечитать запрос; прочитать текст; найти слабое; предложить правки; выдать новую версию (стр. 268–269)
- PALM: LLM пишет Python, исполняет через `code_executor`, переводит результат словами; без `code_executor` код не выполнится (стр. 270–271)
- ReAct: Thought → Action → Observation, повторять до ответа; для фактов мысль после каждого действия, для длинных планов реже (стр. 271–272; 281–282)
- Дебаты: Chain of Debates — несколько моделей спорят; Graph of Debates — утверждения как граф, итог — наиболее поддержанный кластер (стр. 272–273)
- MASS (поиск топологии агентов): 1) настроить промпты блоков 2) подобрать топологию 3) настроить промпты всего процесса (стр. 274–275)
- Закон масштабирования вывода: малая модель + много вычислений ≈ большая модель + простой вывод; несколько вариантов и выбор лучшего (стр. 276–278)
- Deep Research: поиск → анализ пробелов → дополнительный поиск → статья с цитатами (стр. 276–277)
- DeepSearch/LangGraph: узлы `generate_query → web_research → reflection → finalize_answer`; нужны Redis, Postgres, ключ LangSmith (стр. 278–281)

## 18. Guardrails (защитные ограничения) — гл. 18
- Слои защиты: проверка входа; фильтр выхода; ограничения в промпте; ограничения инструментов; внешняя модерация; человек в контуре (стр. 286–287)
- Быстрый фильтр-щит на дешёвой модели (Gemini Flash Lite) (стр. 298). CrewAI-образец: политика из 4 групп — обход правил (jailbreak), запрещённый контент, не по теме, чужая/конкурентная информация; результат разбирается Pydantic-моделью, ошибка JSON → «не прошло» (стр. 287–298)
- Проверка до вызова инструмента: callback `before_tool_callback`; блокирует, если `user_id` в аргументах не совпал с сессией (стр. 298–302)
- Инженерные принципы: модульность, наблюдаемость (структурные логи), минимум прав, отказоустойчивость; чекпоинты и откат (стр. 302–305)
- Применять везде, где вывод влияет на пользователей, системы или репутацию (стр. 306)

## 19. Оценка и мониторинг — гл. 19–20
- Метрики: точность, задержка, расход токенов, соблюдение правил; A/B-тесты, дрейф входных данных, аномалии, аудит (стр. 306–307)
- Простая проверка точности — строгое сравнение строк 1.0/0.0; не терпит парафраз, годится лишь как дымовой тест (стр. 307–309)
- Задержку писать в структурные логи или базу временных рядов (InfluxDB, Prometheus) (стр. 309–310)
- Токены: считать входные и выходные; пример со `split()` — только иллюстрация, нужен токенизатор API (стр. 310–312)
- LLM-судья: рубрика (ясность, нейтральность, уместность, полнота, подходит аудитории), вывод в JSON; проверять пустые ответы из-за модерации (стр. 311–315)
- Сравнение методов: человек (тонко, дорого), LLM-судья (масштабируется, пропускает шаги), автометрики (быстро, неполно), траектории (оценивают процесс, трудно в мульти-агенте) — лучше смешивать (стр. 315)
- Траектория агента: сверять с эталоном — точное совпадение, по порядку, в любом порядке, precision, recall, один инструмент (стр. 316). В рискованных задачах строгий exact match (стр. 316)
- Тестовые файлы: JSON одной сессии с несколькими ходами (стр. 316); evalset — многосессионный набор (стр. 317); запуск ADK: web UI, pytest `AgentEvaluator.evaluate(...)`, CLI `adk eval <модуль> <evalset> [--config ...] [eval1,eval3]` (стр. 320–322)
- Мульти-агент: проверять передачу данных, соблюдение порядка (отель не раньше рейса), выбор нужного агента, масштабируемость (стр. 317)
- «Контрактор» (агент по договору): формальный контракт; переговоры и уточнения; итерации с автотестами; подконтракты (стр. 318–320)
- Без детерминированного текста: в тестах ищи ключевые признаки (дата, вызов `send_email`), не весь текст (стр. 481). Журнал: мысли, вызовы, наблюдения (стр. 481)
- Оценка по результату, по процессу, человеком (шкала 1–5) (стр. 481)

## 22. Приёмы промптов (приложение A) и фреймворки
- Принципы: ясно, кратко, позитивные формулировки («делай»), чёткий глагол действия; экспериментировать с формулировкой и параметрами (стр. 350–351; 374–376)
- Zero/one/few-shot: примеры 3–5, разнообразные, без ошибок, при классификации перемешать классы (стр. 351–353)
- System prompt (глобальные правила), role prompt (роль), разделители (теги `<instruction>`, `<article>`) (стр. 353–356)
- Контекст-инженерия: слои — системный промпт, внешние данные, неявные данные (пользователь, история); смотреть конфиденциальность (стр. 355–357)
- Структурированный вывод: JSON + Pydantic `model_validate_json` (стр. 357–359)
- Self-Consistency: много путей при высокой температуре и голосование (дорого) (стр. 362). Step-Back: сначала общий принцип, потом задача (стр. 363). Tree of Thoughts: дерево ветвей с откатом (стр. 363–364)
- Автоподбор промптов и итерации; «негативные примеры» могут запретить нужное; автооптимизация переобучается на тестовый набор (стр. 366–369)
- Лучшие практики: примеры, простота, указать формат, макс. длина, переменные в шаблонах, документировать попытки, хранить промпты в коде, автотесты, перетестировать при смене модели (стр. 374–376)
- Системный промпт агента: роль и цель; список инструментов; ограничения; процесс; примеры траекторий; следить за «утечкой» инструкций в ответ (стр. 482)
- Фреймворки: LangChain — линейные цепочки (стр. 385–386); LangGraph — граф с циклами и общим состоянием (стр. 386–387); Google ADK — готовые паттерны (стр. 388–389); Crew.AI — команда с ролями (стр. 389–390). Остальные (AutoGen, LlamaIndex, Haystack, MetaGPT, SuperAGI, Semantic Kernel, Strands) — кратко (стр. 390–391)
- Агент с компьютером (ACI): скриншот → распознать элементы → понять → действовать; учесть задержки и всплывающие окна (стр. 378–381)
- CLI-агенты (Claude Code, Gemini CLI, Aider, Copilot CLI) — кратко (стр. 399–403)
